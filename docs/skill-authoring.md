# Skill 撰寫與維護準則

**這份文件給「改 skill 的人」看,不會在執行時被載入。** 這個分界是刻意的:操作程序留在 `SKILL.md` 與 `_shared/`,維護準則、設計理由、事故紀錄留在這裡。少了這個分界,每次事故的檢討都會沉澱進執行路徑,文件慢慢變成事故紀錄而不是操作程序。

## 成本模型

skill 的成本不是檔案長度,是**執行者一次要同時記住多少條規則**。實際的單次成本是:

```
SKILL.md + 該 skill 會讀到的 _shared 分片
```

所以共用層的每一行,都乘上讀它的 skill 數量。量測:

```bash
cd plugins/dev-flow
for f in skills/*/SKILL.md skills/_shared/*.md; do printf "%4d %s\n" "$(wc -l < "$f")" "$f"; done
```

各 skill 的 `description` 是**永遠在 context** 的(約 8 KB / 13 個 skill),但那是觸發判斷的必要成本,不是優化對象。

## 第二種成本:序列往返

上面那個公式量的是**一次執行帶著多少字**。它漏掉了實際更貴的那一半:**這一次執行要來回幾趟**。

每一趟工具呼叫都是一次完整的 prefill + 思考 + 呼叫。載入 27k tokens 的 prefill 大約一兩分鐘;把同樣的東西拆成八個 Read 分八趟拿,是八次 prefill 疊起來,加上八段思考——那才是「一份 spec 花二十分鐘」的來源。所以:

- **載入行寫成清單,並明講「一批送出」。** 散文串起來的八個檔案,執行者會一個一個開;寫成表格加一句「禁止讀一個、想一下、再讀下一個」,同一批就收成一趟
- **佔位路徑要能一次解析、之後重用。** 腳本路徑寫成 `<S>/arch-audit/scripts/…`,`<S>` 的解析法在 `conventions.md`「腳本目錄」,各 SKILL.md 的載入行**各自複述那一道指令**——這是唯一刻意的重複:它要在 `conventions.md` 被讀進來**之前**就用得上(載入行自己就有一道 `doc-section.mjs`),放在共用層會變成雞生蛋
- **每個模式都要有自己的減載表。** 委派模式有、修訂模式沒有,那條路徑就會付全額。**新增執行模式時,同一輪要回答「這個模式不必讀什麼」**
- **會跑的東西要有紀律。** 規則在 `conventions.md`「跑東西的紀律」三關:該不該跑 / 是不是重跑 / 輸出怎麼留。它管的是測試套件、編譯檢查、lint、建圖——這四樣是流程裡唯一會以秒為單位計費的東西,而「保險起見再跑一次」在文檔裡看起來永遠是謹慎,不是浪費。
  這條規則原本只寫了中間那一關(「輸入沒變就不重跑」),漏掉的兩關各對應一次真實的浪費:**第一關**——那一次是整場對話的**第一次**跑,「重跑」紀律整條不成立,而它跑測試是為了判斷「文檔與程式碼哪一邊是舊的」,一個測試答不出來的問題;**第三關**——輸出被 `tail -8` 切掉統計行,於是換個過濾器再跑一次、再一次。**寫規則時要問「這條規則的觸發條件涵蓋得到第一次嗎」,以及「它擋得住換個旗標再跑一次嗎」**

## 自稱「機械比對」的,就該是腳本

文檔裡寫「**這是機械比對,不需要判斷力**」然後叫執行者用眼睛逐字比,是一個明確的訊號:那一段該搬進 `arch-audit/scripts/`。判準很簡單——**規則能不能只用文字比對做完**:

- 能(同名不同定義、`檔案#符號` 指不指得到、旗標認不認得、四格齊不齊)→ 寫腳本,接進 `tests/run.sh` 的 fixture 回歸
- 不能(這個觀察點真的看得見嗎、這條邊該不該納進宣告)→ 留給人,但腳本仍然可以把**候選清單**列出來,讓人只做判斷、不做搜尋

腳本一律走「**下限不是上限**」:機器查得到的那一格查到底,查不到的那一格在輸出裡明說「這一項機器判不了」。**最危險的不是漏查,是查了 0 筆卻印得像全部合格**——`lint-commands.mjs` 因此一律印出處數、`doc-section.mjs --verify` 找不到呼叫時直接當失敗、`lint-laws.mjs` 沒帶 `--skeleton` 時會自己說「沒有跑骨架對帳」。加新檢查時照這個規矩來。

## 輸出的每一行都會被單獨引用

回報、閘門呈報、腳本輸出的每一行,都會被複製到別的地方去讀:貼進 issue、貼進 PR、貼進下一次對話。所以**寫的時候要假設讀的人手上只有那一行**——這是 `_shared/conventions.md`「指稱紀律」那條規則的來源。

兩種失效各有代表:

- **編號沒有限定詞。** 每個子系統各有一組 `F001`/`E001`/`B001`,所以「E001 還沒做」這句話在子系統以外指不到任何東西。修法是全名 `<子系統>/<id>-<slug>`,檔案內的條目掛在文檔全名底下(`auth/F002-token-refresh 的 LAW-3`)。只有兩個地方寫裸 id:文檔自己的 frontmatter `id:` 欄與檔名——那兩處的上下文就是檔案本身
- **主詞受詞被代名詞吃掉。** 「它不在分母裡」「那份文檔要先改」在腳本輸出裡很常見,因為寫的人眼前有整張表。修法是每一句都寫出誰、對哪一份、做什麼

**新增任何一行輸出時**(腳本的 `console.log`、SKILL.md 的回報格式、模板的表格欄),自問一次:這一行被單獨貼到別處,讀得懂嗎?讀不懂就補限定詞,不要靠上下文。**限定詞讓表格變寬是可接受的代價**——寬表格還讀得懂,指不到東西的識別碼讀不懂。

配套的一件事:規則要求全名之後,**吃編號的入口都要吃得下全名**。`scan-status.mjs --doc`、`lint-cross-spec.mjs --docs` 因此同時接受 `auth/F002-token-refresh`、`auth/F002` 與 `F002`;不然回報裡的寫法貼回命令列就查不到,而人會退回去寫裸 id。

## 專案級的常數要有欄位,不要靠每次對話重問

`system.md` 的 `mode`(`greenfield` / `brownfield`)是第一個這種欄位:它決定**整類問題該不該問**,而那類問題(migration、向後相容、既有使用者)在全新專案裡連指涉對象都沒有。這種事實有三個特徵——**整個專案一個值、幾乎不變、決定一整類行為**——符合這三點就該是 frontmatter 的一欄,不是每場對話重問一次的口頭約定:口頭約定活不過一次 `/clear`,而猜錯的人不會知道自己猜錯。

配套是固定的三件事,缺一條這個欄位就會爛掉:**誰寫**(`/system-design` 訪談第 0 題)、**誰讀**(`boundary-rules.md` 定規則,設計與實作 skill 都讀得到)、**沒填怎麼辦**(`scan-status.mjs` 每次盤點都印那一行,缺了印 `⚠ 未宣告`)。第三件最容易漏:一個沒有人會抱怨它沒填的欄位,就是一個遲早全空的欄位。

## 昂貴的動作要有一張「跑幾次」的帳

「輸入沒變就不重跑」擋得住同一個角色連跑兩次,擋不住**四個角色各跑一次**——每一份 SKILL.md 單獨看都合理:qa 要驗自己的紅綠、impl 要確認實作、編排者要仲裁、閘門要驗收。加起來一份 spec 跑了六次整套測試,而沒有任何一份文件寫得出這個總數。

所以**昂貴的動作要有一張跨角色的帳**,住在共用層(`spec-roles.md`「測試跑幾次、跑多大」),一格一個角色,寫明範圍與次數上限。判準是**每一次跑要回答的問題不一樣**:qa 那次問「我的測試編不編得過、紅綠對不對」,編排者那次問「impl 有沒有做到 spec」,整套那次問「有沒有連累別人」。問題相同的兩次,砍掉一次;而「有沒有連累別人」只有在自己那一塊全綠之後問才有意義——這就是整套該跑在迴圈最後、而不是每輪仲裁都跑一次的理由。

配套是**子集指令要先找出來**:沒有「怎麼只跑一個模組」的那一行,每個角色都只會退回去跑整庫,而那不是紀律問題,是他不知道還能怎麼跑。

## 三條追加閘門

每次要往 skill 裡加東西之前,依序過這三關:

1. **先問「有沒有哪一段因此可以刪掉」。** 純追加是退化的徵兆。新增的規則若讓某條舊規則變得多餘,就該一起處理;每次都只加不減,累積是必然的。
2. **跨 skill 的規則放 `_shared/`,只有單一 skill 用得到的放 `SKILL.md`。** 同一條規則兩邊各寫一次是最真實的臃腫來源——兩份都會進 context,而且會各自漂移。
3. **理由只有能擋掉一個可預期的錯誤動作時才留。** 例:「模型是工具參數不是 prompt 內容」擋得掉一個會靜默失敗的誤用,值得留;「checkpoint 不是已驗收」擋得掉把 checkpoint 誤當品質保證,值得留。純粹解釋設計動機給人看的段落,搬來這份文件。

補充一條不對稱性:**可選功能不該佔用跟強制流程一樣的注意力預算。** opt-in、預設 no-op 的內容在多數執行裡會被整段跳過,寫太長是純浪費。要瘦身時從這類內容下第一刀。

## `_shared/` 的分片規則

分片邊界是**「什麼時候需要」,不是「什麼主題」**。分片對照表(每片裝什麼、誰在什麼條件下讀)的唯一權威是 `_shared/conventions.md` 開頭那張表——本檔不抄一份,改分片時**只改那張表**與受影響的 SKILL.md 載入行。

三條邊界判準:

- 新增共用內容時先判斷它屬於哪一片。判斷不出來,通常表示它其實是單一 skill 的規則
- **同觸發、同讀者集的兩片就是一片**——「通常一起讀」寫進表裡的那天,就是該合併的那天(例:frontmatter 規格併入 `doc-lifecycle.md`)。反過來,讀者集真的不同(qa/impl 刻意不讀 `delegation-design.md`、impl 刻意不讀 `testing-policy.md`)的分片,不得為了檔數好看而合併
- **論證單一權威**:每條規則的**論證**(為什麼會出事、失效的機制)只住在一個權威位置——通常是定義該規則的分片;規則出現在其他檔案時寫「規則一行 + `(理由見 X)`」,不複製論證。同一段論證抄在四處,改一次就漂移三份(例:骨架快照的「假綠與真綠同形」住 `orchestration.md`;spec-gaps 併發互蓋住 `delegation.md` 第 4 條)

**拆片最大的風險是漏讀**,唯一的防線是:每個 `SKILL.md` 開頭必須**明列讀哪幾片、以及為什麼要讀**,不能只寫「遵守共用慣例」。加分片或改分片條件時,十三個 `SKILL.md` 的開頭都要同步檢查。

## 什麼該搬進 `templates/`

純模板、樣板、只在特定動作發生時才需要逐欄對照的內容(例:`subsys-build/templates/build-log.md`),搬進該 skill 的 `templates/`,`SKILL.md` 只留一行指路。判準:**這段內容是「每次執行都要記住的規則」,還是「做某個動作時才打開來照抄的東西」?** 後者屬於 `templates/`。

腳本同理,放 `scripts/`(例:`arch-audit/scripts/scan-status.mjs`)。

## 不要做的事

- **不要把單一 skill 的主流程拆成多個檔案。** `_shared/` 拆片是因為它被十三個 skill 共用、需求差異大;單一 skill 的流程拆開只會提高漏讀率,省下的也有限。
- **不要為了行數砍掉能擋錯的理由。** 見閘門第 3 條——判準是「擋不擋得掉一個具體的錯誤動作」,不是長度。

## 事故紀錄

### 2026-08 · qa 的紅綠判準被排程順序靜默停用

`spec-roles.md` 把「確認紅綠符合預期」寫成 qa 的交付判準,而 `subsys-build` 3d 以「檔案集不相交」為由讓 qa 與 impl 不設先後。那個理由只涵蓋**寫入**:兩邊確實不會互蓋檔案,但 qa 判準**讀**的正是 impl 寫的那個狀態。impl 先落地,假綠與真綠在測試輸出裡同形,判準不會報錯、只是失去鑑別力,而仲裁協議只在有紅燈時啟動,接不住沒有紅燈的失效。同一波還暴露第二件事:判準原本寫成「對應未實作標記的介面應**全紅**」,但骨架自身承載的常數與型別宣告從第一天就綠,照字面讀會把合法的測試當成假綠退回。

處置:判準改成逐條對照的三列表(補上「骨架已承載的事實 → 綠」);紅綠的最終確認從 qa 移到編排者,靠**骨架快照**(發委派前的 `HEAD` sha)驗,與 impl 的進度脫鉤;驗不成時必須明寫「未驗證」帶到閘門,不得默認通過。

可推廣的教訓:**把交付判準綁在一個會被併發對手改寫的狀態上,判準就有時效**。這類失效不會報錯,而且只有同時看得到兩邊的角色查得出來——所以判準該由誰確認,取決於誰觀測得到,不是誰產出那份東西。

## 設計決定紀錄

### 2026-09 · `/spike`:結案即刪、單一 sandbox、verdict 不是裁決

spike 存在的理由:`boundary-rules.md`「發問協議」要求問人之前先「已查過」,設計階段規則要求每個不可逆決定附被否決的替代方案,兩者都假設答案讀原始碼讀得出來。**讀了也答不出來、要跑了才知道**的問題(這個函式庫在我們的資料量下撐不撐得住、目標平台編不編得過)原本沒有合法的出口,只能偷偷寫一段試,然後沒有人記錄。spike 把這個動作合法化並留下紀錄;它替決策生產證據,自己不做決策。

四個被想過、最後定下來的決定:

- **程式碼結案即刪,sha 留在文檔。** 第一版是「程式碼保留給 spec-design / spec-impl 參考」。改掉的理由有三:程式碼留著一定會被 import(那段沒有任何 law 保護);留著的話沒有人會把「學到什麼」寫好,反正「看 code 就知道」;repo 會愈長愈胖。而刪掉並不會失去參考能力——每一輪都 commit 並把 sha 記進 `RND-n`,`git show <sha>:spike/…` 撈得回來。代價是參考要多一道 git 指令,換到的是「結論是唯一產出」這條規則有了機制,不只是紀律
- **`spike/` 是單一常駐 sandbox,每個 spike 一個只活在 open 期間的子資料夾。** 每個 spike 各自裝依賴、各自建 venv,第三個開始就會嫌煩然後偷用專案的套件檔;共用環境放根層解決這件事。子資料夾保留是因為候選比較與平行委派要各寫各的,而多輪疊代的模型屋要活到結案,期間可能有別的 spike 要開。這個形狀讓 `lint-spikes.mjs` 的規則變成純機械:open 要有、concluded 不准有、有資料夾沒文檔是沒有紀錄的實驗
- **刪除只走 `spike-close.mjs`。** `git rm` 碰不到 repo 以外與未追蹤的東西,但路徑打錯仍然刪得掉整個 sandbox。所以路徑由腳本從文檔全名算,人只給全名;五道關任一關沒過一個檔都不動,其中「sha 裡的 tree 與 HEAD 相同」那一關擋的是「記了 sha 之後又改過程式碼」——那種情況撈回來的是舊版,而沒有任何錯誤訊息
- **verdict 不是裁決。** spike 回來的是證據;契約怎麼改仍然走 `/spec-redesign`,ADR 仍然走對應的 design skill。編排者不因為 spike 說 feasible 就自己補一條 law 繼續跑。少了這一條,spike 就變成第二條繞過 spec 的開發路徑——而升格(模型屋變正式功能)也因此只有一條路:`feeds` 指向 feature 檔,impl 從 spec 重寫,程式碼不搬

兩個還沒定、要用過真實 spike 再看的:`open` 的 spike 計入 `scan-status` 的 exit code,一個刻意養很久的模型屋會讓 `/arch-audit status` 一直紅,可能需要一個 parked 狀態;`timebox` 對 LLM 寫時間沒有意義,它量不了牆鐘,嘗試次數才量得了。

## 已評估、暫不採用

被想過、算過成本、然後決定不做的設計記在這裡。沒有紀錄的話三個月後只會被重新提一次,而提的人未必踩得到同樣的理由。

### 2026-09 · `ready:` 產物就緒欄位

`status` 一欄扛了建檔到完成的整條路,「spec 交付了沒人動工」與「測試好了實作沒開始」共用同一個 `open`。設計是 frontmatter 加一個累加清單 `ready: [spec, tests, impl]`,三個角色各一格,每格綁在該角色的收尾動作上(委派模式一律 subagent 回報、編排者寫)。用累加清單而非擴充 `status` 值域,是因為 qa 與 impl 平行且互不可見,單一 enum 表達不了「測試好了、實作還沒」,兩者寫同一格也是 race。

原本想的五格砍掉兩格,兩條判準都可以複用:

- **`skeleton` 併進 `spec`** —— enhance 的第三種骨架情況是「不動任何程式碼,骨架就是現狀」,那類工作沒有新骨架檔案,這一格填了是說謊、不填又永遠看起來沒做完。**一個對合法工作無法正確表達的欄位不該存在。**
- **`approved` 刪掉** —— 沒有任何角色的收尾動作是「批准」,而且它會被別人(未結 gap)撤銷,那代表它是衍生值。**設計累加欄位時先問每一格是否都對應某個角色的收尾動作;對不上的那一格不是漏了擁有者,是它不屬於這個維度。**

暫不採用的理由:`code-paths` 同一版才剛加,而沒人回寫的欄位比沒有欄位更糟。等 `code-paths` 在真實專案裡站穩再談。

## 版本號

版本號一律由使用者指定,不自行計算 semver bump。改完內容後若需要變更版本,先問要用哪個版本號再寫入 `plugins/<plugin>/.claude-plugin/plugin.json`。
