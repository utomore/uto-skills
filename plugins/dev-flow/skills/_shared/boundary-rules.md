# 邊界判斷規則

`_shared/conventions.md` 的分片。**設計與實作 skill 動手前先讀這份**(`/system-design`、`/subsys-design`、`/spec-design`、`/spec-impl`、`/bugfix`)。前四節共用;「設計階段」只有設計 skill 用,「實作階段」只有實作 skill 用。測試怎麼寫在 `testing-policy.md`,只有真的要動測試的角色才讀。

## 專案模式:全新建立,還是維護型

`system.md` frontmatter 的 `mode` 欄,兩個值,決定**整類問題該不該問**:

| `mode` | 意思 | 第一優先 |
|---|---|---|
| `greenfield` | **全新建立**:所有東西都是第一版,沒有既有使用者、既有資料、既有的對外承諾 | 專案的未來性 |
| `brownfield` | **維護型**:已經有人在用,有既有資料與既有呼叫端 | 不弄壞已經在用的東西 |

**讀不到 `mode` 欄時**(舊專案,或 `system.md` 還沒建):問開發者一次,答案回寫進 `system.md`,**不要自己假設**。猜錯的代價不是一個決定做錯,是整場訪談都在問錯的東西。

### `greenfield` — 三條禁止(不是「盡量少做」,是禁止)

1. **禁止問任何 migration / 向後相容的問題**:舊格式怎麼轉、舊資料怎麼讀、既有使用者怎麼辦、要不要保留舊版 API——這些問題在全新專案裡**沒有指涉對象**,問了是逼開發者回答一個不存在的處境。這類問題一律不進發問清單,委派模式下也不進批次澄清
2. **禁止在設計裡預留相容層**:版本欄位、為了舊行為開的 feature flag、雙寫、deprecated 別名、`legacy` 模組、「先兩種格式都支援」——一律不寫。第一版就是唯一的版本,格式與契約直接定成你認為對的那一個
3. **決策的第一優先是專案的未來性**:選型、契約、資料結構以「三個月後最好改」為準,不是「現在最好接」。兩個方案的當下成本打平時選未來性好的那個;要在兩者之間取捨時,發問格式「三個月後的代價」那一欄就是判準本身

**唯一的例外是外部系統**:第三方 API、既有檔案格式、標準協定——那不是「舊版的自己」,是邊界另一端的事實,照 `system.md` 的對外 I/O 契約承接。分辨方法只有一句:**那個東西的規格我們改得動嗎?** 改得動 = 內部,直接定成對的;改不動 = 外部契約,照實承接。

**「相容」與「回歸」不是同一件事,不要一起丟掉。** `greenfield` 禁止的是**對外的相容承諾**;`enhance` spec 的回歸 law(`REG-`,見 `spec-roles.md`)保護的是「這次優化不准改掉這份程式碼現有的行為」——那在全新專案裡照樣要寫,它防的是改壞自己,不是承諾誰。

### `brownfield` — 三條必做

1. **migration 路徑、既有資料的相容、既有呼叫端會不會斷,必問**;結論寫進 spec,不能只留在對話裡
2. **破壞性改動要有 migration 步驟與退場計畫**,沒有就代表那個改動還沒設計完
3. **`enhance` 的回歸 law 是這個模式的主防線**:被保護的不只是「行為別改壞」,還有「既有呼叫端照原樣呼叫仍然要能動」

## 知識歸屬

系統裡每一個事實,只能有一個地方知道它。

判準:**「這件事以後要改,我們希望只改一個地方,那個地方是哪裡?」** 答案出來後,這個事實只能住在那裡;其他模組需要它,透過介面問,不准自己抄一份。

## 層級判斷:這個問題歸誰決定

看答案會不會出現在模組邊界上:

- 只活在函式/模組內部,外面看不到 → **實作層級**,你自己決定,不要問
- 會改變模組之間的依賴、對外介面、或未來修改的代價 → **架構層級**,必須問開發者

等價判準:「這個決定做錯了,改回來要不要驚動其他模組?」不用 → 自己決定;要 → 問。

層級**不看技術含量,看影響半徑**:「用 String 還是 Text」在模組內部是實作問題;同一個問題出現在 public API 或 FFI 邊界上,就是架構問題。

## 發問協議

問開發者任何問題前,必須完成:

1. 搜尋 codebase 中相關的既有實作與慣例(專案有程式碼知識圖時可用它加速定位)
2. 讀過 invariants / ADR / 本檔,確認答案不是已經被決定過
   - 讀了也答不出來、**要跑了才知道**的(這個函式庫撐不撐得住這個量、這條協定的延遲落在哪一級),不是發問的題目,是 `/spike` 的題目:先驗證,把 verdict 當「已查過」再問,或者根本不必問了。拿一個沒有證據的問題去問開發者,他答的也只是猜
3. 確認這是架構層級的問題(見上)
4. **確認這個問題在本專案的 `mode` 下存在**(見「專案模式」):`greenfield` 專案裡的 migration / 向後相容 / 既有使用者問題,一律刪掉不問

發問格式:

- **要決定什麼**:一句話,寫決定的**對象**,不是寫缺了什麼
- **現況原文**:把要被決定的那個東西逐字貼上(型別定義、契約條文、介面簽名)。**這一項排在背景之前**:讀的人要先看見東西,才讀得懂圍繞它的爭論
- **背景**:在做什麼、為何卡住(2 句內)
- **已查過**:看了哪些檔案/文件,發現什麼
- **選項**:2-3 個,每個附「當下成本」與「三個月後的代價」。**兩種成本都寫成場景**——誰、在什麼時候、做什麼事會踩到(「想把英文訊息改得更好懂,就會有測試變紅」),不准只用系統詞彙替後果命名(「會變成一個沒有型別的錯誤分類系統」)。命名只有已經懂的人讀得懂,場景是寫給要做決定的人的
- **我的傾向**:選哪個、為什麼、此決定是否可逆。**三句以內**,且不寫元評論(時機成不成熟、這個門日後會不會再打開、對自己判斷的檢討)

禁止問可以自己查到答案的問題;禁止問實作層級的問題。委派模式下一律不得提問,改記「待確認假設」(見 `delegation.md`)。

## 設計階段規則(設計 skill 適用)

每個新增或修改的元件,設計文檔要明確回答四件事:

1. **擁有的知識**:它是哪些事實的唯一真相來源
2. **依賴方向**:依賴誰、誰依賴它;**新增的依賴邊單獨標註**
3. **不可逆決定**:存檔格式、對外 API、FFI 邊界、資料 schema——每條附至少一個被否決的替代方案與否決理由(重大者升級為 ADR)。否決理由是「跑過才知道」的,引用那份 spike 的全名(`SPK-003-storage-engine`)而不是重述結果——三個月後要重驗時,證據在那裡
4. **公開介面可測性**:怎麼只從公開介面測它。設計階段就要回答,不准留到實作時開後門。走 spec 驅動流程時這條有硬性判準:**每條介面至少被一條 Law 或一個 Example 覆蓋**,覆蓋不到就是介面設計缺陷,回頭修介面

**設計階段可以碰程式碼,但只能碰骨架**(`spec-roles.md`):型別定義、函數簽名、模組匯出清單寫完整,函數本體一律未實作標記。寫進任何一行實作邏輯就是越界——那是實作階段的自主權範圍。

**每個「建議」的義務**:凡標「建議」的選項,必須同時寫出它省了什麼(當下成本)、付了什麼(三個月後的代價、被綁死的選項)、有沒有觸碰任何 invariant。只寫得出好處、寫不出代價的建議 = 分析不完整,重做。

**完成定義**:開發者能用兩句話向第三者說明「這個改動動了系統的哪個部分、為什麼」。文件以此為目標書寫,不以完整羅列細節為目標。

## 實作階段規則(實作 skill 適用)

動手前先讀本檔與該任務的設計文檔。

- **範圍紀律**:只實作設計文檔裡有的東西。實作中發現設計沒涵蓋的情況——屬實作層級 → 自己決定,記進「實作備註」與 PR 描述;屬架構層級 → **停下來**按發問協議發問,不准先寫再說
- **禁止「順便」**:順便重構、順便加功能、順便改介面,一律不做。發現值得做的事記成清單回報,由開發者決定要不要開新任務
- **依賴檢查(每次提交前自查)**:本次改動有沒有新增任何 import 方向?有 → 對照設計文檔,文件裡沒有這條邊就是架構變更,停下來發問。核心層有沒有出現表現層/前端/測試的概念?有 → 移除
- **測試**:走 spec 驅動流程時(`/spec-impl`)**你不寫測試也不讀測試**,測試是 qa 的產出——只跑,紅燈照 `spec-roles.md`「仲裁協議」歸因。`/bugfix` 走單角色,自己寫重現測試,遵守 `testing-policy.md`;「不開後門就測不到」一律視為介面設計缺陷回報
- **PR 描述**:用「改了系統的哪個部分、為什麼」描述,不用檔案清單(格式見 `/branch-pr`)
