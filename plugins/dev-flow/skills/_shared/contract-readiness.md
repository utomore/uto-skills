# 契約就緒度檢查(寫任何一行程式碼之前)

`_shared/conventions.md` 的分片。**兩個時機讀這份**:`/subsys-design` 產出 `design.md` 之前(設計者自評)、`/subsys-build` 的委派門檻檢查(編排者他評)。兩處跑的是**同一份清單**,一次寫、兩處用。

## 為什麼存在

spec 被改的原因有兩類,代價差一個數量級:

| | 什麼時候才可能知道 | 判斷 |
|---|---|---|
| **甲類:現實反饋** | 讀到真實程式碼、跑起來、量到數字,才知道假設不成立(某介面不存在、效能不可行、第三方行為與預期不同) | 正常且不可消除,但應該**稀有** |
| **乙類:文檔本身不自洽** | **只看文檔就判定得了**:欄位沒語意、驗收標準沒有觀察點、Example 與 Law 互斥、型別歸屬成環 | 漏到 Level 3 才被撞出來 = **流程漏檢** |

`/arch-audit` 的每一條檢查都是「文檔 vs 程式碼」的對帳,沒有程式碼時整組空轉。本清單問的是另一個問題:**文檔跟自己對不對得上**。

代價的不對稱是本清單存在的全部理由:在這裡抓到,改的是一份 `design.md`;漏到閘門才抓到,要改 spec → qa 重寫測試 → impl 重寫實作,而且那時 impl 已經蓋在上面了。

> **鐵律:凡是不需要程式碼就判定得了的檢查,都要在寫任何一行程式碼之前跑完。**

## 判定紀律

- 每一條都是**機械比對**:不需要判斷力、不需要讀原始碼、不需要問開發者。跑不動代表文檔缺了東西,**那就是發現本身**
- **每一條發現都要指得出位置**(哪個章節、哪一列、哪張卡)。指不出位置的不算發現,也不算過關
- **不過關就回去補文檔,不准「先做再說」**。任何「這個留給 Level 3 補」的念頭,都是把便宜的乙類問題轉成昂貴的甲類代價
- 自評與他評**跑同一份清單不是浪費**:A 段第一次由寫的人跑(同一段上下文,盲點一致),第二次由編排者跑(沒讀過那段訪談,只看得到文字)。整條流程在別處用角色隔離解決這件事(qa 與 impl 互相不可見),這裡用的是同一招

## A 段:子系統內(Level 2)

`/subsys-design` 產出 `design.md` 前逐條跑;`/subsys-build` 委派門檻再跑一次。對照的是**該子系統的 `design.md` 全文**,不需要別的檔案。

**契約卡的內容三條只對「未展開」的 feature 跑**——功能規劃的 `doc` 欄仍是 `-` 的那些。已建檔的 feature 其卡片是**存根**(生命週期見 `doc-lifecycle.md`),權威已轉移到 `F00x`,拿存根去判內容會全部不過,那是誤判不是缺漏。分界線:

| 檢查 | 範圍 |
|---|---|
| A2 的**覆蓋**半段(每列都有卡、標題與 slug 一致、沒有孤兒卡) | **全部** feature——存根保留 `###` 標題,照樣要對得上 |
| A2 的**內容**半段(五個欄位都填了實質內容) | 只有未展開的 |
| A3(介面引用可解析)、A5(驗收標準可觀察) | 只有未展開的 |

要對帳已展開 feature 的卡片內容(例如 `/arch-audit subsys` 的契約卡對帳),讀 `archive/cards-done.md`。

### A1 資訊抽象邊界

全文(含契約卡)不得出現私有函數名、helper 名稱、私有變數命名、內部暫存資料結構;Interface 定義只到「模組間互相調用」的層級。發現越界就刪掉。

某張卡非得寫實作細節才講得清楚 → 那是「Level 2 契約本身沒定義完整」的訊號,回去補契約章節,不要在卡裡越界。

### A2 契約卡覆蓋

「功能規劃」表格每一列都有對應的契約卡,卡片標題與 feature slug **完全一致**,沒有多餘的孤兒卡;卡片五個欄位都填了實質內容(TBD / 待定 / 空白都算沒填)。

### A3 介面引用可解析

每張卡「實作的 Level 2 介面」列的條目,都真的存在於本文件的「對外契約」或「模組間公開介面」章節。對不上 = 契約沒寫完整,回去補。

**這一條只檢查名字對得上,不檢查語意寫得出來**——後者是 A4、A5。名字對得上是必要條件,遠不是充分條件。

### A4 語意完整性

契約章節的**每一個欄位與參數**,說得出:

| 要說得出 | 沒寫會怎樣 |
|---|---|
| **單位**(毫秒?像素?邏輯格?) | qa 寫不出數值斷言,impl 自己挑一個 |
| **值域**(範圍、允許的空值、溢位怎麼辦) | 邊界條件兩邊各補各的 |
| **正負號 / 方向慣例**(往上是正還是負?誰的座標系?) | 兩邊都能跑,結果相反 |
| **空值語意**(缺這個欄位代表「沒有」還是「不變」?) | 靜默分歧,測不出來 |

判準是一句話:**qa 拿著這一條,寫不寫得出一個有具體期望值的斷言?** 寫不出來就是這裡沒寫完。

這是整份清單裡最常抓到東西的一條。原因是結構性的:Level 2 檢查的是「名字」(A3),Level 3 需要的是「語意」,落差每次都由 qa 與 impl 在現場各自補完——**那就叫腦補,而且兩邊各補各的,撞在測試上**。

### A5 驗收標準可觀察

每張卡「驗收標準」提到的**每一個量**,指得出契約章節裡**哪一條介面**觀察得到它。指不出來 = 介面缺觀察點。

這與 `/spec-design` 一致性檢查的「介面設計缺陷」是同一個判準,只是提前到 Level 2 做——留到 Level 3 才發現,唯一的出路就是開測試後門,而後門在 `testing-policy.md` 是一律禁止的。

「功能正常」「運作順暢」這種寫法直接判不過:它到 Level 3 翻不成任何測試。

### A6 依賴無環(**兩張圖都要檢查**)

| 圖 | 節點 | 邊 |
|---|---|---|
| **feature 依賴圖** | 功能規劃每一列 | 「依賴」欄 |
| **模組型別歸屬圖** | 內部模組劃分的每個模組 | 每條介面簽名用到的型別**住在哪個模組** → 那條邊 |

有環就代表切分錯了,重新拆。

**兩張圖是獨立的**:feature 層無環完全可以和模組層有環並存,而後者更難拆。只檢查第一張是這條檢查最常見的漏法。

### A7 知識歸屬

每個模組說得出它擁有哪些事實(是哪些事實的唯一真相來源)。同一個事實有兩個模組宣稱擁有 = 切分錯,重切。

判準見 `boundary-rules.md`「知識歸屬」:**「這件事以後要改,我們希望只改一個地方,那個地方是哪裡?」**

### A8 不可逆決定

對外契約、序列化 / 儲存格式、跨界 DTO 屬不可逆,每條附**至少一個被否決的替代方案與否決理由**(重大者開 ADR)。只寫得出好處、寫不出代價 = 分析不完整,重做(`boundary-rules.md`「每個建議的義務」)。

### A9 可測性

每條對外契約與模組間介面,說得出怎麼**只從公開介面**驗證它。非看內部不可 = 介面有缺口,回去補契約,不准留給 Level 3 開後門。

### A10 職責覆蓋(對上層對帳)

**這一條要開 `system.md`**(A 段唯一的例外,只讀它「子系統劃分」裡本子系統那一小節)。

把該小節的「職責」逐句拆開,每一句在本份 `design.md` 指得到落點:某條對外契約、某個模組群、某個功能規劃項目。指不到的,**只有兩種合法處置**:

| 情況 | 處置 |
|---|---|
| 這一輪不做,但確實屬於本子系統 | 寫成 `planned` 模組群(名字 + 一句話職責),它才進得了盤點的「已規劃、契約未寫」清單 |
| 它其實不屬於本子系統 | 回頭改 `system.md` 的職責敘述(要經開發者同意),不要靜靜放著 |

**不准的處置只有一種:當它不存在。** 沒寫進 `design.md`、也沒寫成 `planned` 的職責,不會出現在任何進度分母裡——子系統會在只做了一部分的時候顯示 100%,而且**這個失真不會產生任何錯誤訊息**,因為每一份文檔各自都是自洽的。

反向也要跑一次:`design.md` 寫了、但 `system.md` 職責沒提到的東西,是**未申報的職責擴張**(可能踩到別人的邊界),同樣列出來跟開發者確認。

## B 段:子系統之間(Level 1↔2)

`/subsys-design` 收尾時跑,**條件**:本子系統有相鄰(依賴或被依賴)的子系統已經建了 `design.md`。一個子系統都還沒有相鄰者時整段跳過,等相鄰者建檔後由那一次 `/subsys-design` 補跑。

### 為什麼 `system.md` 沒有做完這件事

`/system-design` 明訂寫到「**子系統邊界**」的顆粒度即可,所以 Level 1 定完的是:子系統職責與邊界、**對外契約摘要**、通訊拓撲(誰對誰、走什麼、方向)、全域錯誤處理。

真正會咬人的東西不在那裡。A 交給 B 的 DTO 的**實際 schema、欄位語意、錯誤語意**,寫在 A 自己的 `design.md`「對外契約」章節。

所以:**拓撲對齊在 Level 1 做完了,契約對齊沒有**——它分散在各份 `design.md`,而且**每一份都是單方面寫的**。A 先設計時,A 的對外契約是在「沒有 B 這個消費者在場」的情況下定的;B 之後設計時才會發現「這個 DTO 少了我要的欄位」「這個錯誤語意我接不住」。而對外契約依 A8 屬**不可逆決定**——單方視角凍結一個不可逆決定,就是 B 段要擋的事。

### 設計順序

由此推出的順序原則(`/subsys-design` 收尾的下一步建議照這個給):

1. 先把**同一開發階段內、互相有通訊邊的那一組**子系統的 `design.md` 全部寫完(不是全專案所有子系統,是有邊相連的那組)
2. 跑一次 B 段對帳
3. 挑**一個**子系統先 `/subsys-build` 打通到底——選「對外契約被最多人消費」或「最不確定」的那個。第一根樁的價值是暴露契約在實作上站不站得住,而這個反饋你會想在其他子系統動工**之前**拿到
4. 樁打通、契約經過現實檢驗後,其餘子系統可以平行推

兩個極端都不建議:

| | 代價 |
|---|---|
| **全部子系統設計完才動工** | 契約凍結太久沒有現實反饋。等第一次實作發現 Level 1 通訊拓撲有問題,手上已有 N 份 `design.md` 要一起改 |
| **設計一個就做一個** | 第二個子系統設計時幾乎必然要回頭改第一個的對外契約——而第一個已經有程式碼和測試了。這是 A 段要擋的迴圈升級成 Level 2 版本,代價乘以一整個子系統 |

只有一個子系統的專案沒有 B 段的問題,設計完直接 build。

### 素材怎麼拿

B1 / B2 需要**反向依賴索引**(誰依賴我),那半散在別的資料夾,靠路徑推不出來:

```
node "<arch-audit skill 目錄>/scripts/scan-status.mjs" .design --subsys <slug>
```

輸出的「反向依賴」段就是 B1 的候選清單。**腳本只產生索引,不下判斷**——哪些算「正當消費」、哪些算「應該有卻沒有」,逐條對照兩邊的 `design.md` 自己判(紀律見 `design-query.md`)。

### B1 每條對外契約指得出消費者

我宣告的「對外契約」章節,**每一條**說得出哪個子系統(或系統外部呼叫者)會用它。

沒有任何消費者的契約條目 = 契約多寫了,或子系統切錯了。兩種都要處理,不准留著「以後可能會用到」。

### B2 每條消費得到滿足

我消費別人的**每一條**:

1. 在對方 `design.md` 的「對外契約」章節找得到(不是內部模組——摸到內部型別是**邊界外洩**,`/arch-audit subsys` 第 3 條抓的東西)
2. 欄位語意(單位 / 值域 / 正負號 / 錯誤語意)**足夠我寫得出處理邏輯**——這就是 A4 的跨子系統版

第 2 點不過關時,不要在自己這邊補一份定義,那違反 A7 / B4。回去要對方補契約。

**不要自己封裝一份對方的 DTO。** `boundary-rules.md`「知識歸屬」寫死了:其他模組需要它,透過介面問,**不准自己抄一份**。封裝買到的是「隔離變化」,而這裡的變化源是對方的契約——那是你控制得了、而且改了會有對帳擋著的東西,封裝在這裡沒有隔離到任何隔離不了的東西,只多了一層要手動同步的複本(而且複本走樣時**編譯器不會報錯**,因為它是獨立定義的合法型別)。

例外只有一個:**投影**。當本子系統的領域語言與對方不同(對方 12 個欄位我只在乎 3 個,而且我內部用自己的詞彙),可以在邊界做一個**單向、無狀態的投影函數**。判準仍是 A7:

- 對方改了欄位語意我非跟著改不可 → 那份知識**屬於對方**,只能在用的當下投影,不准存副本
- 我的型別是我對那份資料的**取捨與重新命名**,對方改了未必要動 → 那是**我擁有的新事實**,可以住在這裡

一句話:**投影函數可以住在消費端,被投影的事實不行。** 欄位跟對方一一對應、連語意都照抄 = 那不是投影是複製,刪掉。

### B3 方向與拓撲一致且無環

1. 實際的消費關係(B1 + B2 的結果)與 `system.md`「通訊拓撲與原則」章節**相符**,包含方向
2. 子系統層的依賴圖**無環**

契約由誰定義決定方向,兩種都合法但要選定並記進拓撲:

| | 誰定義 | 契約住哪 | 什麼時候選它 |
|---|---|---|---|
| **生產者定義**(預設) | A 定契約,B 照用 | A 的 `design.md` | A 有多個消費者,或 A 是穩定的下層能力 |
| **消費者定義**(依賴反轉) | B 定 port,A 提供 adapter | **B** 的 `design.md` | A 是可替換的資源(儲存、第三方、渲染後端),或 B 是核心領域層、不該依賴基礎設施 |

選消費者定義時,**依賴邊要在 `system.md` 通訊拓撲裡明確畫成反向的**,否則 `/arch-audit system` 第 3 條會判成不一致。

有環時三個解法(與 `/arch-audit system` 第 1 條同一組):introduce interface、事件反轉、搬移職責。子系統層的環比模組層難拆得多,不要想著繞過——回頭看是不是邊界切錯了。

### B4 知識歸屬不重疊(跨子系統)

同一個事實沒有兩個子系統各存一份。

`/system-design` 的自我檢查做過一次,但那是在子系統只有「對外契約摘要」時做的;契約攤開成完整 schema 後才看得出真正的重疊,**目前沒有任何一步重驗**。

多方共用、不屬於任何單一子系統的契約,住 `.design/contracts/G-C00x-<slug>.md`(規格見 `doc-lifecycle.md`),**不准塞進某一個子系統的 `design.md` 再讓別人引用**——那份 `design.md` 從此擁有一個不屬於它的事實,直接違反本條。
