# 委派模式:spec 角色專用(待確認假設與自裁記錄)

`delegation.md` 的分片。**兩種人讀這份**:委派模式下的 spec 角色(`/spec-design`)——這兩份清單只有你會產出;以及編排者(`/spec-build`、`/subsys-build`)——你要拿這些欄位做層級複審、機械對帳與合併。

qa 與 impl 不讀:你們的不確定走 `spec-roles.md`「spec-gaps 協議」,不寫這兩份清單。

## 「待確認假設」段落

委派模式下產出或修改任務文檔時,若有第 2 條的**契約層級**判斷,在文檔的「實作備註」之前插入本段落(沒有就不要放空段落)。每一條都是一則按「發問協議」備妥、延後到閘門才問的問題,欄位缺一不可:

```markdown
## 待確認假設
- ASM-1: <一句話寫「這一條要決定什麼」——寫決定的**對象**,不是寫缺了什麼
         (例:「`ScriptIssue` 的 `siMessage` 欄位,要不要約束它的內容」)>
  - 現況原文:<把要被決定的那個東西**逐字貼上**:型別 / DTO 的定義、design.md 的那一條契約
              原文、介面簽名。原始碼與文檔在你手上,不在編排者也不在開發者手上——這一欄是
              它們唯一的搬運管道>
  - 為何沒答案:<現況原文為什麼支撐不了這個決定,該 feature 的 `## 契約` 為什麼也沒寫(1-2 句)>
  - 契約錨點:<這條假設要動到的契約條目——design.md 的哪一條對外契約 / 模組間公開介面,
              或哪個介面、DTO、型別的名字。寫得出章節就寫章節,寫不出就寫符號名>
  - 層級自答:出現在邊界上?<會/不會>;改錯驚動其他模組?<要/不要>
  - 選項:a) <方案>——當下成本 <...>,三個月後代價 <...>
        b) <方案>——當下成本 <...>,三個月後代價 <...>
  - 傾向:<a 或 b、為什麼。**三句以內**>;可逆性:<可逆 / 有條件可逆(條件是什麼) / 難逆>
  - 暫採:<裁決前 spec 與骨架先照哪個寫> → 影響:<若裁決不同,要改哪些地方>
  - 裁決:未裁
```

**`裁決` 欄由你固定寫「未裁」,之後由編排者在閘門落地時改寫**(格式:`接受 b(WAVE-2 閘門 2026-08-23);已回寫 design.md「對外契約」§2`)。你不會知道結果,但**這一格必須由你先開出來**——沒有欄位,編排者回寫時就沒有地方可寫,而它不會為了一條假設去改模板。

只寫得出傾向、寫不出另一個選項的代價 = 分析不完整,重做(`boundary-rules.md`「每個建議的義務」)。傾向裡的前提不得未經論證就當成立(「日後要 X 加一層 wrapper 即可」——所有的 X 都能用 wrapper 表達嗎?),寫出你依賴的前提。

**兩種成本都要寫成場景**(`boundary-rules.md`「發問格式」):誰、在什麼時候、做什麼事會踩到。用系統詞彙替後果命名(「會變成一個沒有型別的錯誤分類系統」)只有已經懂的人讀得懂;要做決定的人讀的是場景(「想把英文訊息改得更好懂,就會有測試變紅」)。

**`傾向` 欄三句以內,且只准寫「選哪個、為什麼、放棄了什麼」。** 禁止元評論——這個門日後會不會再打開、時機成不成熟、你對自己判斷的檢討,一律不寫。你在跟自己辯論,開發者卻是在一個終端機的選單前面等著按鍵;論證越長,他越只能整段跳過然後選第一個,那正是這套流程要避免的蓋章。

**`現況原文` 欄不可省略。** 你是這條流程裡唯一讀過原始碼的角色:編排者依定義沒讀過(那是委派存在的理由),開發者手上只有你寫的這幾行字。把「不確定的點」壓成 1-2 句之後,那個被決定的東西長什麼樣子就永久遺失了,而閘門上再怎麼展開也生不回來——只能繞著一個沒有人看得見的東西寫抽象論述。貼上五行型別定義的成本對你趨近於零,對閘門則是全部的差別。

**裁決結果的權威在這一格,不在 `build-log.md`。** 這條規則是照 `spec-gaps.md` 的做法補上的:GAP 條目的 `狀態: resolved` 與 `修訂:` 行都寫在**條目自己身上**,所以任何人打開那個檔就知道結案了沒,腳本也數得出未結數。ASM 過去只有「出生」寫在 spec、「結案」寫在 build-log 的彙總表,兩個檔之間沒有任何一條線——結果是三個月後有人打開 `auth/F001-login`,看到三條「待確認假設」,無從知道那些早在第一次閘門就定案了;而 `/arch-audit` feature scope 還明文要求「委派產出的文檔要優先看這一段」,看的人拿到的是一份沒有答案的問題清單。

`build-log.md` 的「待確認假設彙總」**保留**,但角色是**索引與合併關係**(哪幾條 ASM 被併成同一次裁決、沿用了哪一次、回寫到哪裡),不是權威。重複是刻意的:那份是編排過程的審計軌跡,`/arch-audit status` 依定義不掃它。

**`契約錨點` 欄不可省略。** 你和同一波的其他 spec subagent 互相看不到,常常會從各自的角度對**同一個契約條目**各留一條假設;編排者沒讀過你們讀的原始碼,唯一能機械對出「這兩條其實是同一件事」的線索就是這個欄位。它同時也是「前面幾波是不是已經裁過這件事」的比對鍵——寫得夠具體(指到章節或符號名),開發者就不會被同一個問題問第二次;寫成「錯誤處理」這種泛稱,對不上任何東西,等於沒寫。

## 「自裁記錄」清單

實作層級的自裁**不進任務文檔**(那是實作自主權的範圍,寫進 spec 反而污染契約),放在回報裡,由編排者彙整進 `build-log.md` 的「自裁清單」供事後抽查:

```
- SELF-1: <判斷點> → 採取:<判斷>(層級自答:邊界 不會 / 驚動 不要)
        觸及符號:<這個判斷碰到的型別名 / 函數名 / 欄位名,逐一列出;一個都沒碰到就寫「無」>
```

(編號用 `ASM-` / `SELF-` 詞首碼,不用單字母——`A1` 是 `contract-readiness.md` 的檢查條,`S1` 是開發階段;完整註冊表見 `doc-lifecycle.md`)

`觸及符號` 欄不可省略,也不得寫成「內部實作」這種概括詞。它是編排者做**升級篩**的唯一材料:編排者不會重讀你讀過的原始碼,只能拿這些名字去對 spec 的介面表、`design.md` 的契約章節與 DTO 定義——名字沒寫出來,篩子就是空的,你判錯層級也沒有人攔得住。

自裁不是黑箱:抽查發現裁錯層級(其實動到了邊界),代表層級門檻要收緊——這比預設全部上桌便宜得多。
