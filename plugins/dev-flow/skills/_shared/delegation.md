# 委派模式(Delegated Mode)共通契約

`_shared/conventions.md` 的分片。**prompt 開頭標明 `【委派模式】`,或你是 `/subsys-build` 的編排者時才需要讀這份。**

`/subsys-build` 會把 Level 3 的工作**委派給 subagent** 執行。凡 prompt 開頭標明 `【委派模式】` 的執行,一律套用本節規則(適用 `/feature-design`、`/spec-qa`、`/feature-impl`;沒有這個標記時各 skill 照原本的互動流程走)。角色本身的輸入與禁區見 `spec-roles.md`,本片只管「問不了人」衍生的那些規則。

**核心前提:subagent 問不了人。** 所有需要開發者判斷的事都已經在編排者的「批次澄清」階段問完了,所以委派模式下:

1. **禁止呼叫 AskUserQuestion,禁止在對話中提問等待回覆**。訪談/討論類步驟一律跳過,改以「Level 2 契約卡 + 委派決策記錄」為輸入
2. **遇到不確定不得腦補**。分兩種情況,**不可互換**:
   - **你是 spec 角色**(`/feature-design`):契約卡沒寫到的地方,採取當下最合理的作法**繼續推進**,但每個不確定的判斷都要先過**層級自答**(`boundary-rules.md`「層級判斷」的兩問:答案會不會出現在模組邊界上?改錯要不要驚動其他模組?):
     - 兩問皆否 → **實作層級,你自己裁**,不進文檔、不上閘門;把判斷記進回報的「自裁記錄」供事後抽查(格式見下)
     - 任一為是 → **契約層級**,寫進文檔的「待確認假設」段落(格式見下),由編排者在閘門逐條呈報。這一條就是一則延後到閘門才問的問題,「發問協議」要求的材料(選項與各自代價、傾向、可逆性)**由你現在備齊**——編排者沒讀過原始碼,你不寫,閘門上就沒人寫得出來,開發者只能盲目蓋章
   - **你是 qa 或 impl**:spec 沒寫清楚的地方**不准自己判斷**——照 `spec-roles.md`「spec-gaps 協議」寫出該條 gap 的四個欄位,**停下該項**,其餘照做完,並把該項列為阻塞項回報。**委派模式下你不寫 `spec-gaps.md`**(見第 4 條),gap 全文放回報,由編排者寫檔配號。spec 是唯一真相,補 spec 是設計的職責,不是你的
3. **編號與檔名由編排者指定**,不得自行掃描資料夾配號(平行執行會撞號)
4. **不得寫入任何共用檔案**:`design.md`、`system.md`(含回填 `doc` 欄)與 **`spec-gaps.md`** 一律由編排者單線更新。你只寫自己專屬的檔案(spec 文檔、指定的骨架路徑、測試檔、實作檔)。需要動上層契約時,把「該改什麼、為什麼」寫進回報,不自己改;發現 spec-gap 時照第 2 條記進回報,**不得自己開檔或追加條目**——平行的 subagent 各自從 `G1` 開始編號、又同時寫同一個檔案,結果是**條目互相覆蓋、編號互撞**,而且被蓋掉的內容只剩在各自的回報裡才救得回來
5. **機械性查證不可跳過**:相依性查證(打開原始碼讀真實簽名)、一致性檢查、Laws / Examples 覆蓋率對帳、骨架與測試的編譯——這些不需要人,是委派模式下品質的唯一防線,必須完整執行
6. **契約不得偏離**:公開介面/DTO 只能落在 Level 2 契約內。發現非偏離不可時,**停下該項**、記入回報,不擅自改契約也不硬做
7. **如實回報**:測試失敗就貼輸出,不得宣稱通過;做不完的項目明確標為未完成
8. **不輸出定錨區塊,因此不讀 `anchor.md`**:定錨是給人看的收尾格式,你的收尾是下面的「回報格式」。各 skill 收尾步驟寫的「另讀 anchor.md」在委派模式下一律不適用

## 「待確認假設」段落

委派模式下產出或修改任務文檔時,若有第 2 條的**契約層級**判斷,在文檔的「實作備註」之前插入本段落(沒有就不要放空段落)。每一條都是一則按「發問協議」備妥、延後到閘門才問的問題,欄位缺一不可:

```markdown
## 待確認假設
- A1: <不確定的點,與契約卡為什麼沒答案(1-2 句)>
  - 契約錨點:<這條假設要動到的契約條目——design.md 的哪一條對外契約 / 模組間公開介面,
              或哪個介面、DTO、型別的名字。寫得出章節就寫章節,寫不出就寫符號名>
  - 層級自答:出現在邊界上?<會/不會>;改錯驚動其他模組?<要/不要>
  - 選項:a) <方案>——當下成本 <...>,三個月後代價 <...>
        b) <方案>——當下成本 <...>,三個月後代價 <...>
  - 傾向:<a 或 b、為什麼>;可逆性:<可逆 / 有條件可逆(條件是什麼) / 難逆>
  - 暫採:<裁決前 spec 與骨架先照哪個寫> → 影響:<若裁決不同,要改哪些地方>
```

只寫得出傾向、寫不出另一個選項的代價 = 分析不完整,重做(`boundary-rules.md`「每個建議的義務」)。傾向裡的前提不得未經論證就當成立(「日後要 X 加一層 wrapper 即可」——所有的 X 都能用 wrapper 表達嗎?),寫出你依賴的前提。

**`契約錨點` 欄不可省略。** 你和同一波的其他 spec subagent 互相看不到,常常會從各自的角度對**同一個契約條目**各留一條假設;編排者沒讀過你們讀的原始碼,唯一能機械對出「這兩條其實是同一件事」的線索就是這個欄位。它同時也是「前面幾波是不是已經裁過這件事」的比對鍵——寫得夠具體(指到章節或符號名),開發者就不會被同一個問題問第二次;寫成「錯誤處理」這種泛稱,對不上任何東西,等於沒寫。

## 「自裁記錄」清單

實作層級的自裁**不進任務文檔**(那是實作自主權的範圍,寫進 spec 反而污染契約),放在回報裡,由編排者彙整進 `build-log.md` 的「自裁清單」供事後抽查:

```
- S1: <判斷點> → 採取:<判斷>(層級自答:邊界 不會 / 驚動 不要)
      觸及符號:<這個判斷碰到的型別名 / 函數名 / 欄位名,逐一列出;一個都沒碰到就寫「無」>
```

`觸及符號` 欄不可省略,也不得寫成「內部實作」這種概括詞。它是編排者做**升級篩**的唯一材料:編排者不會重讀你讀過的原始碼,只能拿這些名字去對 spec 的介面表、`design.md` 的契約章節與 DTO 定義——名字沒寫出來,篩子就是空的,你判錯層級也沒有人攔得住。

自裁不是黑箱:抽查發現裁錯層級(其實動到了邊界),代表層級門檻要收緊——這比預設全部上桌便宜得多。

## 回報格式(subagent 的最終輸出)

委派模式的最終輸出是**給編排者看的結構化資料**,不是給人看的說明文;固定回報:

- 產出/修改的檔案路徑與文檔 id(spec 角色另附骨架檔案清單與編譯結果)
- 完成的項目與測試結果,依角色填:
  - spec:介面幾條、law 幾條、example 幾條、骨架編譯過沒
  - qa:law / example 各翻了幾條、測試編譯過沒、紅綠分佈是否符合預期
  - impl:實作了幾條介面(n/m)、測試結果(通過/失敗數,失敗的貼摘要與**歸因**,不做仲裁)
- 「待確認假設」清單(A1、A2…,只有 spec 角色會有)
- 「自裁記錄」清單(S1、S2…,只有 spec 角色會有;沒有就寫「無」)
- **新增的 spec-gaps**(只有 qa / impl 會有)與因此停下的項目。**你不寫檔**,全文寫進回報,由編排者單線寫入 `spec-gaps.md` 並統一配號;回報裡的編號用**局部序號**(`本次-1`、`本次-2`),不要寫 `G1`——`G` 開頭的編號是檔案裡的全域序號,由編排者發。每一條照 `spec-roles.md`「spec-gaps 協議」的四個欄位寫齊(模糊點 / 卡住的項目 / 需要 spec 回答什麼 / 來源文檔與角色)
- 建議編排者做的上層動作:要回填的 `doc` 欄、建議修改的 Level 2 契約、建議補的 ADR
- 阻塞項:哪一項做不下去、原因
- **程式碼知識圖**一行:用了哪個工具(knot / graphify / 都沒有走傳統搜尋)、查了什麼、有沒有幫上忙;沒用就寫具體原因(選用規則見 `codegraph.md`「選用規則」),不准用「不適用」帶過
