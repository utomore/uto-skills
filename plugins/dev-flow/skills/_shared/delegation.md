# 委派模式(Delegated Mode)共通契約

`_shared/conventions.md` 的分片。**prompt 開頭標明 `【委派模式】`,或你是 `/subsys-build` 的編排者時才需要讀這份。**

`/subsys-build` 會把 Level 3 的工作**委派給 subagent** 執行。凡 prompt 開頭標明 `【委派模式】` 的執行,一律套用本節規則(適用 `/spec-design`、`/spec-qa`、`/spec-impl`;沒有這個標記時各 skill 照原本的互動流程走)。角色本身的輸入與禁區見 `spec-roles.md`,本片只管「問不了人」衍生的那些規則。

**核心前提:subagent 問不了人。** 所有需要開發者判斷的事都已經在編排者的「批次澄清」階段問完了,所以委派模式下:

1. **禁止呼叫 AskUserQuestion,禁止在對話中提問等待回覆**。訪談/討論類步驟一律跳過,改以「Level 2 契約卡 + 委派決策記錄」為輸入
2. **遇到不確定不得腦補**。分兩種情況,**不可互換**:
   - **你是 spec 角色**(`/spec-design`):契約卡沒寫到的地方,採取當下最合理的作法**繼續推進**,但每個不確定的判斷都要先過**層級自答**(`boundary-rules.md`「層級判斷」的兩問:答案會不會出現在模組邊界上?改錯要不要驚動其他模組?):
     - 兩問皆否 → **實作層級,你自己裁**,不進文檔、不上閘門;把判斷記進回報的「自裁記錄」供事後抽查(格式見 `delegation-design.md`)
     - 任一為是 → **契約層級**,寫進文檔的「待確認假設」段落(格式見 `delegation-design.md`),由編排者在閘門逐條呈報。這一條就是一則延後到閘門才問的問題,「發問協議」要求的材料(選項與各自代價、傾向、可逆性)**由你現在備齊**——編排者沒讀過原始碼,你不寫,閘門上就沒人寫得出來,開發者只能盲目蓋章
   - **你是 qa 或 impl**:spec 沒寫清楚的地方**不准自己判斷**——照 `spec-roles.md`「spec-gaps 協議」寫出該條 gap 的四個欄位,**停下該項**,其餘照做完,並把該項列為阻塞項回報。**委派模式下你不寫 `spec-gaps.md`**(見第 4 條),gap 全文放回報,由編排者寫檔配號。spec 是唯一真相,補 spec 是設計的職責,不是你的
3. **編號與檔名由編排者指定**,不得自行掃描資料夾配號(平行執行會撞號)
4. **不得寫入任何共用檔案**:`design.md`、`system.md`(含回填 `doc` 欄)與 **`spec-gaps.md`** 一律由編排者單線更新。你只寫自己專屬的檔案(spec 文檔、指定的骨架路徑、測試檔、實作檔)。需要動上層契約時,把「該改什麼、為什麼」寫進回報,不自己改;發現 spec-gap 時照第 2 條記進回報,**不得自己開檔或追加條目**——平行的 subagent 各自從 `GAP-1` 開始編號、又同時寫同一個檔案,結果是**條目互相覆蓋、編號互撞**,而且被蓋掉的內容只剩在各自的回報裡才救得回來
5. **機械性查證不可跳過**:相依性查證(打開原始碼讀真實簽名)、一致性檢查、Laws / Examples 覆蓋率對帳、骨架與測試的編譯——這些不需要人,是委派模式下品質的唯一防線,必須完整執行
6. **契約不得偏離**:公開介面/DTO 只能落在 Level 2 契約內。發現非偏離不可時,**停下該項**、記入回報,不擅自改契約也不硬做
7. **如實回報**:測試失敗就貼輸出,不得宣稱通過;做不完的項目明確標為未完成
8. **不輸出定錨區塊,因此不讀 `anchor.md`**:定錨是給人看的收尾格式,你的收尾是下面的「回報格式」。各 skill 收尾步驟寫的「另讀 anchor.md」在委派模式下一律不適用

## 「待確認假設」與「自裁記錄」兩份清單

第 2 條的兩種判斷各有一份清單,**只有 spec 角色會產出**:**契約層級**的寫進文檔的「待確認假設」段落(由編排者在閘門逐條呈報),**實作層級**的寫進回報的「自裁記錄」(不進文檔,由編排者彙整供事後抽查)。

兩者的完整欄位格式與寫法見 `delegation-design.md`——**你是 spec 角色或編排者才需要讀那片**;qa 與 impl 走 `spec-roles.md`「spec-gaps 協議」,不寫這兩份清單。

## 回報格式(subagent 的最終輸出)

委派模式的最終輸出是**給編排者看的結構化資料**,不是給人看的說明文;固定回報:

- 產出/修改的檔案路徑與文檔 id(spec 角色另附骨架檔案清單與編譯結果)
- 完成的項目與測試結果,依角色填:
  - spec:介面幾條、law 幾條、example 幾條、骨架編譯過沒
  - qa:law / example 各翻了幾條、測試編譯過沒、紅綠分佈是否符合預期
  - impl:實作了幾條介面(n/m)、測試結果(通過/失敗數,失敗的貼摘要與**歸因**,不做仲裁)
- 「待確認假設」清單(`ASM-1`、`ASM-2`…,只有 spec 角色會有)
- 「自裁記錄」清單(`SELF-1`、`SELF-2`…,只有 spec 角色會有;沒有就寫「無」)
- **新增的 spec-gaps**(只有 qa / impl 會有)與因此停下的項目。**你不寫檔**,全文寫進回報,由編排者單線寫入 `spec-gaps.md` 並統一配號;回報裡的編號用**局部序號**(`本次-1`、`本次-2`),不要寫 `GAP-1`——`GAP-` 編號是檔案裡的全域序號,由編排者發。每一條照 `spec-roles.md`「spec-gaps 協議」的四個欄位寫齊(模糊點 / 卡住的項目 / 需要 spec 回答什麼 / 來源文檔與角色)
- 建議編排者做的上層動作:要回填的 `doc` 欄、建議修改的 Level 2 契約、建議補的 ADR
- 阻塞項:哪一項做不下去、原因
- **程式碼知識圖**一行:用了哪個工具(knot / graphify / 都沒有走傳統搜尋)、查了什麼、有沒有幫上忙;沒用就寫具體原因(選用規則見 `codegraph.md`「選用規則」),不准用「不適用」帶過
