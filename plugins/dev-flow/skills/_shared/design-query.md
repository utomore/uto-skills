# 設計文檔查詢:能力與指令對應

`_shared/conventions.md` 的分片。**要查「某份設計文檔跟誰有關係」時讀這份**;文檔怎麼編號、怎麼互相引用仍以 `doc-lifecycle.md` 為準。

查的是 `.design/` 的**設計文檔**,不是程式碼。與程式碼知識圖的分工見最後一節。

## 為什麼需要它

`.design/` 的資料夾樹本身就是索引的一半:文檔屬於哪個子系統由**檔案路徑**決定,所以「auth 有哪些文檔」`ls` 就是完整答案,不需要工具。

工具解決的是路徑給不了的另一半:

| 問題 | 為什麼路徑答不出來 |
|---|---|
| **誰依賴我** | 引用寫在**別的資料夾**的文檔的 `depends-on` 裡,反向索引推不出來 |
| **這個 feature 的介面長什麼樣** | 在檔案內文,不在檔名 |
| **它用了哪些共用契約、哪幾條** | 引用可能寫在 frontmatter,也可能只出現在內文 |
| **這個子系統現在乾不乾淨** | 盤點模式的 exit code 是全樹的,答的是「整個專案」不是「這一個」 |
| **還沒做的有哪些** | **資料夾只長在已經做過的地方**。沒建 `design.md` 的子系統、沒寫契約的模組群,在檔案系統上完全不存在;它們只住在 `system.md` 的名冊與開發階段表、以及 `design.md` 的模組群表裡 |
| **這個檔案是哪份文檔做出來的** | 這是**反方向**的問題。`.design/` 的樹只答得出「文檔 → 實作」(打開 F00x 看它的 `code-paths`),答不出「實作 → 文檔」;後者散在每一份 F/E/B 的 frontmatter 裡,要掃過全樹才湊得出來 |

最後一列是這支腳本最重要的一件事。`ls` 能告訴你做了什麼,答不出**還沒做什麼**——而後者才是「這個專案到底完成了幾成」的分母。

## 指令對應

| 什麼時候 | 指令 | 接著一定要做什麼 |
|---|---|---|
| 要展開某個 feature,先看它在整體的哪裡、依賴誰 | `node "<S>/arch-audit/scripts/scan-status.mjs" .design --doc <文檔全名>` | **打開它列出的檔案讀原文**再落筆;輸出的介面段是索引不是授權 |
| 要對某個子系統做決定(委派、對帳、驗收) | `… scan-status.mjs .design --subsys <slug>` | 先看「模組群」段有沒有 `planned` 的:有的話該子系統的進度數字只涵蓋 active 那幾群。「反向依賴」段是 `contract-readiness.md` **B1 的候選清單**,逐條對照兩邊的 `design.md` 自己判 |
| 要知道**產品**做到哪、還差什麼 | `… scan-status.mjs .design`(不帶 flag),看「開發階段」表與「已規劃、未建 design.md 的子系統」/「已規劃、契約未寫的模組群」三段 | 這三段才是產品級分母;子系統狀態表的百分比只涵蓋已展開的部分 |
| 要改一份共用契約,先看誰在用 | `… scan-status.mjs .design --doc G-C00x-<slug>` | 「誰引用這份契約」的每一個子系統都要通知到;契約條目是不可逆決定 |
| 手上有一個程式碼檔案,要知道它是哪份 spec 做的、被哪些 E/B 改過 | `… scan-status.mjs .design --file <path>` | **打開它列出的文檔讀原文**再落筆。查無不代表這段程式碼沒來歷——也可能是那份文檔收尾時漏回寫 `code-paths`,輸出會提示你分辨 |
| 要全專案進度、就緒度、不一致清單 | `… scan-status.mjs .design`(不帶 flag) | 照 `/arch-audit status` 的既有流程 |
| 要分辨某份文檔的 `in-progress` 是「正在做」還是「卡死」 | 同上,或 `--subsys` / `--doc` | 看狀態欄有沒有 `⚠卡<子系統>/GAP-n`:有的話下一步是**修 spec**(`/spec-design` 更新模式),不是繼續做 |

**旗標、參數與 exit code 的數值一律跑 `node "<S>/arch-audit/scripts/scan-status.mjs" --help`**,本片不抄一份——抄過來的那份會在改旗標時被忘記。本片只講腳本自己講不出來的三件事(它不知道是誰在呼叫它):

1. **exit code 的語意兩種模式不同,呼叫端不要混用。** 盤點 / `--subsys` 的 exit code 是**驗收**(有沒有未完成);`--doc` / `--file` 的是**有沒有查到**。拿查詢的 exit code 當驗收判準,會把「查到一份還沒做完的文檔」讀成「通過」
2. **`--subsys` 給一個名冊上有、但還沒建 `design.md` 的 slug 不是錯誤**,是待辦——腳本會印出它的職責。真的不在名冊也沒資料夾才是查無
3. **`--file` 查無有兩種意思**:全樹沒人填過 `code-paths`(反查還沒有資料可用),或填了但沒人認領這條路徑(程式碼不走本流程,或該文檔收尾漏回寫)。輸出會分開講,別把後者當成「這段程式碼沒來歷」

## 誰能用、能用到什麼程度

| 角色 | 界線 |
|---|---|
| `/subsys-design`、`/subsys-build`、`/arch-audit`、`/study` | **全開**。跨子系統對帳、委派門檻、影響面盤點本來就要看全局 |
| `/spec-design` | **全開**。它的相依性查證本來就要讀別份文檔的介面表 |
| `/spec-impl` | **可用,但輸出不得用來繞過禁區**。你的禁區是「不得讀、寫、改任何測試檔」——查詢輸出不含測試路徑,所以查它是安全的;但**不准拿查到的東西當 spec 沒寫到的部分的答案**,那走 `spec-roles.md`「spec-gaps 協議」 |
| `/spec-qa` | **限用**,見下 |

### `/spec-qa` 的限用界線

qa 的禁區針對的是**實作程式碼**,設計文檔不在字面內。但開放全部會稀釋「只從這一份 spec 投影」的紀律,所以界線與 `codegraph.md` 的限用界線同構:

| | 用法 |
|---|---|
| **允許** | 查**本 feature 所屬子系統**的 `design.md` 契約條目、查 `G-C00x` 共用契約的欄位語意(單位 / 值域 / 正負號)——這些是**契約**,是斷言的合法依據 |
| **禁止** | 查**別份 feature spec** 的內容(`--doc <別份文檔的全名>`);任何「因為 auth/F00X-… 是這樣寫的,所以這裡預期輸出應該是 Y」的推論 |

> **鐵律:契約可以查,別人的 spec 不行。** 每一條斷言的唯一依據都是**本份** spec 的 law 或 example 原文,加上它引用的契約條目。本份 spec 沒寫到的行為,照樣記 `spec-gaps` 停下該項——**不准拿查詢結果去把 gap 填掉**。

## 鐵律:索引不是原文

> **索引告訴你去哪份文檔看,不保證那份文檔現在寫的還是這樣。**

`--doc` 的「介面 / 數據」段印的是文檔原文沒錯,但它是**當下這一份**的快照,而且腳本只認固定的章節標題與表格格式——文檔用了別的寫法,它就漏印,而**漏印不會有任何錯誤訊息**。

所以:

- **可以**用它找候選、算影響面、看歸屬與依賴方向
- **禁止**拿它當相依性查證的依據。`/spec-design` 的「必須打開原始碼讀到實際定義」一字不改;要寫進 spec 的每一條介面,同樣要打開那份文檔讀到原文
- 腳本**只產生索引,不下判斷**:它答得出「哪份文檔、什麼狀態、誰依賴誰」,答不出「那份文檔寫的對不對」。對不對是 `contract-readiness.md`(寫碼前)與 `/arch-audit`(寫碼後)的題目

## 與程式碼知識圖的分工

兩者**不重疊、不互為備援**,查的是不同的東西:

| 工具 | 查什麼 | 什麼時候空轉 |
|---|---|---|
| `scan-status.mjs`(本片) | **設計文檔**的關係:誰依賴誰、契約住哪、介面**文檔上**怎麼寫 | 文檔還沒寫 |
| `scan-graph.mjs` / graphify / knot(`codegraph.md`) | **程式碼**的關係:實際的 import、呼叫鏈、跨界引用 | **程式碼還沒寫**——所以設計階段整組用不上 |

**兩邊對不上 = 文檔與現實脫節,那正是 `/arch-audit` 的題目**,不是拿其中一邊去覆蓋另一邊的理由。不要拿程式碼圖回答契約問題(圖不知道什麼是契約),也不要拿文檔索引當程式碼現況的證據(文檔會過期)。
