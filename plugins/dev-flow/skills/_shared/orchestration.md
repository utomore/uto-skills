# 編排者專用:模型分派、委派 prompt、骨架快照與仲裁處置

`spec-roles.md` 的分片。**你是編排者(`/spec-build`、`/subsys-build`,或互動模式下的開發者本人)才讀這份。**

qa 與 impl 不讀:快照不由它們驗(它們看不到骨架被填掉了),仲裁的裁決與處置也不是它們的職責——它們只做歸因,那部分留在 `spec-roles.md`。

## 委派模型分派

每次呼叫 Agent 工具都必須明確帶上 `model`,不得省略讓它繼承主 session:

| 角色 | 委派的 skill | 模型 |
|---|---|---|
| spec | `dev-flow:spec-design`(只有 `/subsys-build` 會委派) | **`opus`** |
| qa | `dev-flow:spec-qa` | **`sonnet`** |
| impl | `dev-flow:spec-impl` | **`sonnet`** |
| 編排者(你) | — | 不指定,跟隨開發者當下的 session 模型 |

理由:只有 spec 那一層在做**契約判斷**——寫錯會沿著 qa 與 impl 兩條投影一起錯,而且錯誤要到仲裁才浮出來,值得用最強的模型;qa 與 impl 拿到的是已經鎖死的 spec 與骨架,做的是翻譯與填空,判斷空間有限。分派固定下來,子代的成本與行為就不隨主 session 漂移,閘門看到品質問題時也能直接歸因到 spec 寫得夠不夠,而不是模型差異。

模型是**呼叫 Agent 工具時的參數,不是 prompt 內容**——寫進 prompt 模板不會報錯,只是靜默沒作用。

## qa 與 impl 的委派 prompt(共通段)

兩個編排者的 qa / impl prompt 都以下面兩段為底;`/subsys-build` 的 impl prompt 另加**寫入白名單**段(見該 skill 3d),`/spec-build` 不用。

```
【委派模式】遵守 <delegation.md 路徑> 的委派模式共通契約:不得提問、
不得寫 design.md/system.md、機械性查證不可跳過。
你是 qa 角色,遵守 <spec-roles.md 路徑>:只讀 spec 的數據/介面/Laws/Examples 與骨架,
禁止閱讀任何實作程式碼;程式碼知識圖只准用來定位測試檔與型別結構,
不得用它推論受測函數的行為。禁止修改骨架、禁止要求測試後門。
**禁止讀寫 spec-gaps.md**:發現 gap 就停下該項,把四個欄位寫進回報,
編號用「本次-1」這種局部序號,不要自己配 G 編號、不要自己建檔。
交付前確認測試「編譯通過 + 紅綠符合預期」,對照表的**預期欄**逐條標明;
不符預期的照實回報,**不得刪測試或放寬斷言去湊綠**——紅綠由編排者在骨架快照上驗。

執行 dev-flow:spec-qa,目標:<文檔全名,如 auth/F002-token-refresh>
```

```

禁止改動骨架的簽名與型別定義。紅燈只做歸因不做仲裁,列為阻塞項回報。

那一格由編排者在跑完整套測試之後回寫,你判斷不了「全綠」。
```

## gap 單線寫檔(收到回報就做)

subagent 的 gap 只在回報裡,由**你**寫進 `spec-gaps.md`:讀檔案現有的最大 `GAP-` 編號(檔案不存在就由你建,frontmatter 規格見 `doc-lifecycle.md`;舊檔用 `G<n>` 的接著它的最大值配,但新條目寫 `GAP-<n>`),依序往下配號,照 `spec-roles.md`「spec-gaps 協議」的格式追加,標題括號填**來源文檔全名與角色**(例:`## GAP-3(auth/F004-session-list / qa)`)。回報裡的局部序號(`本次-1`)只是那一份的順序,**不是檔案裡的編號**——照抄會撞號。追加完對一次帳:寫進去的條目數 = 各份回報裡 gap 的總數。

## 骨架快照(委派模式下由編排者驗,不由 qa 保證)

qa 交付判準(`spec-roles.md`)第一列的「紅」,只在**骨架本體還是未實作標記**的那段時間裡觀測得到。impl 一旦填完本體,假綠(斷言恆真、沒呼叫到受測介面)與真綠(測試沒問題,只是實作已經在了)在測試輸出裡**完全同形**——判準不是被違反,是被**靜默停用**,整波會以「全綠」通過閘門。qa 救不了這件事:它依禁區看不到實作,連骨架被填掉了都無從得知,只會誠實回報一個已經沒有鑑別力的結果;仲裁協議也接不住,它只在**有紅燈**時啟動,假綠不產生紅燈。

所以委派模式下,判準的**最終確認在編排者**:

1. 發出本波任何委派**之前**記下 `HEAD` 的 sha,這就是**骨架快照**——qa 與 impl 投影的同一個起點。**同時就把快照工作樹建好**:`git worktree add --detach <路徑> <快照 sha>`
2. 收到 qa 的測試檔後,把測試檔複製進**快照工作樹**跑一次紅綠(只跑本波 qa 的測試檔,不必跑整套),驗完移除 worktree。**先建好再用,不要等發現骨架被動過才建**:impl 與 qa 平行跑,誰先落地不受你控制,而「工作樹還乾淨就直接跑」這條捷徑會隨排程順序時靈時不靈——靈的時候省不了多少,不靈的時候是靜默失去鑑別力
   - 依賴環境帶不過 worktree、驗不成 → 在回報與 build-log 明寫**「本波 qa 紅綠未驗證」**,帶到閘門,**不得默認為通過**
3. 這樣驗出來的紅綠與 impl 的進度無關,qa 與 impl 才真的可以不設先後

互動模式沒有併發,輪到 qa 時實作還沒開始,當下即快照,跑一次就是基線。

## 仲裁的裁決與處置(有紅燈時)

歸因的四分流(impl 錯 / qa 誤讀 / spec bug / 3 輪上限)是 `spec-roles.md`「仲裁協議」那張表,本片不重複;qa 與 impl 只做歸因,**裁決由你做**,逐條處理、順序不可顛倒(先歸因,不先修)。裁完的處置:

- 判 **impl 錯** → 把該條 spec 原文附給 impl 要求修正(委派模式:新開 `dev-flow:spec-impl`,`model: "sonnet"`,prompt 只給失敗清單與對應的 spec 條文原文),**不准動測試、不得附上測試原始碼**;prompt 照樣帶「只跑子集」那一條——**重派的那一輪最容易退回整庫**,而整套仍然是你這一輪結束後才跑的那一次
- 判 **qa 誤讀** → 附上條文原文要求 qa 改測試(委派模式:新開 `dev-flow:spec-qa`,`model: "sonnet"`,只給條文原文與要改的測試名),**不得附上實作原始碼**;判定只能依 spec 原文,**不得拿實作的行為當依據**(那等於讓實作反過來定義正確性)
- 判 **spec bug** → **不發任何委派**,停下來向開發者回報等 spec 修訂;**禁止讓 qa 與 impl 自行協商**,也禁止編排者自己補一條 law 就繼續跑
- **每一輪重跑的範圍**:先只跑**上一輪紅的那些測試**確認修好了,再跑一次完整套件確認沒有連累別人。**不要在同一輪裡跑兩次整套**;上一輪到這一輪之間沒有任何檔案變動時,照 `conventions.md`「跑東西的紀律」直接沿用上次結果,不重跑
- 同一 feature 修正 **3 輪**仍有紅 → 停止並升級給開發者,附失敗摘要與你判斷的**結構性原因**(介面切錯、law 之間互相矛盾、example 與 law 不一致、依賴的前置 feature 行為與 spec 不符),**禁止繼續嘗試**——三輪都收斂不了,問題幾乎不在這一輪的程式碼,而在 spec 的結構,再跑幾輪只會累積更多錯的程式碼
