# spec 三角色契約(設計 / qa / impl)

`_shared/conventions.md` 的分片。**走 spec 驅動流程時讀這份**(`/feature-design`、`/enhance-design`、`/spec-qa`、`/feature-impl`、`/enhance-impl`、`/spec-build`、`/subsys-build`)。`/bugfix` 不適用(輸入是既有程式碼,沒有可投影的唯一真相)。

## 鐵律

> **spec 是唯一真相,測試與實作都只是 spec 的投影。**

骨架是 spec 的程式碼形式;qa 與 impl 各自從同一份 spec 投影出去,**彼此不可見**。兩邊對不上的時候,錯的預設是 spec,不是任何一邊。

```
     設計 ──> spec 文檔 + 骨架(型別完整、簽名完整、本體未實作)
                          │
              ┌───────────┴───────────┐
        qa 讀 │                       │ impl 讀
        寫測試 │                       │ 填本體
              └───────> 編排者 <───────┘
                    跑測試 → 仲裁
```

## 三個角色的輸入與禁區

| 角色 | 唯一輸入 | 產出 | 絕對禁區 |
|---|---|---|---|
| **設計** | 需求 + Level 2 契約卡 + 既有程式碼(**必用**程式碼知識圖定位,見 `codegraph.md`) | spec 文檔 + **骨架** | 不得寫任何實作邏輯(本體一律未實作標記);不得寫測試 |
| **qa** | spec 的「數據 / 介面 / Laws / Examples」+ 骨架 | 測試檔 | 不得讀任何實作程式碼;程式碼知識圖**只能導航**(型別建構子、測試檔位置、既有測試候選),不得用來推論行為(見 `codegraph.md`「`/spec-qa` 的限用界線」);不得改骨架;不得要求測試後門 |
| **impl** | spec 全文 + 骨架 | 把未實作標記換成本體、必要的私有 helper | 不得讀、寫、改**任何測試檔**;不得改動骨架的簽名與型別定義 |
| **編排者**(`/spec-build` 單份、`/subsys-build` 整個子系統,或開發者本人) | 全部 | 跑測試、仲裁、閘門、回報 | 不寫 spec、不寫測試、不寫實作 |

互動模式下三個角色由同一個人依序扮演,隔離靠紀律(輪到 qa 就不看實作、輪到 impl 就不開測試檔);**真正的隔離只有委派模式做得到**,所以互動模式下若發現自己已經看過另一邊,如實講出來,不要假裝隔離成立。

## 骨架(skeleton)

設計階段**直接在專案原始碼樹**寫出檔案框架:哪些檔案與模組、每個檔案裡的型別定義(完整)與函數簽名(完整),函數本體一律填未實作標記。

| 語言 | 未實作標記 |
|---|---|
| Haskell | `undefined` |
| Rust | `todo!()` |
| TypeScript / JavaScript | `throw new Error("not implemented")` |
| Python | `raise NotImplementedError` |
| Go | `panic("not implemented")` |
| Java / Kotlin / C# | `throw new UnsupportedOperationException()` |

三條硬規則:

1. **骨架必須通過編譯 / 型別檢查**。編不過的骨架不算交付——qa 拿不到能 import 的東西,整條流程就停在那裡
2. **未實作處必須在執行期明確失敗**,不得回傳假值(回傳 `0`、`[]`、`null` 會讓測試假綠,比沒寫還糟)
3. spec「介面」段的每一條,都要指得出骨架的 `檔案:行號`;對不上就是 spec 與骨架漂移,先修再交。行號是**建檔當下**的導航線索,impl 填完本體後必然往下移——一致性檢查與 `/arch-audit` 的「骨架符合度」一律比對**簽名原文**,不比對行號,不要為了行號回頭改 spec

## qa 的交付判準(可機械驗證)

測試交付時必須 **編譯通過 + 紅綠符合預期**。預期**逐條**判定,不是「整批全紅」:

| 這條測試打到的東西 | 骨架的狀態 | 預期 |
|---|---|---|
| feature 的介面、enhance 新增或簽名變動的介面 | 未實作標記 | **紅** |
| 骨架**自身就承載的事實**(常數、enum 成員、型別與繼承宣告、欄位結構) | 骨架原文 | **綠** |
| enhance 的**回歸 law**(行為不變、簽名不動) | 現狀程式碼 | **綠** |

第二列不經過任何未實作標記,從第一天就綠、而且**應該**綠。把它當成「該紅卻綠」退回,等於逼 qa 刪掉合法的測試。

**該紅卻綠的測試一律退回重寫**——那代表斷言恆真、或根本沒呼叫到受測介面。**該綠卻紅的回歸測試**代表 qa 對現況的理解與程式碼不符,但 qa 不准開實作去看,改記 spec-gaps 請設計補明現況行為。

## 骨架快照(委派模式下由編排者驗,不由 qa 保證)

上表第一列的「紅」,只在**骨架本體還是未實作標記**的那段時間裡觀測得到。impl 一旦填完本體,假綠(斷言恆真、沒呼叫到受測介面)與真綠(測試沒問題,只是實作已經在了)在測試輸出裡**完全同形**——判準不是被違反,是被**靜默停用**,整波會以「全綠」通過閘門。qa 救不了這件事:它依禁區看不到實作,連骨架被填掉了都無從得知,只會誠實回報一個已經沒有鑑別力的結果;仲裁協議也接不住,它只在**有紅燈**時啟動,假綠不產生紅燈。

所以委派模式下,判準的**最終確認在編排者**:

1. 發出本波任何委派**之前**記下 `HEAD` 的 sha,這就是**骨架快照**——qa 與 impl 投影的同一個起點
2. qa 照常跑、照實回報紅綠分佈,但**不得因為看到綠就自行刪測試、改斷言或放寬期望值**;不符預期的照實列出來
3. 收到 qa 的測試檔後,由編排者在快照狀態上驗一次紅綠(只跑本波 qa 的測試檔,不必跑整套):
   - `git diff --quiet <快照 sha> -- <骨架檔案>` 乾淨 → 直接在工作樹跑,結果即基線。**這是常態**:impl 序列跑,qa 通常先回來
   - 已被 impl 動過 → `git worktree add` 一個 detached worktree 在快照 sha,把 qa 的測試檔複製進去跑,驗完移除
   - 依賴環境帶不過 worktree、驗不成 → 在回報與 build-log 明寫**「本波 qa 紅綠未驗證」**,帶到閘門,**不得默認為通過**
4. 這樣驗出來的紅綠與 impl 的進度無關,qa 與 impl 才真的可以不設先後

互動模式沒有併發,輪到 qa 時實作還沒開始,當下即快照,跑一次就是基線。

## spec-gaps 協議

qa 或 impl 發現 spec 模糊、矛盾、或沒涵蓋當下這個情況時:**停下該項**,不腦補、不推測、不與另一邊協商,追加到 `.design/subsystems/<slug>/spec-gaps.md`(全域文檔的 gap 寫進 `.design/spec-gaps.md`),其餘不受影響的項目照常做完。

**委派模式下誰寫這個檔:編排者,不是你。** `spec-gaps.md` 是**共用檔案**——同一波的 qa 與 impl 併發執行,各自開檔、各自從 `G1` 編號、各自整檔寫回,結果是條目互相覆蓋、編號互撞(見 `delegation.md` 第 4 條)。所以委派模式下 subagent 只把 gap 的四個欄位寫進回報,編排者收齊後**單線**寫入並統一配號;互動模式(開發者本人扮演角色)沒有併發,照常自己寫。

與「待確認假設」(`delegation.md`)的分工**不可互換**:

| | 誰記 | 記完之後 |
|---|---|---|
| 待確認假設 | **設計者**在委派模式下,契約卡沒寫到的地方 | 自己做判斷,**繼續推進** |
| spec-gaps | **qa / impl**,spec 沒寫清楚的地方 | **停下該項**,等 spec 修訂 |

**gap 幾乎都是 qa 發現的,不是 impl。** impl 面對沒寫清楚的地方,總寫得出某個能跑的實作,察覺不到自己剛剛替 spec 做了決定;qa 要寫出斷言,寫不出來就立刻撞牆。所以兩件事:qa 對「寫不出斷言」要敏感,而 impl **測試全綠也不得把有未結 gap 的項目標 `done`**——兩種相反的實作都會全綠,你只是碰巧選了其中一種。

追加格式(只追加,不改既有條目;修訂後回填狀態):

```markdown
## G1(F002 / qa)
- 模糊點:<spec 哪一段講不清楚>
- 卡住的項目:<哪條 law / example / 簽名做不下去>
- 需要 spec 回答什麼:<一個具體問題,不是「請補完整」>
- 狀態:open
```

標題括號裡的**來源文檔 id 與角色**不可省略:這是同一波多個 subagent 的 gap 混進同一個檔案後,唯一分得出「這條是誰提的、卡住哪個 feature」的線索。編號 `G1`、`G2`… 在**該檔內**遞增,委派模式下由編排者依檔案現況配號,subagent 回報時用局部序號(`本次-1`),不要自己寫 `G` 編號。

## 仲裁協議(有紅燈時,誰都不准先改碼)

編排者(互動模式下是開發者本人)逐條處理失敗的測試,順序不可顛倒:

1. **先歸因,不先修**:這條失敗測試對應 spec 的**哪一條 law 或 example**?先回答這個問題再談任何修改
2. 對應得上,且測試與該條原文一致 → **impl 錯**。把該條 spec 原文附給 impl 要求修正,**不准動測試**
3. 對應得上,但測試與該條原文逐字比對後不符 → **qa 誤讀**。附上條文原文要求 qa 改測試;判定只能依 spec 原文,**不得拿實作的行為當依據**(那等於讓實作反過來定義正確性)
4. 對應不上,或 spec 根本沒涵蓋這個情況 → **spec bug**。停下來向開發者回報,等 spec 修訂;**禁止讓 qa 與 impl 自行協商**,也禁止編排者自己補一條 law 就繼續跑
5. **迴圈上限 3 輪**:同一個 feature 修正三輪仍有紅燈,停止並升級給開發者,附失敗摘要與你判斷的**結構性原因**(介面切錯、law 之間互相矛盾、example 與 law 不一致、依賴的前置 feature 行為與 spec 不符),**禁止繼續嘗試**

第 5 條的用意是切斷「再試一次就好」的無底洞:三輪都收斂不了,問題幾乎不在這一輪的程式碼,而在 spec 的結構,再跑幾輪只會累積更多錯的程式碼。
