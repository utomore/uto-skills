# spec 三角色契約(設計 / qa / impl)

`_shared/conventions.md` 的分片。**走 spec 驅動流程時讀這份**(`/spec-design`、`/spec-qa`、`/spec-impl`、`/spec-build`、`/subsys-build`)。`/bugfix` 不適用(輸入是既有程式碼,沒有可投影的唯一真相)。

## 鐵律

> **spec 是唯一真相,測試與實作都只是 spec 的投影。**

骨架是 spec 的程式碼形式;qa 與 impl 各自從同一份 spec 投影出去,**彼此不可見**。兩邊對不上的時候,錯的預設是 spec,不是任何一邊。

```
     設計 ──> spec 文檔 + 骨架(型別完整、簽名完整、本體未實作)
                          │
              ┌───────────┴───────────┐
        qa 讀 │                       │ impl 讀
        寫測試 │                       │ 填本體
              └───────> 編排者 <───────┘
                    跑測試 → 仲裁
```

## 三個角色的輸入與禁區

| 角色 | 唯一輸入 | 產出 | 絕對禁區 |
|---|---|---|---|
| **設計** | 需求 + 該 feature 檔的 `## 契約` + 既有程式碼(**必用**程式碼知識圖定位,見 `codegraph.md`)+ 相關 spike 的結論(程式碼結案已刪,用 RND 記的 sha `git show` 撈;不可逆決定與 Laws 的證據,**不得複製進骨架**) | spec 文檔 + **骨架** | 不得寫任何實作邏輯(本體一律未實作標記);不得寫測試;**不得執行測試套件**——你要驗的只有「骨架編不編得過」,跑一次編譯 / 型別檢查就夠了。整庫的紅綠是編排者的題目,你跑它既沒有裁決權(仲裁只發生在編排者那一層),也拿不到你缺的任何資訊 |
| **qa** | spec 的「數據 / 介面 / Laws / Examples」+ 骨架 | 測試檔 | 不得讀任何實作程式碼,**`spike/` 底下的也算實作**;程式碼知識圖**只能導航**(型別建構子、測試檔位置、既有測試候選),不得用來推論行為(見 `codegraph.md`「`/spec-qa` 的限用界線」);不得改骨架;不得要求測試後門;**不跑完整套件**——只跑自己寫的那個測試模組(見下方「測試跑幾次、跑多大」) |
| **impl** | spec 全文 + 骨架(+ spec 引用的 spike 程式碼,用文檔記的 sha `git show` 撈,**只當參考實作**) | 把未實作標記換成本體、必要的私有 helper | 不得讀、寫、改**任何測試檔**;不得 import `spike/`、不得整段搬 spike 程式碼而不對照 spec;不得改動骨架的簽名與型別定義;**不跑完整測試套件**——只跑涵蓋本份 spec 的子集(依介面表挑路徑),整套與仲裁都在編排者手上,你跑的那次會被重跑,而你對別份 feature 的紅燈也沒有裁決權 |
| **編排者**(`/spec-build` 單份、`/subsys-build` 整個子系統,或開發者本人) | 全部 | 跑測試、仲裁、閘門、回報 | 不寫 spec、不寫測試、不寫實作 |

互動模式下三個角色由同一個人依序扮演,隔離靠紀律(輪到 qa 就不看實作、輪到 impl 就不開測試檔);**真正的隔離只有委派模式做得到**,所以互動模式下若發現自己已經看過另一邊,如實講出來,不要假裝隔離成立。

## 骨架(skeleton)

設計階段**直接在專案原始碼樹**寫出檔案框架:哪些檔案與模組、每個檔案裡的型別定義(完整)與函數簽名(完整),函數本體一律填未實作標記。

| 語言 | 未實作標記 |
|---|---|
| Haskell | `undefined` |
| Rust | `todo!()` |
| TypeScript / JavaScript | `throw new Error("not implemented")` |
| Python | `raise NotImplementedError` |
| Go | `panic("not implemented")` |
| Java / Kotlin / C# | `throw new UnsupportedOperationException()` |

三條硬規則:

1. **骨架必須通過編譯 / 型別檢查**。編不過的骨架不算交付——qa 拿不到能 import 的東西,整條流程就停在那裡
2. **未實作處必須在執行期明確失敗**,不得回傳假值(回傳 `0`、`[]`、`null` 會讓測試假綠,比沒寫還糟)
3. spec「介面」段的每一條,都要指得出骨架的 `檔案#符號`;對不上就是 spec 與骨架漂移,先修再交。**位置一律寫符號名,不寫行號**——行號在 impl 把未實作標記換成本體的那一刻就往下移,而流程裡沒有人負責回頭修它,於是每份跑完的 spec 都留著一欄過期的座標;符號名不會因為本體變長而改變。一致性檢查與 `/arch-audit` 的「骨架符合度」比對**簽名原文與符號名**(`lint-laws.mjs` 擋掉寫成行號的)

## qa 的交付判準(可機械驗證)

測試交付時必須 **編譯通過 + 紅綠符合預期**。預期**逐條**判定,不是「整批全紅」:

| 這條測試打到的東西 | 骨架的狀態 | 預期 |
|---|---|---|
| 初版的介面、修訂新增或簽名變動的介面 | 未實作標記 | **紅** |
| 骨架**自身就承載的事實**(常數、enum 成員、型別與繼承宣告、欄位結構) | 骨架原文 | **綠** |
| 修訂的 **`REG-` 回歸 law**(行為不變、簽名不動) | 現狀程式碼 | **綠** |

第二列不經過任何未實作標記,從第一天就綠、而且**應該**綠。把它當成「該紅卻綠」退回,等於逼 qa 刪掉合法的測試。

**該紅卻綠的測試一律退回重寫**——那代表斷言恆真、或根本沒呼叫到受測介面。**該綠卻紅的回歸測試**代表 qa 對現況的理解與程式碼不符,但 qa 不准開實作去看,改記 spec-gaps 請設計補明現況行為。

## 測試跑幾次、跑多大(整條迴圈的帳)

一份 spec 從委派到收尾,**完整套件只跑一次**(修訂目標 `rev > 0` 兩次:基準線一次、收尾一次),其餘一律子集。每一格的「範圍」不是建議,是上限:

| 誰 | 什麼時候 | 範圍 | 次數 |
|---|---|---|---|
| 設計 | — | **不跑測試**,只跑編譯 / 型別檢查驗骨架 | 0 |
| qa | 交付前 | **只跑自己寫的那個測試模組**(要驗的是「編不編得過、紅綠符不符合預期」,別人的測試答不了這一題) | 1 |
| impl | 收尾前 | 本份 spec 的測試子集(依介面表挑路徑) | 互動 1;**委派 0**——用 prompt 附的基準線 |
| 編排者 | 收齊回報後 (0) | 骨架快照工作樹上跑**本波 qa 的測試檔** | 1 |
| 編排者 | 判定 (1) | **本波所有 feature 的測試子集**(合起來跑一次,不是一份一份跑) | 1 |
| 編排者 | 仲裁每一輪 | **只跑上一輪紅的那幾條 + 該 feature 的子集** | 每輪 1 |
| 編排者 | 本波全綠之後、checkpoint commit 之前 | **完整套件——整條迴圈就這一次** | 1 |
| 編排者 | 階段閘門 / 收尾 | **不跑**,沿用波末那一次(中間沒有檔案變動) | 0 |
| 編排者 | 修訂目標的基準線(fan out 之前) | 完整套件 | 1(初版目標 0) |

**為什麼整套壓到最後一次**:整套回答的是**「這次改動有沒有連累別人」**,而這個問題只有在「本波自己的測試已經全綠」之後問才有意義。每一輪仲裁都問一次,拿回來的是同一個答案再加上一堆還沒修完的紅燈——那些紅燈本來就在子集裡看得到,整套只是把它們重印一遍,代價是整個專案的測試時間乘上輪數。

**子集的指令要先找出來,整場對話重用**:從 CI 設定 / `Makefile` / `package.json` / 測試框架的說明讀出「怎麼只跑一個模組或一個檔案」(`pytest tests/x.py::TestY`、`cabal test --test-options='-p /Auth/'`、`go test ./auth/...`),寫下來,之後每個角色照抄。**找不到就問開發者一次**——這一題不問,每個角色都只會退回去跑整庫,而那正是這張表要擋的事。委派模式下由編排者把那一行寫進每一份 prompt。

## 骨架快照

qa 交付判準第一列的「紅」只在骨架本體還是未實作標記時觀測得到——impl 填完本體後,假綠與真綠在測試輸出裡同形,判準會被**靜默停用**(完整論證與驗證程序見 `orchestration.md`,編排者才讀)。

- **互動模式**沒有併發:輪到 qa 時實作還沒開始,當下即快照,跑一次就是基線
- **委派模式**下最終確認在**編排者**,不由 qa 保證;qa 照常跑、照實回報紅綠分佈,但**不得因為看到綠就自行刪測試、改斷言或放寬期望值**

## spec-gaps 協議

qa 或 impl 發現 spec 模糊、矛盾、或沒涵蓋當下這個情況時:**停下該項**,不腦補、不推測、不與另一邊協商,追加到 `.design/subsystems/<slug>/spec-gaps.md`(全域文檔的 gap 寫進 `.design/spec-gaps.md`),其餘不受影響的項目照常做完。

**委派模式下誰寫這個檔:編排者,不是你**(併發互蓋的理由見 `delegation.md` 第 4 條)。subagent 只把 gap 的四個欄位寫進回報,編排者收齊後**單線**寫入並統一配號;互動模式(開發者本人扮演角色)沒有併發,照常自己寫。

與「待確認假設」(`delegation.md`)的分工**不可互換**:

| | 誰記 | 記完之後 |
|---|---|---|
| 待確認假設 | **設計者**在委派模式下,`## 契約` 沒寫到的地方 | 自己做判斷,**繼續推進** |
| spec-gaps | **qa / impl**,spec 沒寫清楚的地方 | **停下該項**,等 spec 修訂 |

**gap 幾乎都是 qa 發現的,不是 impl。** impl 面對沒寫清楚的地方,總寫得出某個能跑的實作,察覺不到自己剛剛替 spec 做了決定;qa 要寫出斷言,寫不出來就立刻撞牆。所以兩件事:qa 對「寫不出斷言」要敏感,而 impl **測試全綠也不得把有未結 gap 的項目標 `done`**——兩種相反的實作都會全綠,你只是碰巧選了其中一種。

**進度與阻塞是兩個正交的維度。** `status` 是累加的(open → in-progress → done),gap 是從**任何一格**都會發射的中斷:qa 寫不出斷言時撞到、impl 發現非改簽名不可時撞到。所以 gap 不佔 `status` 的任何一個值——`/arch-audit status` 把未結 gap 標回那份文檔的狀態欄(`in-progress ⚠卡auth/GAP-2`),讓「正在做」與「卡死等 spec」在同一行上分得開。這兩者的下一步完全相反:一個是繼續做,一個是**回頭修 spec**。

追加格式(只追加,不改既有條目;修訂後回填狀態):

```markdown
## GAP-1(auth/F002-token-refresh / qa)
- 模糊點:<spec 哪一段講不清楚>
- 卡住的項目:<哪條 law / example / 簽名做不下去>
- 需要 spec 回答什麼:<一個具體問題,不是「請補完整」>
- 狀態:open
```

**結案格式**(修訂 spec 的人回填):只改 `狀態` 那一行,並追加一行 `修訂`。**前三個欄位保持原文不動**——那是當初卡住的證據,改掉之後就查不出「這條契約為什麼長這樣」。

```markdown
## GAP-1(auth/F002-token-refresh / qa)
- 模糊點:<原文不動>
- 卡住的項目:<原文不動>
- 需要 spec 回答什麼:<原文不動>
- 狀態:resolved
- 修訂:<文檔全名 auth/F002-token-refresh> §<章節>(<日期>);<這一次改了什麼,一句話>
```

`resolved` 是**唯一**的結案值,而且**狀態必須寫成列表項**(`- 狀態:…`,不是 `**狀態**:…`):盤點腳本只認 `/^resolved/i`,其餘寫法(`done`、`closed`、`已解決`)與漏寫一律當 `open`。`done` / `closed` 是**任務文檔**的詞彙(見 `conventions.md`),兩套詞不同義卻長得像,是最常挑錯的那一格。**這兩件事現在由 `scan-status.mjs` 機械檢查**,認不出來的寫法會被點名並讓它 exit 1 —— 以前是靜默的:讀不到就默默當 `open`,所以只有「內容已經結案」的條目才會現形,真的還 open 的條目寫錯了看起來完全正常,格式漂移的實際發生率永遠比看得到的高。`修訂` 行要指得出**文檔全名與日期**,`scan-status.mjs` 拿它跟該文檔的 `updated` 對帳——**結案沒有證據會被列為不一致**。一份檔案的條目全部 resolved 後,把 frontmatter 的 `status` 改成 `done`。

**誰回填**:修訂 spec 的那一次,由執行者在改完文檔的**同一輪**回填——Level 3 的 gap 走 `/spec-design` **修訂模式**,追到 Level 2 契約沒給的走 `/subsys-design` **更新模式**。**委派模式下一律由編排者寫**(理由同上:併發互蓋)。

**沒有人回填的後果是永久的**:gap 只由 qa / impl 產生,而 `open` 條目同時擋著三個地方——該文檔的 `status` 不准變 `done`、`/spec-build` 與 `/subsys-build` 的前置不放行、`scan-status.mjs` 一直 exit 1。spec 明明已經改好卻沒回填,整條流程就停在那裡,而且看起來像是還有真的問題沒解決。

標題括號裡的**來源文檔全名(`<子系統>/<id>-<slug>`)與角色**不可省略:這是同一波多個 subagent 的 gap 混進同一個檔案後,唯一分得出「這條是誰提的、卡住哪個 feature」的線索。寫成裸 `F002` 雖然 `scan-status.mjs` 還認得,但那一行被複製到閘門回報或 issue 裡就指不到任何東西。編號 `GAP-1`、`GAP-2`… 在**該檔內**遞增(不寫 `G1`——`G` 是全域文檔的首碼,見 `doc-lifecycle.md`「編號與縮寫註冊表」),委派模式下由編排者依檔案現況配號,subagent 回報時用局部序號(`本次-1`),不要自己寫 `GAP-` 編號。

## 仲裁協議(有紅燈時,誰都不准先改碼)

**歸因先於修改**:每一條失敗的測試,先回答「它對應 spec 的**哪一條 law 或 example**」,再談任何改動。四種分流:

| 歸因結果 | 誰錯 |
|---|---|
| 對應得上,測試與該條原文一致 | **impl 錯**——改實作,**不准動測試** |
| 對應得上,但測試與原文逐字比對後不符 | **qa 誤讀**——改測試;判定只能依 spec 原文,**不得拿實作的行為當依據** |
| 對應不上,或 spec 根本沒涵蓋 | **spec bug**——停下該項回報,禁止 qa 與 impl 自行協商 |
| 同一個 feature 已修正 3 輪仍有紅 | **停止並升級**,附失敗摘要與結構性原因,禁止繼續嘗試 |

qa 與 impl **只做歸因,不做裁決**:把歸因結論與證據回報,由編排者裁。裁決與處置(誰重派、prompt 給什麼、什麼時候停)見 `orchestration.md`。
