# /feature-design — Level 3 功能設計

先讀取 `../_shared/conventions.md`(核心慣例:樹狀結構、編號、引用格式)與 `../_shared/frontmatter.md`(本 skill 要新建 feature 文檔);prompt 標明 `【委派模式】` 時,另讀 `../_shared/delegation.md`。

## 目標

從需求出發,以討論收斂功能邊界,產出 `.design/subsystems/<subsystem-slug>/features/F00x-<slug>.md`。功能對外的介面**必須落在該子系統 Level 2 定義的契約內**;超出契約的,先回頭走 `/subsys-design` 更新模式調整 Level 2,再回來寫本文檔。

## 委派模式(prompt 標明【委派模式】時)

被 `/subsys-build` 委派執行時,先讀 `../_shared/delegation.md`,並對本 skill 做以下替換(**沒有這個標記時完全不適用,照原流程走**):

| 步驟 | 委派模式下的作法 |
|---|---|
| 前置 4(掃描配號) | **跳過**。id 與檔名由編排者在 prompt 指定,不得自行掃描 |
| 1. 深度討論 | **跳過**。輸入改為 prompt 給的**契約卡**(涵蓋負責模組、Level 2 介面、資料流段落、驗收標準、明確不做)+ 委派決策記錄 + 所屬 `design.md` 的契約章節 |
| 2. 相依性查證 | **完整執行,一字不改**。這是機械性工作,也是委派模式下唯一的品質防線 |
| 3. 產出文檔 | 照原格式;有不確定的判斷時,在「實作備註」前加「待確認假設」段落 |
| 4. 一致性檢查 | **完整執行**。發現不一致就改文件重跑,不得帶著矛盾交出去 |
| 5. 回頭檢查架構文件 | **只檢查、不修改**。要改 `design.md` / `system.md` 的,寫進回報給編排者裁決 |
| 回填 `design.md` 的 `doc` 欄 | **不做**。由編排者單線回填(平行寫同一檔會互蓋) |
| 6. 收尾 | 改為輸出 `delegation.md` 定義的**結構化回報**,不是給人看的摘要 |

契約卡不足以支撐某個決定時:採當下最合理的作法繼續,記進「待確認假設」——**不要停擺、也不要在對話中提問**(沒有人會回答)。契約卡本身與 `design.md` 契約章節矛盾時,以 `design.md` 為準並回報這個矛盾。

## 前置(不可跳過)

1. 讀取 `.design/system.md`(燈塔)。**不存在時**:告知開發者建議先執行 `/system-design`,除非開發者明確要求直接寫設計文檔
2. 確認功能落在哪個子系統,讀取該 `subsystems/<slug>/design.md`;不相關的子系統不讀。`design.md` 的「功能規劃」有此項時,以該列與對應的**「Feature 契約卡」**為討論起點(卡片已定下負責模組、Level 2 介面、資料流段落、驗收標準與明確不做,討論從這裡往下深化,不要重新發明邊界);沒有對應子系統時,先和開發者確認是否要新增子系統(走 `/subsys-design`)或放寬為不拆子系統的小專案做法(此時與開發者確認文檔位置)
3. 讀取與目標相關的 `.design/adr/`(依主題挑選,不必全讀)
4. 掃描該子系統 `features/` 現有檔名,決定新編號(`F` 前綴最大值 +1,三位數)

## 流程

### 1. 深度討論(不可跳過)

與開發者反覆討論直到功能完全明確,**不確定就問,禁止腦補**:

- 功能邊界:做什麼、不做什麼(有契約卡時以卡上的「明確不做」為底線)
- 對應 `design.md`「功能規劃」中哪一項(或確認是清單外的新項目);落在哪個開發階段
- 資料流:輸入、處理、輸出、儲存變化;走 Level 2 資料流管線的哪一段
- **相依性**:依賴哪些已存在或進行中的任務文檔?→ 這決定了能否與其他任務平行開發
- 介面:會用到哪些既有介面?需要新增哪些介面?新增的介面是否在 Level 2 模組介面/對外契約的範圍內?
- 驗收標準:怎樣算完成?

### 2. 相依性查證(討論階段起就生效)

**相依性必須經過嚴格查證,禁止未查證就寫入文件**:

- 討論階段對相依性的任何說法一律視為**待查證假設**,不是結論
- 要把某個既有函式/模組列為相依,必須先**打開原始碼讀到它的實際定義**(完整簽名:參數與回傳型別、所在檔案路徑),並依定義判斷它實際涵蓋的職責範圍
- **名稱不是依據**:函式/模組名稱只是線索,不能憑名稱語意推論它做什麼;查證前不得下任何相依結論
- 讀不到定義(模組尚未實作、屬於進行中的文檔)時,不得假裝查證過:改為相依那份**文檔 id**(引用格式:同子系統 `F001`、跨子系統 `auth/F002`、全域 `G-E001`),並在「相依性」段註明此相依是依文檔的介面約定而非既有程式碼

### 3. 產出 `features/F00x-<slug>.md`

檔名英文 kebab-case、內文繁體中文,固定結構。

**撰寫順序**:先寫「實作方式」→「使用到的既有串接介面」→「新增的介面」→「TodoList」,**最後**才回頭填 frontmatter 的 `depends-on` 與「相依性」段。相依性是介面表的**結果**,不是前提。

```markdown
---
id: F00x
type: feature
title: <slug>
description: <一句話,40 字內:這個功能做什麼>
status: open
created: <today>
updated: <today>
depends-on: []          # 依賴的文檔 id(引用格式見 conventions);空陣列 = 可平行開發(最後填,由介面表反推)
related-adr: []
related-feature: []
---

# F00x: <功能名稱>

## 功能概述
(要解決的問題、驗收標準)

## 相依性
(frontmatter depends-on 的文字說明:依賴哪些文檔、為什麼、
 是否可與其他進行中任務平行處理)

## 對應的 Level 2 契約
(本功能實作 design.md 哪些模組介面 / 對外契約;逐條列出並確認未超出範圍)

## 實作方式
(細到可直接開工:資料流、演算法方向、錯誤處理;
 內部私有函數與變數命名留給實作階段自主決定,不在此鎖死)

## 使用到的既有串接介面
(每一列的簽名必須是從來源檔案讀出的原文;「來源文檔」填定義該介面的文檔 id,無則填 `-`)
| 介面(含完整簽名) | 來源檔案 | 來源文檔 | 用途 |
|---|---|---|---|
| <函式/API/模組與簽名> | <路徑> | <文檔 id 或 -> | <為什麼呼叫它> |

## 新增的介面
(本功能新增的公開函式/API/模組定義,含簽名與說明;必須落在 Level 2 契約內)

## TodoList
(`dep:` 標註該任務依賴的文檔 id 或前置 Todo;無則寫 `-`)
- [ ] T1: <任務>  `dep: -`
- [ ] T2: <任務>  `dep: T1`

## 1-to-1 測試對照表
| Todo | 測試 | 說明 |
|------|------|------|
| T1   | test_xxx | <驗證什麼> |
| T2   | test_yyy | <驗證什麼> |

## 待確認假設
(只在委派模式下、且真的有不確定判斷時才放這一段;互動模式下不確定就直接問開發者,不留假設)
- A1: <不確定的點> → 採取:<判斷> → 影響:<若判斷錯要改什麼>

## 實作備註
(開發過程中與設計的偏差記錄於此,撰寫時留空)
```

TodoList 的每一項都必須在測試對照表有對應的一條測試(1-to-1)。

產出後,回填 `design.md`「功能規劃」對應列的 doc 欄為本檔 id(同步 `design.md` 的 `updated`)。

### 4. 相依性一致性檢查(必做,不可跳過)

文件全文寫完後,**由下往上**回推一次(上半部的結論不會自動跟著下半部的細節修正,必須明確回頭對帳):

1. **反推候選集合**:逐列讀「使用到的既有串接介面」表,收集每列的「來源文檔」,去重,得到 `候選 depends-on`
2. **與 frontmatter 對帳**,把差異全部列出來:
   - `frontmatter 有、候選沒有` → 憑直覺填的多餘相依,**必須刪掉**,除非能指出一條具體的呼叫或資料依賴(共用資料結構、檔案格式、執行順序);能指出就補進介面表或在「相依性」段寫明理由
   - `候選有、frontmatter 沒有` → 漏填,補進 `depends-on`
3. **逐項比對 TodoList 的 `dep:` 標註**:引用的文檔 id 都必須落在最終 `depends-on` 內;`dep:` 指向的前置 Todo 必須存在且排在它前面
4. **回讀「相依性」段**,確認描述的是最終 `depends-on`,不是討論階段的假設;「可否平行開發」的結論跟著重算
5. **簽名複驗**:介面表每一列的簽名都要是從來源檔案讀出的原文;對不上就以程式碼為準,並回頭修正「實作方式」受影響的敘述

有任何不一致就**改文件、再跑一次本步驟**,直到全部對齊。改動涉及相依結論時,把「原本填什麼 → 改成什麼 → 依據哪一列介面」告知開發者。

### 5. 回頭檢查架構文件(必做)

寫完後比對 `.design/system.md` 與所屬 `design.md`:

- 是否引入新技術、新關鍵套件、新資料結構、新階段?
- 新增的介面是否改動了 Level 2 的模組介面或對外契約?架構圖要不要反映?

需要更新時:列出差異給開發者確認,同意後更新對應架構文件(同步 `updated`;子系統內部的變動改 `design.md`,跨子系統邊界的變動改 `system.md`);涉及新的重大技術決策時補一份 ADR。**注意**:純粹的內部實作選擇不需要回寫架構文件(實作自主權)。

### 6. 收尾

摘要:文檔路徑與編號、相依性結論(可否平行、`depends-on` 最終值與依據)、一致性檢查是否修正過相依結論、架構文件是否有更新、「功能規劃」doc 欄是否已回填。最後提醒:可用 `/feature-impl <id>` 依本文檔實作。
