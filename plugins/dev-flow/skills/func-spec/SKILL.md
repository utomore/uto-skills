# /func-spec — 功能/改善規格書

先讀取 `../_shared/conventions.md`,遵守其中所有文檔慣例。

## 模式判斷

- `/func-spec:feature` 或引數含 `feature` / 「新功能」 → **feature 模式**:從需求出發撰寫新功能規格,產出 `docs/spec/func-000x-<slug>.md`
- `/func-spec:enhance` 或引數含 `enhance` / 「優化」 / 「改善」 → **enhance 模式**:從**現有程式碼架構**出發撰寫優化規格,產出 `docs/enhance/enhance-000x-<slug>.md`
- 無法判斷 → 用 AskUserQuestion 問開發者要走哪個模式

兩個模式共用「共通紀律」章節(相依性查證、一致性檢查、架構回頭檢查),差別在出發點與產出位置:feature 是「還不存在的功能」,以討論為主;enhance 是「已存在的程式碼」,**必須先讀程式碼**才有資格討論。

## 前置(兩模式共用)

1. 讀取 `docs/arch/architecture.md`(燈塔文件;舊專案為 `docs/architecture.md`,照常使用但提醒可用 `/arch-design` 遷移)。**不存在時**:告知開發者建議先執行 `/arch-design`,除非開發者明確要求直接寫 spec
2. 目標落在某個子系統(主架構 `subarchs` 有對應文件)時,一併讀取該 `docs/arch/subarch-*`;不相關的子系統不讀。子系統的 subarch 有「功能規劃」節時,確認本次規格對應清單中哪一項(或確認是清單外的新項目)
3. 讀取與目標相關的 `docs/adr/` 文件(依主題挑選,不必全讀)
4. 掃描產出資料夾現有檔名決定新編號(最大值 +1):feature 模式掃 `docs/spec/`,enhance 模式掃 `docs/enhance/`

## Feature 模式 — 新功能規格

### F1. 深度討論(不可跳過)

與開發者反覆討論直到功能完全明確,**不確定就問,禁止腦補**:

- 功能邊界:做什麼、不做什麼
- 與 architecture.md 中哪個垂直切片/階段對應;落在哪個子系統(有對應 subarch 時,介面與元件劃分以該 subarch 為依據;subarch 的「功能規劃」清單有此項時,以清單描述為討論起點)
- 資料流:輸入、處理、輸出、儲存變化
- **相依性**:依賴哪些已存在或進行中的 spec?→ 這決定了任務能否與其他 spec 平行開發
- 介面:會用到哪些既有介面?需要新增哪些介面?
- 驗收標準:怎樣算完成?

### F2. 產出 `docs/spec/func-000x-<slug>.md`

檔名英文 kebab-case、內文繁體中文,固定結構。

**撰寫順序**:先寫「實作方式」→「使用到的既有串接介面」→「新增的介面」→「TodoList」,**最後**才回頭填 frontmatter 的 `depends-on` 與「相依性」段。相依性是介面表的**結果**,不是前提;先填 depends-on 會讓後面的細節即使打架也沒人回修。

```markdown
---
id: func-000x
type: spec
title: <slug>
description: <一句話,40 字內:這個功能做什麼>
status: open
created: <today>
updated: <today>
depends-on: []          # 依賴的 spec id;空陣列 = 可平行開發(最後填,由介面表反推)
related-adr: []
related-spec: []
---

# <功能名稱> 功能規格

## 功能概述
(要解決的問題、驗收標準)

## 相依性
(frontmatter depends-on 的文字說明:依賴哪些 spec、為什麼、
 是否可與其他進行中任務平行處理)

## 實作方式
(細到可直接開工:模組劃分、資料流、演算法、錯誤處理)

## 使用到的既有串接介面
(每一列的簽名必須是從來源檔案讀出的原文;「來源 spec」填定義該介面的 spec id,無則填 `-`)
| 介面(含完整簽名) | 來源檔案 | 來源 spec | 用途 |
|---|---|---|---|
| <函式/API/模組與簽名> | <路徑> | <spec id 或 -> | <為什麼呼叫它> |

## 新增的介面
(本功能會新增的函式/API/模組定義,含簽名與說明)

## TodoList
(`dep:` 標註該任務依賴的 spec id 或前置 Todo;無則寫 `-`)
- [ ] T1: <任務>  `dep: -`
- [ ] T2: <任務>  `dep: T1`

## 1-to-1 測試對照表
| Todo | 測試 | 說明 |
|------|------|------|
| T1   | test_xxx | <驗證什麼> |
| T2   | test_yyy | <驗證什麼> |

## 實作備註
(開發過程中與規格的偏差記錄於此,撰寫時留空)
```

TodoList 的每一項都必須在測試對照表有對應的一條測試(1-to-1)。

產出後,若本功能對應某 subarch「功能規劃」清單中的一項,回填該列的 spec 欄為本檔 id(同步 subarch 的 `updated`)。

## Enhance 模式 — 現有程式碼優化規格

出發點是**目前的程式架構**,不是新需求。核心紀律:**先讀程式碼、再談優化**——沒有打開原始碼讀過現況,就沒有資格提出或評估任何優化方向。

### E1. 檢視現況(不可跳過,先於任何討論結論)

1. 確認優化標的:開發者有指定範圍(模組、子系統、某個 spec 的實作)就以其為準;沒指定就先問。也可能來自 `/code-audit` 報告的建議——有對應報告就先讀該節
2. **打開標的的原始碼實際閱讀**:現有模組劃分、資料流、演算法、錯誤處理;把「現況怎麼運作」讀到能複述的程度
3. 對照 architecture.md 與相關 subarch:現況與架構文件是否一致?不一致本身可能就是要優化的點
4. 找出標的對應的 `docs/spec/` 規格(之後回鏈進 `related-spec`)

### E2. 深度討論(不可跳過)

基於 E1 讀到的現況與開發者討論,**不確定就問,禁止腦補**:

- 現況痛點:哪裡慢、哪裡難維護、哪裡耦合過深?痛點要能指到**具體的檔案與程式碼位置**,不能只是印象
- 優化目標與量化標準:改善後怎麼衡量?(效能數字、複雜度、重複程度、測試覆蓋…)怎樣算完成?
- 改動邊界:動哪些模組、明確不動哪些?對外介面是否維持相容?
- **相依性**:受影響的既有 spec、進行中的任務;可否平行開發
- 風險與回退:改壞了怎麼辦?需要哪些回歸測試保護?

### E3. 產出 `docs/enhance/enhance-000x-<slug>.md`

檔名英文 kebab-case、內文繁體中文,固定結構。**撰寫順序**同 feature 模式:先寫「改善方案」→ 介面兩表 →「TodoList」,最後才回填 `depends-on` 與「相依性」段。

```markdown
---
id: enhance-000x
type: enhance
title: <slug>
description: <一句話,40 字內:要改善什麼>
status: open
created: <today>
updated: <today>
depends-on: []          # 依賴的 spec/enhance id;空陣列 = 可平行開發(最後填,由介面表反推)
related-adr: []
related-spec: []        # 回鏈到被優化的 spec id
---

# <優化名稱> 改善規格

## 現況分析
(E1 讀到的實際運作方式與痛點,附具體檔案路徑與程式碼位置;
 不是從文檔抄來的,是從原始碼讀出來的)

## 改善目標
(要達成什麼、量化的驗收標準、明確不改動的範圍)

## 相依性
(frontmatter depends-on 的文字說明:依賴/影響哪些 spec、為什麼、
 是否可與其他進行中任務平行處理)

## 改善方案
(細到可直接開工:怎麼從現況改到目標——模組調整、資料流變化、
 演算法替換、遷移步驟、錯誤處理;對外介面是否相容)

## 使用到的既有串接介面
(每一列的簽名必須是從來源檔案讀出的原文;「來源 spec」填定義該介面的 spec id,無則填 `-`)
| 介面(含完整簽名) | 來源檔案 | 來源 spec | 用途 |
|---|---|---|---|

## 介面變動
(本次優化新增/修改/移除的函式/API/模組定義,含簽名與說明;
 修改與移除要列出受影響的呼叫端)

## TodoList
(`dep:` 標註該任務依賴的 spec id 或前置 Todo;無則寫 `-`)
- [ ] T1: <任務>  `dep: -`
- [ ] T2: <任務>  `dep: T1`

## 1-to-1 測試對照表
(含保護現有行為的回歸測試)
| Todo | 測試 | 說明 |
|------|------|------|

## 實作備註
(開發過程中與規格的偏差記錄於此,撰寫時留空)
```

TodoList 的每一項都必須在測試對照表有對應的一條測試(1-to-1)。

## 共通紀律(兩模式皆必做)

### 相依性查證(討論階段起就生效)

**相依性必須經過嚴格查證,禁止未查證就寫入文件**:

- 討論階段對相依性的任何說法一律視為**待查證假設**,不是結論
- 要把某個既有函式/模組列為相依,必須先**打開原始碼讀到它的實際定義**(完整簽名:參數與回傳型別、所在檔案路徑),並依定義判斷它實際涵蓋的職責範圍——本目標要做的事,哪些它已經做了、哪些真的落在它之外
- **名稱不是依據**:函式/模組名稱只是線索,不能憑名稱的語意直覺推論它做什麼或不做什麼;名稱給人的印象與實際職責不符是常態,查證前不得下任何相依結論
- 讀不到定義(模組尚未實作、屬於進行中的 spec)時,不得假裝查證過:改為相依那份 **spec id**,並在「相依性」段註明此相依是依 spec 的介面約定而非既有程式碼

### 相依性一致性檢查(必做,不可跳過)

文件全文寫完後,**由下往上**回推一次。這一步的前提是:文件是一路往下寫的,上半部的結論不會自動跟著下半部的細節修正,所以必須明確回頭對帳。

1. **反推候選集合**:逐列讀「使用到的既有串接介面」表,把每一列的「來源 spec」收集起來,去重,得到 `候選 depends-on`
2. **與 frontmatter 對帳**,把差異全部列出來:
   - `frontmatter 有、候選沒有` → 這是憑直覺填的多餘相依。**必須刪掉**,除非能指出一條具體的呼叫或資料依賴(不在介面表裡的那種,例如共用資料結構、檔案格式、執行順序);能指出就把它補進介面表或在「相依性」段寫明理由
   - `候選有、frontmatter 沒有` → 漏填,補進 `depends-on`
3. **逐項比對 TodoList 的 `dep:` 標註**:每個 Todo 引用的 spec id 都必須落在最終 `depends-on` 內;`dep:` 指向的前置 Todo 必須存在且排在它前面
4. **回讀「相依性」段的文字敘述**,確認它描述的是最終的 `depends-on`,而不是討論階段的假設;「可否平行開發」的結論要跟著重算
5. **簽名複驗**:介面表中每一列的簽名都要是從來源檔案讀出來的原文,不是憑記憶或函式名稱寫的。對不上就以程式碼為準,並回頭修正「實作方式/改善方案」中受影響的敘述

有任何一項不一致就**改文件、再跑一次本步驟**,直到全部對齊為止。改動涉及相依結論(可否平行開發)時,把「原本填什麼 → 改成什麼 → 依據哪一列介面」告知開發者。

### 回頭檢查架構文件(必做)

寫完規格後,比對 `docs/arch/architecture.md`(目標落在子系統時,連同該 `subarch-*` 一起比對):

- 是否引入了新技術、新套件、新資料結構、新階段?
- 架構圖是否需要反映新元件或元件調整?
- 子系統的對外介面或內部元件劃分是否被本次規格改動?(enhance 模式特別注意:優化常會動到元件劃分)

需要更新時:列出差異給開發者確認,同意後更新對應架構文件(同步 `updated`;子系統內部的變動改 subarch,跨子系統邊界的變動改主架構);若涉及新的重大技術決策,同時補一份 ADR。

### 收尾

摘要:規格檔案路徑與編號(func 或 enhance)、相依性結論(可否平行、depends-on 最終值與其依據)、一致性檢查是否有修正過相依結論、架構文件(architecture.md / subarch)是否有更新、subarch「功能規劃」是否有回填。最後提醒:可用 `/spec-impl <id>` 依本文檔實作。
