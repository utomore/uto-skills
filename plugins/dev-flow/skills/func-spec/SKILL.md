# /func-spec — 新功能規格書

先讀取 `../_shared/conventions.md`,遵守其中所有文檔慣例。

## 前置

1. 讀取 `docs/arch/architecture.md`(燈塔文件;舊專案為 `docs/architecture.md`,照常使用但提醒可用 `/arch-design` 遷移)。**不存在時**:告知開發者建議先執行 `/arch-design`,除非開發者明確要求直接寫 spec
2. 本功能落在某個子系統(主架構 `subarchs` 有對應文件)時,一併讀取該 `docs/arch/subarch-*`;不相關的子系統不讀
3. 讀取與本功能相關的 `docs/adr/` 文件(依主題挑選,不必全讀)
4. 掃描 `docs/spec/` 現有檔名,決定新編號(最大值 +1)

## 流程

### 1. 深度討論(不可跳過)

與開發者反覆討論直到功能完全明確,**不確定就問,禁止腦補**:

- 功能邊界:做什麼、不做什麼
- 與 architecture.md 中哪個垂直切片/階段對應;落在哪個子系統(有對應 subarch 時,介面與元件劃分以該 subarch 為依據)
- 資料流:輸入、處理、輸出、儲存變化
- **相依性**:依賴哪些已存在或進行中的 spec?→ 這決定了任務能否與其他 spec 平行開發
- 介面:會用到哪些既有介面?需要新增哪些介面?
- 驗收標準:怎樣算完成?

**相依性必須經過嚴格查證,禁止未查證就寫入文件**:

- 討論階段對相依性的任何說法一律視為**待查證假設**,不是結論
- 要把某個既有函式/模組列為相依,必須先**打開原始碼讀到它的實際定義**(完整簽名:參數與回傳型別、所在檔案路徑),並依定義判斷它實際涵蓋的職責範圍——本功能要做的事,哪些它已經做了、哪些真的落在它之外
- **名稱不是依據**:函式/模組名稱只是線索,不能憑名稱的語意直覺推論它做什麼或不做什麼;名稱給人的印象與實際職責不符是常態,查證前不得下任何相依結論
- 讀不到定義(模組尚未實作、屬於進行中的 spec)時,不得假裝查證過:改為相依那份 **spec id**,並在「相依性」段註明此相依是依 spec 的介面約定而非既有程式碼

### 2. 產出 `docs/spec/func-000x-<slug>.md`

檔名英文 kebab-case、內文繁體中文,固定結構。

**撰寫順序**:先寫「實作方式」→「使用到的既有串接介面」→「新增的介面」→「TodoList」,**最後**才回頭填 frontmatter 的 `depends-on` 與「相依性」段。相依性是介面表的**結果**,不是前提;先填 depends-on 會讓後面的細節即使打架也沒人回修。

```markdown
---
id: func-000x
type: spec
title: <slug>
description: <一句話,40 字內:這個功能做什麼>
status: open
created: <today>
updated: <today>
depends-on: []          # 依賴的 spec id;空陣列 = 可平行開發(最後填,由介面表反推)
related-adr: []
related-spec: []
---

# <功能名稱> 功能規格

## 功能概述
(要解決的問題、驗收標準)

## 相依性
(frontmatter depends-on 的文字說明:依賴哪些 spec、為什麼、
 是否可與其他進行中任務平行處理)

## 實作方式
(細到可直接開工:模組劃分、資料流、演算法、錯誤處理)

## 使用到的既有串接介面
(每一列的簽名必須是從來源檔案讀出的原文;「來源 spec」填定義該介面的 spec id,無則填 `-`)
| 介面(含完整簽名) | 來源檔案 | 來源 spec | 用途 |
|---|---|---|---|
| <函式/API/模組與簽名> | <路徑> | <spec id 或 -> | <為什麼呼叫它> |

## 新增的介面
(本功能會新增的函式/API/模組定義,含簽名與說明)

## TodoList
(`dep:` 標註該任務依賴的 spec id 或前置 Todo;無則寫 `-`)
- [ ] T1: <任務>  `dep: -`
- [ ] T2: <任務>  `dep: T1`

## 1-to-1 測試對照表
| Todo | 測試 | 說明 |
|------|------|------|
| T1   | test_xxx | <驗證什麼> |
| T2   | test_yyy | <驗證什麼> |

## 實作備註
(開發過程中與規格的偏差記錄於此,撰寫時留空)
```

TodoList 的每一項都必須在測試對照表有對應的一條測試(1-to-1)。

### 3. 相依性一致性檢查(必做,不可跳過)

spec 全文寫完後,**由下往上**回推一次。這一步的前提是:文件是一路往下寫的,上半部的結論不會自動跟著下半部的細節修正,所以必須明確回頭對帳。

1. **反推候選集合**:逐列讀「使用到的既有串接介面」表,把每一列的「來源 spec」收集起來,去重,得到 `候選 depends-on`
2. **與 frontmatter 對帳**,把差異全部列出來:
   - `frontmatter 有、候選沒有` → 這是憑直覺填的多餘相依。**必須刪掉**,除非能指出一條具體的呼叫或資料依賴(不在介面表裡的那種,例如共用資料結構、檔案格式、執行順序);能指出就把它補進介面表或在「相依性」段寫明理由
   - `候選有、frontmatter 沒有` → 漏填,補進 `depends-on`
3. **逐項比對 TodoList 的 `dep:` 標註**:每個 Todo 引用的 spec id 都必須落在最終 `depends-on` 內;`dep:` 指向的前置 Todo 必須存在且排在它前面
4. **回讀「相依性」段的文字敘述**,確認它描述的是最終的 `depends-on`,而不是討論階段的假設;「可否平行開發」的結論要跟著重算
5. **簽名複驗**:介面表中每一列的簽名都要是從來源檔案讀出來的原文,不是憑記憶或函式名稱寫的。對不上就以程式碼為準,並回頭修正「實作方式」中受影響的敘述

有任何一項不一致就**改文件、再跑一次本步驟**,直到全部對齊為止。改動涉及相依結論(可否平行開發)時,把「原本填什麼 → 改成什麼 → 依據哪一列介面」告知開發者。

### 4. 回頭檢查架構文件(必做)

寫完 spec 後,比對 `docs/arch/architecture.md`(功能落在子系統時,連同該 `subarch-*` 一起比對):

- 是否引入了新技術、新套件、新資料結構、新階段?
- 架構圖是否需要反映新元件?
- 子系統的對外介面或內部元件劃分是否被本功能改動?

需要更新時:列出差異給開發者確認,同意後更新對應架構文件(同步 `updated`;子系統內部的變動改 subarch,跨子系統邊界的變動改主架構);若涉及新的重大技術決策,同時補一份 ADR。

### 5. 收尾

摘要:spec 檔案路徑、編號、相依性結論(可否平行、depends-on 最終值與其依據)、一致性檢查是否有修正過相依結論、架構文件(architecture.md / subarch)是否有更新。
