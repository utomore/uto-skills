## Laws(行為性質)
分兩類,兩類都要寫;**每條都要填滿四格**(量詞 / 定義域 / 前提 / 觀察點)。四格的意義與填法見
`feature-spec.md` 的「四格怎麼填」,兩種模式規則完全相同:填不滿 = 這條 law 翻不成測試,當場修掉;
觀察點引用不到「數據與介面變動」表裡的介面 = 介面設計缺陷,回頭修介面(`lint-laws.mjs` 會擋)。

**回歸 law(改完必須一模一樣的現有行為)**
- REG-1: 優化前後,parse 對同一輸入的結果完全相同
  - 量詞:對所有 xs
  - 定義域:xs ∈ 任意來源內容(含空輸入、單行、超大輸入、格式錯誤)
  - 前提:無(無條件成立)
  - 觀察點:`parse xs` 的回傳值,與優化前記錄的基準線逐一相同
- REG-2: 格式錯誤走錯誤分支,不拋例外
  - 量詞:對所有 xs
  - 定義域:xs ∈ 不合語法的來源內容
  - 前提:無(無條件成立)
  - 觀察點:`parse xs` 回傳 `Left ParseError`,且呼叫過程不拋出任何例外

**新 law(這次優化才成立的性質)**
- LAW-1: 同一個來源只讀一次(快取生效)
  - 量詞:對所有 xs
  - 定義域:xs ∈ 任意來源內容
  - 前提:同一個行程生命週期內,先前已成功呼叫過 `parse xs`
  - 觀察點:第二次 `parse xs` 期間,`readSource` 被呼叫的次數為 0

(`readSource` 本來不在介面上——是為了讓 LAW-1 有觀察點才提上來的。**這是正常的**:
 law 需要什麼觀察手段,介面就要提供什麼,而不是反過來讓 qa 去戳內部。)

(編號用 `REG-` / `LAW-` 詞首碼,不寫 `R1` / `L1`,見 doc-lifecycle.md 註冊表。
 某個介面確實沒有可陳述的性質時,寫 `無law <介面名>:<具體理由>`——不准留空)
