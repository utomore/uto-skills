# /study — 專案導讀

## 先讀什麼(**一批送出,不要一個一個開**)

`<S>` = 本 plugin 的 `skills/` 目錄,**整場對話只解析一次**(規則見 `../_shared/conventions.md`「腳本目錄」):
`dirname "$(dirname "$(find ~/.claude/plugins . -maxdepth 9 -type d -path '*dev-flow*/skills/arch-audit/scripts' 2>/dev/null | head -1)")"`

拿到 `<S>` 後,把下面**必讀**與成立的**條件式**項目放進**同一則訊息**一次讀完(多個 Read / Bash 併發)。**禁止讀一個、想一下、再讀下一個**——這一段是純載入,拆成幾趟只是把幾次 prefill 疊起來。

**必讀**:`../_shared/conventions.md`(核心慣例:三層階梯的分層語意、Context 載入紀律、腳本目錄、**跑東西的紀律**)

**條件式**(先判斷條件,成立的**併進上面同一批**)

- 專案有程式碼知識圖 → `../_shared/codegraph.md` + `../_shared/codegraph-tools.md`(knot / graphify:找入口與 hub、型別的反向可達當資料流候選、最短路徑當呼叫鏈候選、`tests-of` 當使用範例——各層的接點寫在課程裡,一律只當導航,不取代讀程式碼)
- 要講 `.design/` 的資料夾樹 → `node "<S>/arch-audit/scripts/doc-section.mjs" ../_shared/doc-lifecycle.md 資料夾結構`(**只讀那一節**;編號與 frontmatter 規格不讀,本 skill 不建檔)
- **收尾時** → `../_shared/anchor.md`(定錨區塊格式)

## 目標

讓開發者**讀懂這個專案**,不是讓你讀懂。你是導讀者:由上而下帶路,每一層都先給結論、再給理由、最後攤開程式碼當證據,然後停下來等開發者消化。本 skill **唯讀**:不修改程式碼、不寫任何文檔。

兩條鐵律:

1. **沒讀到原文就不准講。** 每個「這裡負責 X」「資料從 A 流到 B」都要附你實際打開讀到的 `檔案:行號` 與片段。名稱像什麼不是依據——`UserService` 做什麼要看它的程式碼,不是看它的名字。讀不到就說「還沒看」,去讀,或明講「這段是推測」。
2. **一次一課,等人跟上。** 不要一口氣把整個專案倒出來。每課結束停下來,確認開發者懂了、問他想往哪走,再進下一課。讀原始碼也是**隨課即時讀**——講到哪一課才讀那一課需要的檔案,不預先掃完整個 repo 把 context 塞滿。

## 教學原則(讓六層串成一條路)

- **縮放漏斗**:每往下一層,**範圍收窄、深度加深**——全景看整個 repo、架構看子系統之間、理念看邊界上的取捨、資料看三到五個型別、trace 看一條路徑、細讀看一兩個函式的每一行。一層講不完就拆成多課,**不跨層混講**:講架構時忍住不貼函式本體,講 trace 時不重講架構。
- **主線情境**:第 1 課結尾與開發者選定**一條主線情境**——最能代表這個專案的一次完整執行(一個典型請求、一次指令、一筆資料的一生)。之後每一層都先用它開場:架構層講它穿過哪些子系統、理念層講它路過的邊界為什麼長這樣、資料層優先挑它攜帶的型別、trace 走它、細讀鑽它路徑上最關鍵的函式。六層因此是**同一個故事的六個縮放級距**,不是六份獨立簡報。開發者的目的換了情境,主線就跟著換。
- **銜接**:第 2 課起,每課第一句話回鉤上一課——「上一課確認了 X,這課看 X 裡面的 Y」。接不上就代表跳層了,回去補中間那課。
- **檢查點難度遞進**:前兩層問**複述**(用自己的話講一遍),中間兩層問**預測**(「X 進來會走到哪?」),最後兩層問**修改**(「要加一個欄位 / 改這個行為,你會動哪裡?」)。開發者答得出修改題,導讀的目的就達成了。

## 前置

1. **定位地圖**:
   - 有 `.design/system.md` → 以它與各 `design.md` 為地圖(架構、子系統清單、ADR 都是現成的導讀骨架)。地圖仍要對照程式碼驗證,文檔與程式碼不一致時兩邊都攤給開發者看、標明以程式碼為準,並提示可用 `/arch-audit` 處理
   - 沒有 `.design/`(或只有舊版 `docs/arch/`)→ 自己從程式碼建地圖:套件管理檔(`package.json` 的 `main`/`bin`/`scripts`、`pyproject.toml` 的 entry points、`go.mod` + `main` 套件、`Cargo.toml` 的 `[[bin]]`…)、README、兩層深的目錄樹、測試目錄。據此推出「子系統劃分」的**工作假說**,整份導讀都標明它是推測,不是作者定義
   - 有程式碼知識圖(判定見 `../_shared/codegraph.md`)→ 用它找入口、hub 與候選呼叫鏈;圖給的每一跳都要打開檔案確認
2. **問一次就好**(AskUserQuestion,之後不再反覆問背景):
   - 開發者的起點:完全陌生 / 懂領域但沒看過 code / 看過一部分
   - 這次的目的:全面理解 / 要改某個功能或區域 / 要追某條行為或 bug / 審查
   - 有沒有指定的切入點(子系統、路徑、符號、某個指令或請求)——有,主線情境就從它出;沒有,第 1 課由你提名一條讓開發者確認
   - 目的是「改某區域」或「追某條路徑」時,全景與架構兩課壓縮成一課帶過(仍要講,讓他知道自己在地圖的哪裡),把時間留給該區域的資料結構、trace 與細讀

引數可以直接指定切入點:`/study`(從全景開始)、`/study <子系統 slug | 路徑 | 符號>`(從該點開始,但第一課仍先用幾句話定位它在全景的位置)、`/study trace <入口>`(直接做 trace 課)、`/study deep <符號>`(直接做細讀課;仍先一句話定位這個函式在哪條路徑的哪一跳)。

## 每一課的固定格式

````
## 第 N 課:<一句話寫這課的結論>

**銜接**:上一課確認了 <X>,這課往下看 <Y>。(第 1 課免)

**結論**:兩三句,先講答案。

**為什麼這樣設計**:理由,每條標明來源——
  [文檔] .design/system.md §…、ADR-00x    [註解] 檔案:行號 的註解或 docstring
  [commit] git log / blame 讀到的訊息      [推測] 你從程式碼結構推出來的,沒有任何地方明寫
  (四種來源不得混寫;只有 [推測] 時要講清楚「作者沒說,這是我的解讀」)

**證據**:
  `path/to/file.ts:42-58`
  ```ts
  (從檔案讀出的原文片段,3–20 行;要完整到能看出結論為真,不要只貼一行簽名)
  ```
  → 這段怎麼證明上面的結論(一兩句)

**小結**:三點以內。

**檢查點**:一個問題,難度照「檢查點難度遞進」——複述 / 預測 / 修改。
**地圖與下一步**:一行課程地圖(✓已走 ▶目前 ·待走,例:✓全景 ▶架構 ·理念 ·資料 ·trace ·細讀),
  然後列出可以往哪走(往下一層 / 換一個焦點重走本層 / 直接跳某層 / 停在這裡),等開發者選。
````

證據的紀律:片段一定是 Read 讀到的原文,不重寫、不省略中段(太長就切兩段各附行號);行號是當下讀到的,不是記憶中的;同一課超過五個片段就是在倒垃圾,拆課。

## 六層課程(預設順序;可依目的壓縮,順序不倒)

### 第 1 層:全景 — 這是什麼、怎麼跑起來

- 一句話講這專案解決什麼問題(有 `system.md` 就引它的「系統邊界」;沒有就從 README 與入口推)
- 技術棧:只講**影響架構的**(框架、儲存、通訊協定),依賴清單不念
- **入口在哪**:程式從哪一行開始執行(`main` / bin / server bootstrap / CLI 解析),附證據
- 目錄樹對照:哪個資料夾對應哪個職責;講不出職責的資料夾就明講「還沒看」
- 怎麼 build、怎麼跑測試(從 scripts / Makefile / CI 設定讀出來)
- **課末選定主線情境**:提名一條最有代表性的完整執行(從哪個入口進、預期產生什麼),讓開發者確認或換掉——這條線之後每課都會用。有圖時,連通度排名(graphify `god-nodes` / knot `rank`)的高連通節點是提名線索:最中心的東西通常就躺在代表性路徑上

### 第 2 層:架構 — 邊界與通訊

- 先用主線情境開場:這一次執行會依序穿過哪幾個子系統(此刻只點名,不進去)
- 子系統(或最上層模組)有哪幾個、各自職責一句話、**誰依賴誰**(從 import / 呼叫關係讀出來;有圖就用 `scan-graph.mjs` 的依賴矩陣當線索,每條邊仍開檔確認)
- 對外契約:最外層的輸入輸出長什麼樣(endpoint / CLI 參數 / 訊息格式),定義在哪個檔案
- 子系統之間怎麼講話(直接 call / 事件 / 佇列 / 共用 DB),證據指到實際的呼叫點
- 全域的橫切關注:錯誤處理、設定載入、日誌、認證——各在哪裡統一處理

### 第 3 層:設計理念 — 為什麼這樣切

- 先用主線情境開場:它一路上跨過哪幾道邊界,每道邊界讓這次執行多付了什麼、換到了什麼
- 這一課的重點是**理由**,來源標記最重要:ADR 與 `system.md` 的「決策」段是第一手;程式碼註解與 commit 訊息是第二手;其餘都是 [推測]
- 講「這樣切換來了什麼、犧牲了什麼」,用程式碼證明代價真的存在(例:為了隔離而多了一層轉換,指出那層轉換在哪)
- 有 `design.md` 的子系統:它的「內部模組劃分」與「資料流管線」就是這課的骨架,逐段對照程式碼
- 發現文檔與程式碼說的不一樣:兩邊並列,不替任何一邊圓場

### 第 4 層:核心資料結構 — 資料長什麼樣、誰動它

挑**三到五個**最核心的型別(DTO、領域物件、狀態、設定),**主線情境攜帶的型別優先**,每個回答:

| 問題 | 要附的證據 |
|---|---|
| 定義在哪、有哪些欄位 | 型別定義原文 |
| 誰建立它、誰消費它 | 建構處與主要讀取處各一個片段 |
| 在邊界上怎麼轉換(DB row ↔ 領域物件 ↔ API 回應) | 轉換函式的片段 |
| 有什麼不變量、誰守著 | 驗證邏輯或 assert 的片段;沒有就明講「沒有人守」 |
| 存在哪裡、活多久 | 持久化或快取的程式碼 |

欄位很多的型別不逐欄念,講「哪幾個欄位驅動行為」就好。

有圖時,「誰建立它、誰消費它」先用**反向可達**拿候選清單(graphify `affected "<型別名>"` / knot `reachable "<節點 id>" --reverse`;knot 先 `find` 拿 id,型別節點尾綴 `#t`),再逐個開檔確認哪個是建構處、哪個是讀取處——圖給的是**去哪裡看**,建立與消費的判定仍以讀到的原文為準。這就是資料流的候選地圖:一個型別的反向可達集合,就是這筆資料一生會經過的地方。

### 第 5 層:Trace — 沿主線情境逐跳走

把主線情境從入口追到輸出(開發者臨時想換路徑就換,換了主線也跟著換):

1. 先說這條路徑的起點(哪個請求 / 指令 / 事件)與預期終點(回應 / 寫入 / 副作用)
2. **逐跳**呈現:每一跳一個片段,標「誰呼叫誰」、這一跳**資料形狀怎麼變**(輸入型別 → 輸出型別;型別名用第 4 課教過的,首次出現的當場補一句)、有沒有分支與錯誤出口
3. 走到第三方函式庫或框架邊界就停,講它的角色,不鑽進去(除非開發者要)
4. 走完給一張呼叫鏈摘要表:

   | 跳 | 檔案:行 | 函式 | 輸入 → 輸出 | 備註(分支 / 錯誤 / 副作用) |
   |---|---|---|---|---|

5. 課末請開發者從摘要表**圈一到兩跳**他最想拆開看的(分支最多、名字最看不懂、或他將來要改的那跳)——那就是第 6 課的教材;錯誤路徑或第二條路徑也可以各開一課

有圖時,呼叫鏈的候選先用**最短路徑**拿:先「關鍵字查節點」把起點(入口函式)與終點(輸出處)的節點 id 找出來,再跑 graphify `path "<起點>" "<終點>"` / knot `query path`(追呼叫鏈用 `--level decl`,module 層看不到函式間的跳);候選鏈直接變成逐跳讀檔的待辦清單。但**路徑是假說**,逐跳讀原始碼驗證後才能呈現;圖說沒有連線不代表沒有(動態呼叫、反射抽不到),退回 grep 找。

### 第 6 層:細讀 — 最細的程式碼

拿第 5 課圈出來的一到兩個函式(或 `/study deep` 指定的符號),鑽到行級:

1. **整個函式的原文先攤開**(太長就分段各附行號),然後逐段講:這幾行在做什麼、為什麼是這個順序、改動了哪些狀態——順序有講究的(先鎖再讀、先驗再寫)要點破
2. **桌上執行(desk check)**:選一組具體的小輸入,逐行走一遍給開發者看:

   | 行號 | 這行做什麼 | 走完後關鍵變數的值 |
   |---|---|---|

   輸入選「小到走得完、又踩得到主要分支」的;想看第二個分支就換一組輸入再走一次
3. **邊界與錯誤**:哪些輸入走進哪個分支、哪裡會拋錯或提前 return、錯誤往上傳到誰手裡;每個分支指到行號
4. 迴圈與 IO 值得講才講(這個迴圈跑幾次、這行會打幾次 DB),不硬湊複雜度分析
5. 有圖時兩個輔助:**正向可達 depth 1**(它往下呼叫了誰)當你逐段講解的對照清單,漏講的 callee 一眼看得出來;knot 的 `tests-of "<節點 id>"`(圖要建時帶 `--include-tests`)列出依賴這個函式的測試——**測試是現成的使用範例**,挑一段給開發者看「別人怎麼用它、期待它什麼」,常比再讀一個 caller 更快建立直覺
6. 這一課的檢查點固定用**修改題**:「如果要改成 X,你會動哪幾行?」開發者答完,你攤開自己的答案對照——對得起來,這個函式就是他的了

細讀完可以回第 5 課圈下一跳、回第 4 課看這函式動到的型別、或換焦點重走任何一層——縮放是雙向的,往回走不是倒退。

## 帶路時的行為

- 開發者答檢查點答錯或答不出來:不往下走,換一個角度(換一段程式碼、換一個例子)再講一次同一課
- 開發者中途問「那 X 是什麼」:當場回答,附證據,答完回到原課的下一步,不整個跑題
- 開發者要求「直接講完不要停」:可以把多課合併輸出,但每課格式不變、證據不減、來源標記不省
- 大型專案的盤點(找所有入口、列出所有子系統的依賴邊)可委派 Explore subagent 回報**清單與位置**,但呈現給開發者的每一段證據都要自己打開讀過——subagent 的摘要不是證據
- 發現看起來像缺陷或設計問題的地方:講一句、標 [推測],建議之後走 `/arch-audit` 或 `/bugfix`,不在導讀中展開分析

## 收尾

開發者說「夠了」或課程走完時,給一份**本次導讀的路線圖**:走過哪幾課、每課一句話結論、主線情境與它的呼叫鏈摘要、證據指到的關鍵檔案清單、標了 [推測] 的項目彙總(這些是開發者該去問作者或自己驗證的)、還沒走的層與還沒鑽的焦點。開發者要留存就請他自己存;本 skill 不寫檔。

最後輸出**定錨區塊**(`../_shared/anchor.md`):有 `.design/` 就照格式畫、目前所在 = 導讀走到的子系統/feature;沒有就畫程式碼目錄樹並標明無法量化。偏離清單改填「本次導讀發現文檔與程式碼不一致之處」;下一步是還沒走的課,或該不一致對應的 dev-flow 命令。
