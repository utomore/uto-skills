# /subarch-design — 子系統架構設計

先讀取本檔同層的 `../_shared/conventions.md`,遵守其中所有文檔慣例(資料夾結構、命名、frontmatter)。

## 目標

基於整體架構,為**單一子系統**產出 `docs/arch/subarch-000x-<slug>.md`:承接主架構定下的邊界與職責,把子系統內部的元件、資料流、演算法與介面設計到可以撰寫 func-spec 的程度。**在範圍與設計明確之前,禁止產出任何文件。**

## 前置(不可跳過)

1. 讀取 `docs/arch/architecture.md`(舊專案為 `docs/architecture.md`)。**不存在時**:停止,告知開發者必須先執行 `/arch-design` 建立整體架構 — 沒有主架構就沒有子系統可言
2. 讀取與本子系統相關的 `docs/adr/`(依主題挑選,不必全讀)
3. 掃描 `docs/arch/` 現有 `subarch-*` 檔名,決定新編號(最大編號 +1);同時讀主架構 frontmatter 的 `subarchs`,確認要設計的子系統是否已有文件

## 模式判斷

- 目標子系統無對應 `subarch-*` 檔 → **初始模式**:完整訪談後從零產出
- 已存在 → **更新模式**:先讀取現有內容,針對要調整的部分訪談,更新文件並視情況新增 ADR

## 流程

### 1. 訪談階段(核心,不可跳過)

先向開發者確認**要設計哪一個子系統**(主架構「子系統劃分」有列的,用 AskUserQuestion 讓開發者選;沒列的,先確認是否要回頭更新主架構)。之後分多輪詢問直到設計完全明確,**不確定就再問,禁止自行腦補**。必須涵蓋:

1. **邊界確認**:主架構寫的定位、職責、對外介面還成立嗎?本子系統做什麼、明確不做什麼?與主架構的描述有衝突時,先和開發者確認以哪邊為準(需要改主架構就先改)
2. **內部元件切分**:子系統內有哪些元件/模組?各自職責?
3. **對外介面**:其他子系統或外部呼叫者怎麼使用它?輸入輸出的契約是什麼?
4. **內部資料流**:資料從進入到離開子系統經過哪些處理?
5. **技術選型**:是否沿用主架構的技術棧?有無子系統特有的框架、套件?— 每個新選擇都要問偏好並給建議與理由
6. **資料儲存與結構**:本子系統擁有哪些資料?結構的框架格式?
7. **關鍵演算法**:核心邏輯的演算法與取捨?
8. **開發階段**:對應主架構的哪個(些)開發階段?內部有無自己的里程碑?

每輪訪談後摘要目前已確認的內容,列出仍不明確的點繼續問。全部明確後,向開發者做最終確認再產出。

### 2. 功能規劃(主動提出,不可跳過)

設計明確後、產出文件前,**由你主動規劃並列出**「完成這個子系統需要哪些 features」——這一步不是問開發者要什麼,而是你基於訪談結果先提出一份完整草案再請開發者修改確認:

1. 依元件切分與開發階段,拆出**大致的 feature 清單**:大概需要幾個 features、分幾個階段、各是哪些;合起來要能覆蓋整個子系統(對外介面、內部元件、資料流全部有人負責),每個 feature 的粒度以「一份 func-spec 可以承載」為準
2. 每個 feature 給:一句話說明、所屬階段、與其他 feature 的先後依賴
3. 呈現給開發者確認:太大就拆、太細就併、缺的補上;開發者同意後定案寫進文件

這份清單是**規劃層級**的路線圖,不是規格——細節留給 `/func-spec:feature` 逐一展開;之後實際建了規格,再把 spec id 回填進清單。

### 3. 產出 `docs/arch/subarch-000x-<slug>.md`

檔名英文 kebab-case、內文繁體中文,固定章節:

```markdown
---
id: subarch-000x
type: subarch
title: <subsystem-slug>
description: <一句話,40 字內:這個子系統負責什麼>
status: active
created: <today>
updated: <today>
parent-arch: architecture   # 回鏈主架構
related-adr: []             # 本子系統相關的 ADR id
---

# <子系統名稱> 子系統架構

## 定位與範圍
(在整體架構中的位置、承接的職責、明確不做什麼;引用主架構「子系統劃分」的對應小節)

## 需求說明

## 架構規劃
(內部元件切分與各元件職責)

## 對外介面
(其他子系統/外部呼叫者使用的介面契約:函式/API 簽名、輸入輸出格式)

## 使用的技術
(沿用主架構的部分一句帶過,只詳述子系統特有的選型)

## 架構圖
(ASCII 繪製,呈現子系統內部元件與資料流,並標出對外介面的出入口)

## 資料結構的框架格式

## 使用到的套件

## 開發階段
(對應主架構開發階段;有內部里程碑則列出)

## 功能規劃
(完成本子系統所需的 feature 路線圖,依階段分組;
 「spec」欄在 /func-spec 建檔後回填實際 id,未建檔時填 `-`)

### 階段一:<階段名稱>
| # | feature | 一句話說明 | 依賴 | spec |
|---|---------|-----------|------|------|
| 1 | <feature-slug> | <做什麼> | - | - |
| 2 | <feature-slug> | <做什麼> | #1 | - |

### 階段二:<階段名稱>
| # | feature | 一句話說明 | 依賴 | spec |
|---|---------|-----------|------|------|

(小結:共 N 個 features、M 個階段;全部完成即代表子系統可交付)
```

### 4. 回填與同步(必做)

1. 主架構 frontmatter 的 `subarchs` 加入新 id(更新模式免),同步 `updated`
2. 主架構「子系統劃分」對應小節補上本檔的 id 與檔名
3. 訪談若修正了子系統邊界或對外介面,回頭更新主架構的對應描述與架構圖(經開發者同意)

### 5. 產出 ADR(視情況)

子系統層級的**重大技術選擇**(子系統特有的框架、儲存方案、關鍵演算法)各產出一份 `docs/adr/adr-000x-<slug>.md`(格式同 `/arch-design`,編號接續 `docs/adr/` 現有最大值),並把 id 填入本 subarch 的 `related-adr`。沿用主架構既有決策的不必重開 ADR。

### 6. 收尾

- 向開發者摘要:產出的檔案、子系統設計重點、功能規劃結論(幾個 features、幾個階段)、主架構有哪些同步更新、新增了哪些 ADR
- 說明之後可用 `/func-spec:feature` 依「功能規劃」清單逐一展開規格(撰寫時以主架構 + 本 subarch 文件為依據,建檔後回填清單的 spec 欄)
