## 目標

拿一個 Level 2 已設計完成的子系統,把 `features/` 底下所有 `status: planned` 的檔(每份都帶一節 `## 契約`)展開:Level 3 的 spec、測試與實作**委派給 subagent** 一路做完:

```
批次澄清(人在場,一次問完)
    ↓
每個階段的每一波:
    配號 + 指派骨架路徑 → 委派 spec(平行)→ 【spec 批准閘門:人放行】
        → 委派 qa ∥ impl(互相不可見)→ 你跑測試 → 仲裁(≤3 輪)→ 波次收線呈報
    ↓
階段閘門(arch-audit + 回報,人放行)→ 下一階段
```

## 你自己做什麼、不做什麼

**這是本 skill 最重要的分工,違反就會出現撞號與文件互蓋。**

| 只有你(編排者)能做 | 委派給 subagent 做 |
|---|---|
| 問開發者(批次澄清、spec 批准閘門、階段閘門) | 寫 spec 文檔與骨架 |
| 配號(F00x)、決定檔名 slug、**指派骨架檔案路徑** | 相依性查證(讀原始碼確認簽名) |
| 寫入 `design.md`(回填 `doc` 欄)與 `system.md` | 寫測試(qa)、寫實作(impl) |
| 寫入 `spec-gaps.md`(建檔、配號、追加條目) | — |
| 寫入 `build-log.md` | — |
| **跑測試、做仲裁**(`orchestration.md`「仲裁協議」) | — |
| 跑 `/arch-audit`、彙整回報 | — |
| git commit(波次 checkpoint、階段收尾) | **不碰 git**:不 add、不 commit、不切分支 |

你**不寫任何 spec、不寫任何測試、不寫任何實作**。你的產出只有:`build-log.md`、`design.md` 的回填、`spec-gaps.md` 的條目、git commit、仲裁裁決、給開發者的回報。

**所有共用檔案由你單線寫入**——`design.md`、`system.md`、`build-log.md`、`spec-gaps.md`。委派出去的 subagent 是併發的,兩個同時整檔寫回同一個檔案,後寫的會把先寫的內容整段蓋掉,而且**當下不會有任何錯誤訊息**(spec-gaps 為什麼特別容易中招,見 `delegation.md` 第 4 條);所以委派 prompt 一律寫明 gap 只回報、不寫檔(見 3d)。

## 前置(不可跳過)

1. 確定目標子系統:引數有給就用;沒給就讀 `.design/system.md` 的 `subsystems`,用 AskUserQuestion 讓開發者選
2. 讀 `.design/system.md` + 該 `subsystems/<slug>/design.md` 全文 + frontmatter `related-adr` 列的 ADR。**不相關的子系統不讀**
3. 跑一次狀態掃描,取得現有 feature 文檔與不一致清單:

   ```
   node "<S>/arch-audit/scripts/scan-status.mjs" .design
   ```

4. **委派門檻檢查**(任一項不過就停下來,不要硬跑):
   - 逐條跑 `../_shared/contract-readiness.md` 的 **A 段(A1–A10)**——`/subsys-design` 收尾時已經跑過一次,**這裡照樣要跑完整的十條**,不是複查也不是抽查
   - 掃描沒有「架構 / 子系統不一致」
   - `spec-gaps.md` 沒有 `open` 的條目(有的話代表上一輪還有 spec 沒修完,先處理)

   **為什麼同一份清單要跑第二次**:第一次是寫的人跑的(同一段訪談上下文,盲點跟著他走),這一次是你跑的——你沒讀過那段對話,只看得到文字,看不懂的地方就是真的沒寫清楚。整條流程在別處用角色隔離解決這件事(qa 與 impl 互相不可見),這裡用的是同一招。而且**你此刻還沒讀過任何原始碼**,純文檔的機械比對正好是你現在唯一做得動、也最該做的事。

   不過關時:列出缺什麼(指到章節,或哪一份 planned 檔的 `## 契約` 缺哪幾欄——`scan-status.mjs .design --subsys <slug>` 的「契約就緒 n/m」會直接告訴你),告知開發者先走 `/subsys-design` 補齊(契約不完整就委派,等於讓 subagent 腦補契約——這正是本流程要避免的事),然後結束。

5. **模組群範圍確認**(`design.md` 有「模組群」表時):本次委派只展開 **active** 的那幾群——`planned` 群沒有契約、也沒有任何 feature 檔,委派出去只會腦補。開跑前**明講**「本次涵蓋 K/N 群,planned 的 J 群這一輪不做,分別是 X、Y」,收尾也要再講一次。**不准把「active 群做完」講成「子系統做完」**

6. `build-log.md` 已存在 → **接續模式**:讀它,跳過已完成的波次,從中斷處繼續(配號沿用既有的表,不重配)

7. **工作樹檢查**:`git status` 要乾淨。checkpoint commit 用 `git add -A`,開跑時若有無關的改動會被一起吞進去——不乾淨就請開發者先 stash 或 commit。接續模式下另外對照 `git log`,確認 build-log 記的進度與 git 歷史一致(對不上以 git 為準,build-log 補正)

## 1. 排波次

從各 `planned` 檔 frontmatter 的 `depends-on` 建依賴圖(v2 起那就是真依賴,不再有第二份會漂的表):

1. 節點 = feature;邊 = 「依賴」欄(`#n` 指同/前階段的項次,`<子系統>/<id>` 或 `G-*` 指別的子系統或全域的文檔)
2. 跨子系統或全域的依賴:確認那份文檔是否已 `done`。未完成的,在批次澄清時問開發者是「等」還是「照介面約定先做」
3. 拓撲排序切波次:同一波 = 所有依賴都已滿足的 features,可平行
4. **階段(`###` 標題)是硬邊界**:波次不跨階段——階段 N 全部驗收通過才進階段 N+1
5. **骨架檔案不得在同一波內重疊**:依各檔 frontmatter 的 `modules` 與 `## 契約` 的「負責模組」預估每個 feature 的骨架會落在哪些檔案;兩個 feature 指向同一個檔案時,把後者拆到下一波。**這是 3a 指派骨架路徑的前提**——平行的 spec subagent 會同時寫骨架,撞到同一個檔案就會互蓋
6. 本子系統已有程式碼(接續模式,或在既有程式碼上加功能)且專案有程式碼知識圖時,跑一次 `node "<S>/arch-audit/scripts/scan-graph.mjs" .design --subsys <slug>` 對帳:程式碼實際的跨子系統依賴,與各檔 `depends-on` 宣告的依賴對不對得起來?**對不上的差異不要自己吸收**,帶進步驟 2 的批次澄清問開發者

7. **排完波次,把閘門位置一起排進去**:階段的最後一波固定是閘門;另外,**自上一次閘門起累計滿 3 波、或累計滿 4 個 feature**,先到的那一個所在的那一波也是閘門(**期中閘門**)。在排程表的「閘門」欄標 `階段` / `期中` / `—`

   為什麼要在排程當下就標死:3f 原本只綁**階段結束**,而階段數是 `design.md` 切出來的,跟工作量無關。多階段的子系統閘門反覆觸發,漂移(契約偏移、`status` 沒回寫、SRP 破損)撐不過一階;**單階段的子系統可以連跑好幾波、整個子系統做完都遇不到一次檢查點**,同樣的漂移一路複利到最後才一次爆出來。階段愈少愈危險,而階段少通常代表子系統單純 —— 直覺上反而是最不需要擔心的那一種,所以這條不能靠直覺補。排程時標死,才不會變成「跑到那裡編排者記不記得」

把「階段 → 波次 → features」的排程呈現給開發者(這是後面一切的骨架,值得先讓人看一眼)。這份排程等一下就是 `build-log.md` 排程表的內容,**每一波都要建一列**(還沒開跑的狀態填 `待跑`)——3e 的波次收線靠那一欄畫進度條,跑到才補列就畫不出「共幾波、還剩幾波」。

## 2. 批次澄清(只問跨波次的政策題)

subagent 問不了人,所以要在 fan out 之前把**它們自己判斷不了、又不隨 feature 而異**的事問掉。

**這一步問什麼、不問什麼,界線要抓緊。** 你此刻還沒有讀過任何原始碼(那是 spec subagent 的工作,也是委派存在的理由),所以「這個 feature 的執行者會在哪裡卡住」這種問題,你只能從 `## 契約` 上**猜**——猜出來的問題準度低,卻花掉開發者最新鮮的一段注意力。真正該問的契約細節,是讀過程式碼的 spec subagent 挖出來的「待確認假設」,它們走 3c 閘門,那裡的材料完整得多。

所以這一步**只問下面四類**——它們的共同點是「答案跨所有 feature 通用,不需要讀程式碼就答得出來」:

- **契約類**(介面、DTO、錯誤語意、邊界歸屬):屬 Level 2。**只問 `## 契約` 上明確留白的欄位**(寫著 TBD / 待定 / 空白,或各份之間互相矛盾的地方),不要替 subagent 預想它會怎麼卡。開發者答完後,**回寫進 `design.md` 的對應章節,或該份 feature 檔的 `## 契約`**——這是契約的補完,本來就該留在 Level 2
- **執行取向類**(套件選擇、資料結構偏好、測試深度、遷移相容性、要不要先做假資料):不屬 Level 2(寫進去會違反抽象邊界)。答完後寫進 `build-log.md` 的「委派決策記錄」。**`greenfield` 專案把「遷移相容性」整項刪掉**——見下方的模式過濾
- **測試框架類**:兩題。(1) 專案還沒有 property-based 測試框架時,現在就問要不要引入、用哪一個——**qa 在委派模式下不得自行引入依賴**,不先問就只能退化成參數化測試。(2) **只跑一個模組 / 一個檔案的測試指令長什麼樣**(`pytest tests/x.py::TestY`、`cabal test --test-options='-p /Auth/'`、`go test ./auth/...`):先自己從 CI 設定 / `Makefile` / `package.json` 找,找不到才問。答案記進 `build-log.md` 的「委派決策記錄」,並抄進每一份 qa 與 impl 的 prompt——**這一行沒有,每個角色都只會退回去跑整庫**
- **排程類**:未完成的跨子系統依賴要等還是照約定先做、這次要跑到第幾階段、**閘門密度**(見下)

**閘門密度**是排程類裡固定要問的一題,答案決定 3c 的波次閘門停不停,記進 `build-log.md` 的「委派決策記錄」:

| 檔位 | 3c 波次閘門何時阻塞 |
|---|---|
| **嚴格** | 每一波都停,議程空著也停(第一次展開新子系統、或契約剛補過時選這個) |
| **標準**(預設) | 議程**為空**時降級為非阻塞呈報,有任一條爭議點就照常停 |
| **快速** | 只有**不可逆決定**、**未宣告的新增依賴邊**與**跨 feature 對帳對不上的名字**才停;契約層級假設一律照 subagent 的傾向採用,記進 build-log 留到階段閘門一次回顧 |

快速檔的代價要對開發者講明白:**契約假設變成事後審查**,裁決不同時 impl 已經蓋在上面了,回頭改的成本比在閘門裁貴一級。所以快速檔只在「契約很紮實、上一階段抽查沒裁錯」時建議;不可逆決定、依賴邊與跨 feature 對帳不進這個折扣——前兩者依定義最難逆,第三者依定義波及兩個以上的 feature,任何檔位都停。

**送出之前先過一次專案模式過濾**(`system.md` 的 `mode`,規則見 `../_shared/boundary-rules.md`「專案模式」):`greenfield` 專案裡,凡是問 migration、舊格式、既有使用者、要不要保留舊版 API 的題目**一律從清單上刪掉**,不是留著讓開發者回答「不用」——那種題目在全新專案裡沒有指涉對象,而開發者最新鮮的那段注意力應該花在真正有指涉對象的題目上。`brownfield` 相反:這幾類是必問,漏了就是把 migration 的決定留給 subagent 猜。

用 AskUserQuestion 分組問(每題附你的建議選項與理由)。**問完後把「還剩哪些不確定」明確講出來**——這些會變成 subagent 的「待確認假設」,在 3c 閘門逐條裁決;開發者要知道現在放行的是什麼風險,以及那些問題會在哪一步回來。

澄清結束後建立 / 更新 `build-log.md`(格式見下),並把契約類的回寫套進 `design.md`(同步 `updated`)。

## 3. 每個階段的執行迴圈

對當前階段的每一波,依序跑 3a → 3f。

### 3a. 預先配號、指派骨架路徑與模型(你做,fan out 之前)

**為本波(建議直接為整個階段)每個 feature 預先分配**三樣東西,寫進 `build-log.md` 的配號表:

1. `F00x` 編號與檔名 slug(兩者合起來就是這份文檔的**全名** `<子系統>/F00x-<slug>`;配號表、委派 prompt、之後每一次呈報都用全名稱呼這份文檔)
2. **骨架檔案路徑**(依步驟 1 第 5 點的預估;同一波內不得重疊)
3. 執行模型(見下表)

號由**你**用配號腳本一份一份鑄出來,**一個 feature 一道指令**(配號與建檔是同一個動作,不准自己數資料夾):

```
node "<S>/arch-audit/scripts/scan-ids.mjs" .design --claim <子系統>/F --slug <kebab-slug>
```

每一道印出 `<id>`、檔案路徑與**全名**(`auth/F005-logout`)——三樣都抄進配號表,委派 prompt 用全名稱呼那份文檔。檔案當場就建好了(只有 frontmatter 骨架),spec subagent 收到的是「把內容填進這個檔」,不是「自己去建一個檔」。

**這一步不能省也不能延後**:配號是「掃描 → 建檔」,中間那段空窗就是撞號發生的地方,平行的 subagent 各自跑一次會同時看到同一個最大值;骨架路徑同理,不由你指派就會兩個 subagent 同時建同一個檔案。號與路徑都由你發,衝突就不存在(委派模式下 subagent 不得自行配號,見 `../_shared/delegation.md` 第 3 條)。

**模型分派**照 `../_shared/orchestration.md`「委派模型分派」(spec 用 `opus`、qa 與 impl 用 `sonnet`;每次呼叫 Agent 工具都帶 `model` 參數,理由與「參數不是 prompt 內容」的提醒見該片),把每個 feature 的模型記進配號表。

### 3b. 委派 spec(平行,opus)

本波每個 feature 各開一個 subagent,**同一則訊息內一次送出**讓它們併發。spec 文檔各寫各的檔案、骨架路徑由你指派過不重疊,所以平行安全。每一個呼叫都要帶 `model: "opus"`。

用 subagent 的真正理由是 **context 隔離**:相依性查證要讀大量原始碼,那些 context 留在 subagent 裡,你只收回結構化回報。這就是 conventions 的「Context 載入紀律」自動化版本。

每個 subagent 的 prompt 必須包含:

```
【委派模式】遵守 <delegation.md 路徑> 的委派模式共通契約:不得提問、
不得寫 design.md/system.md、不得自行配號、機械性查證不可跳過。
你是 spec 角色,遵守 <spec-roles.md 路徑>:不寫實作邏輯、不寫測試,
骨架的函數本體一律未實作標記且必須通過編譯。

執行 dev-flow:spec-design,目標:
- 子系統:<slug>            設計文檔:.design/subsystems/<slug>/design.md
- 指定文檔全名 / 檔名:<slug>/F00x-<slug> / F00x-<slug>.md   (由編排者配號,不得自行掃描)
- 指定骨架檔案路徑:<路徑清單>              (不得寫到清單外的檔案)
- `## 契約`:<該份 feature 檔那一節的原文>
- 委派決策記錄(相關條目):<從 build-log 摘出與本 feature 有關的決策>
- 已完成的前置 feature 與其文檔全名:<...>

完成後依「回報格式」回報,不要寫成給人看的說明文。
```

回報收齊後,由**你**做:

1. 把本波每一份 feature 檔的 `status` 從 `planned` 改成 `specced`(**單線寫**,同步 `updated`)——平行的 subagent 一律不碰 frontmatter。改完跑一次索引生成:

   ```
   node "<S>/arch-audit/scripts/scan-status.mjs" .design --write-index
   ```

   `## 契約` **不動**:v2 起契約住在 feature 檔自己身上,沒有搬家、沒有存根、沒有第二份要同步
2. 跑一次編譯 / 型別檢查,確認整波的骨架**合起來**也編得過(各自編得過不代表放在一起沒衝突)。**這一次不能沿用** subagent 各自回報的編譯結果——它們各自在自己的檔案上編過,合起來的衝突只有這一跑看得到。這是本波唯一需要你自己編譯的一次,3e 之前不要再跑
3. 彙整所有「待確認假設」與「建議修改的 Level 2 契約」,**先不要自己改契約**。彙整時做**雙向層級複審**——兩個方向都要跑,只做降級是危險的過濾:

   - **降級**(假設 → 自裁):對每條假設重跑 `boundary-rules.md` 的兩問(答案出現在邊界上嗎?改錯要驚動其他模組嗎?)。subagent 判錯層級、其實是實作層級的 → 不上閘門,連同各 subagent 回報的「自裁記錄」一起記進 build-log 的「自裁清單」(出處標「編排者降級」)
   - **升級**(自裁 → 假設):對每條「自裁記錄」跑**機械篩**,不需要你重讀原始碼——把該條的 `觸及符號` 欄逐個名字拿去對三個地方:**本波任何一份 spec 的「介面」表**、**`design.md` 的契約章節(對外契約 / 模組間公開介面)**、**任何 DTO / 型別定義**。命中任何一處 → **升級為契約層級**,補進 3c 的裁決議程(標「編排者升級」),並要求該 feature 的 spec subagent 補齊選項/代價/可逆性欄位。`觸及符號` 欄空白或寫成「內部實作」這種概括詞的,一律退回該 subagent 補寫,**不得當作「沒碰到東西」放過**

   兩種錯的代價不對稱:多問一條只花開發者半分鐘;漏問一條會靜默變成契約,而且要等到抽查(3f)或 `/arch-audit` 才浮出來——那時 impl 已經蓋在上面了。所以**篩不確定時一律升級**。

   複審完的契約層級條目,再依 `契約錨點` 欄跑兩道**機械對帳**(都不需要你重讀原始碼):

   - **對已裁決的沿用**:拿每條的 `契約錨點` 去比對 `build-log.md` 的「委派決策記錄」與「待確認假設彙總」。前面幾波(或批次澄清)已經裁過同一個錨點的 → **直接沿用既有裁決,不上閘門**,在 build-log 標「沿用 WAVE-1 ASM-2」,並把該 feature 的 spec 依裁決結果對齊(對不上就退回該 spec subagent 改)。同一件事問第二次,除了浪費開發者的注意力,還會拿到跟上次矛盾的答案——而契約只能有一個
   - **同一波內的合併**:`契約錨點` 相同的多條假設 → **合併成一條**再上閘門,合併後記下**波及的 feature 清單**(這也是 3c 排序要用的數字)。合併時把各 feature 的選項取聯集、代價欄逐條併,任一條的傾向與其他不同就在呈報時用全名點名「auth/F003-… 傾向 a、auth/F005-… 傾向 b」——**不要自己選一個當代表**,傾向分歧本身就是開發者該知道的訊號

   錨點寫成「錯誤處理」這種泛稱、對不上任何契約條目的,退回該 spec subagent 寫具體(指到章節或符號名);錨點欄空白的一律退回,**不得當成「沒有錨點」直接上閘門**——那會讓合併與沿用兩道對帳同時失效。

   剩下的才是 3c 要逐條裁決的,每條的選項/代價/可逆性欄位必須齊全,缺的退回該 feature 的 spec subagent 補寫
4. 有 subagent 回報阻塞 → 不要換個說法重試同一件事;記進 build-log,帶到閘門
5. commit 本波的 spec 與骨架(message 例:`docs(<slug>): WAVE-2 spec + 骨架`)

### 3c. spec 批准閘門(人放行)

**qa 與 impl 都只讀 spec,spec 錯了就是兩邊一起錯。** 所以 fan out 之前先讓開發者裁決。閘門的設計原則:**開發者的注意力只花在契約層級的決定上**——把十條雜訊和一顆鑽石排進同一張表,鑽石就得不到審視,「同意」就退化成蓋章。分三段走。

**閘門停不停,由步驟 2 選定的檔位與本波的議程共同決定。** 三道機械過濾(降級 / 沿用 / 合併)跑完之後,先數議程:不可逆決定、未宣告的新增依賴邊、**跨 feature 對帳對不上的名字**、契約層級假設各幾條,加上你自己讀完的疑慮。**議程為 0 且你沒有疑慮**時(「標準」數四類、「快速」只數前三類),該檔位**降級為非阻塞呈報**——照發第 (1) 段的總覽、在 build-log 記一行「WAVE-2 空議程自動放行」、直接進 3d,不要問。此時的閘門問的是「你同意這份沒有任何爭議點的 spec 嗎」,那不是審查,是蓋章;而蓋章慣了,有爭議點的那一波也會被順手蓋過去。

**降級的是問不問,不是呈不呈報。** 第 (1) 段的總覽任何檔位都要輸出——包含「本波無不可逆決定」「新增依賴邊全部在宣告內」這種零條目的明說。開發者看不到總覽,就不知道自動放行的那一波裡有什麼。

**(1) 總覽呈報**(本波 spec 全部寫完後一次呈報,不逐 feature 打斷):

1. 每份 spec 的**目的、介面表、Laws、Examples** 摘要——重點是 Laws 與 Examples,那是驗收標準的可執行形式
2. 骨架檔案清單與編譯結果
3. **本波所有 spec 的「不可逆決定」逐條列出**(存檔格式、對外 API、FFI 邊界、資料 schema),每條附 subagent 寫的被否決替代方案與否決理由。**這一項不可省略**:依定義它們是整條流程裡最貴的決定,但 subagent 是把它們寫成**既定事實**而不是「待確認假設」交出來的——不主動搬上議程,就永遠不會有人問到它們。條目數為 0 時明確說「本波無不可逆決定」,不要靜默略過
4. **本波新增的依賴邊 vs `design.md` 宣告的依賴**:把各 spec「依賴方向」段的「新增的依賴邊」蒐集起來,與 `design.md` 的模組依賴 / 契約章節做一次 diff。**這一步與第 5 點由同一支腳本一次做完**(跑一次,兩張清單都出來):

   ```
   node "<S>/arch-audit/scripts/lint-cross-spec.mjs" .design --docs <本波的 id,逗號分隔>
   ```

   它的「新增的依賴邊」段把每一條標成「兩端都在 design.md 裡 / design.md 找不到」。**標成找不到的不等於違規**——`design.md` 可能用別的寫法表達同一條邊,那正是要上閘門裁的東西;腳本負責的是**一條都不漏掉**,判斷仍然是你的。**這是機械比對,不需要判斷力**:不在宣告內的每一條都要列出來(哪個模組 → 哪個模組、出自哪份 spec)。新增 import 方向依 `boundary-rules.md` 就是架構變更,現在攔下來只花一次裁決;等 3f 的 `/arch-audit` 才撞到,整波 impl 已經蓋在上面了
5. **跨 feature 對帳:同一波的各份 spec 有沒有互相打架**。上面那道 `lint-cross-spec.mjs` 的「同名不同定義」段就是這一項的機械結果(exit 1 = 有衝突),**沿用它的輸出,不要再跑一次**。腳本只比對**表格裡宣告過的名字**;`G-C00x` 的用法一致性它比不了,那一段仍要你自己讀。把本波所有 spec 的「數據」表與「介面」表攤開,凡是**同名**的型別、欄位、常數、簽名,逐一比對定義是否**逐字相同**;引用到同一條 `G-C00x#<條目>` 的,再比對各自寫的用法與那份契約的原文是否一致。不同的每一組都要列出來(哪個名字、哪幾份 spec、各自寫了什麼)。**這是機械比對,不需要判斷力**,而且**只有你做得到**:spec subagent 互相不可見,qa 只讀分到的那一份,impl 也只讀那一份——`/spec-qa` 雖然會攔「example 與 law 矛盾」,但它看得到的範圍就是單份 spec。**跨 feature、跨波次的矛盾目前沒有任何角色負責,只有編排者站得到這個位置。** 漏在這裡,兩份 spec 各自內部自洽、各自的測試也各自全綠,矛盾要到兩個 feature 真的接起來才爆,那時兩邊的 impl 都已經蓋上去了。對不上時,歸因與第 3 點同一組分流:是某一份寫錯 → 退回那份 spec 重寫;是兩份都合理但契約沒定 → 升級為契約層級議程,連同回寫 `design.md` 一起裁
6. 你自己讀過之後的疑慮:哪條 law 讀起來有兩種解釋、哪個介面沒有被任何 law 或 example 覆蓋
7. 自裁清單:只報「本波自裁 N 條(其中編排者降級 M 條、編排者升級 K 條),已記進 build-log」——**不逐條唸**,那是抽查的材料,不是裁決的議程。`N` 為 0 而假設也為 0 時要說破:這通常代表 spec subagent 根本沒跑層級自答,不是契約寫得完美
8. 待裁決的契約假設:報**合併後的條數**與一行標題清單,每條標出**波及哪幾個 feature**(合併前的原始條數也講一句,例:「原 7 條,依契約錨點合併為 4 條」)。另外報**沿用既有裁決 J 條**(哪幾條、沿用哪一次的裁決),讓開發者知道有東西被跳過、以及為什麼不必再問。

   **合併後仍超過 5 條就先說破**:這通常代表 `## 契約` 本身留了太多洞,問開發者是逐條裁完,還是回 `/subsys-design` 補契約後重跑本波受影響的 spec——十幾條逐條裁,常常不如把契約補好一次

**(2) 逐條裁決(一次一條,禁止打包成表)**:

議程的順序固定,**不可逆決定排在最前面**,因為它們依定義就是最難逆的那一類:

1. **不可逆決定**(第 (1) 段第 3 點):每一條問開發者「接受這個決定嗎、接受這個替代方案被否決的理由嗎」。subagent 自己編的否決理由要照 `boundary-rules.md`「每個建議的義務」檢查——只寫得出好處、寫不出代價的,退回該 spec subagent 補寫再上桌
2. **不在宣告內的新增依賴邊**(第 4 點):每一條問「這條依賴要納進 `design.md`,還是要求 spec 改設計避開它」
3. **跨 feature 對帳對不上、且兩份都合理的**(第 5 點):每一條問「這個名字的定義以哪一份為準,還是兩者都不對、要在 `design.md` / `G-C00x` 補一條共同定義」。**這一類任何檔位都要停**——它依定義波及兩個以上的 feature,而快速檔的折扣是給「只影響一處」的假設的
4. **契約層級的待確認假設**(第 8 點)。**「快速」檔這一類不問**:照各條的「暫採」放行,把「哪一條、採了哪個方案、波及哪幾個 feature」記進 build-log 的「待確認假設彙總」標「快速檔逕行採用」,留到 3f 逐條攤開回顧。其餘檔位排序看兩個維度:**先按可逆性,最難逆的先問**;可逆性相同時,**波及的 feature 數多的先問**。一個難逆但只影響一個模組內部的決定,和一個可逆但五個 feature 都要照著寫的決定,後者值得更清醒的注意力——所以呈報每一條時都要把「這條影響 auth/F003-… / auth/F005-… / auth/F007-…」用全名講出來,那是開發者判斷這題該花多少心思的依據

每一條先輸出完整發問格式,**順序固定,開頭必須是被決定的東西、不是背景**:

1. **要決定什麼**:一句話,寫決定的對象(例:「`ScriptIssue` 的 `siMessage` 欄位,要不要約束它的內容」)
2. **現況原文**:把假設條目的 `現況原文` 欄**原樣貼出來**——型別定義、契約條文、介面簽名。開發者要先看見那個東西,才讀得懂圍繞它的爭論;而這一欄是「spec subagent 讀過原始碼、你和開發者都沒讀過」的唯一補償,漏貼就等於把它讀到的東西丟掉。假設條目沒有這一欄(舊格式)或寫成泛稱的,**退回該 spec subagent 補上**,不要自己編——你沒讀過那份原始碼
3. **背景與已查過**:從 spec 的假設條目取材
4. **選項**:各自的當下成本 / 三個月後代價
5. **傾向與可逆性**:subagent 的傾向與理由(三句以內)、可逆性、這條**波及哪幾個 feature**

再用 AskUserQuestion 問**這一條**,選項就是假設列的方案(subagent 的傾向放第一個並標明)。等裁決落地才進下一條。

**選項必須是開發者真的可能選的。** 兩個選項裡有一個是明顯沒人會挑的陪襯(「或者這個功能不做」),這題就不是在問問題,是在要簽名。碰到這種:退回該 spec subagent 要求寫出真實的第二方案;它寫得出來就照問,寫不出來就代表**這件事根本沒有選擇餘地**——降級為自裁,在呈報裡用一句話說明「為什麼沒有替代方案」,不佔裁決議程。

呈報**用完整句子,禁止只用術語縮寫**:每個關鍵取捨都要說清楚**這是什麼、為什麼要改、不改會怎樣、改了放棄什麼**——「AnimOf 查無 → 哨兵 + 佔位全幅」這種電報體,開發者只能一知半解地全部同意,呈報了等於沒呈報。spec 條目裡的識別字(型別名、函數名)保留原文,但它做什麼要用句子帶出來,不得假設開發者記得每個名字。

**這條「識別字」的義務同樣管流程內部的代號**:`F00x` / `E00x` / `G-C00x` / `LAW-n` / `ASM-n` / `Level 1|2|3` / 「契約層級」「波及」這類本流程自己造的詞,**第一次出現時要用括號帶一句它是什麼**(例:「auth/F002-token-refresh(同一個子系統裡還沒設計的 `evalScript`)」、「auth/F002-token-refresh 的 LAW-10 到 LAW-21(spec 裡定義 validateScript 行為的那十二條性質)」)。代號本身也一律寫全名(`../_shared/conventions.md`「指稱紀律」):你手上同時有一整個子系統的文檔,開發者手上只有你這段字。這些代號在你的視窗裡有整份 build-log 當上下文,在開發者的終端機裡只有一段字;整段用代號寫出來的呈報,和電報體是同一種失效。

subagent 的傾向裡藏著未論證的前提時(「日後要 X 加 wrapper 即可」——所有 X 都能用 wrapper 表達嗎?),你要在呈報時點破,不得照單轉述。

全部裁完後,用 AskUserQuestion 讓開發者選:**批准,繼續** / **要改哪幾份 spec**(改完重跑 3b 的該幾個 feature)/ **停下來**。

**(3) 回寫與契約 diff 確認(批准拆兩段)**:裁決中要回寫 `design.md`(契約補完)或 spec 條文的,由**你**回寫。**合併過的裁決要套用到波及清單上的每一個 feature**——只改提出假設的那一份,其餘幾份還照各自的「暫採」寫著,qa 與 impl 就會從兩份互相矛盾的 spec 投影出去;回寫後逐份確認暫採段已經對齊裁決結果。

**每一條上過閘門的假設,都要在該條 ASM 的 `裁決:` 欄留下結果**(格式:`接受 b(WAVE-2 閘門 2026-08-23);已回寫 design.md「對外契約」§2`;「快速」檔逕行採用的寫 `快速檔逕行採用 a(WAVE-2)`;沿用前面裁決的寫 `沿用 WAVE-1 ASM-2 的裁決`)。**合併過的裁決,波及清單上的每一條 ASM 都要各自寫一次**——只寫提出假設的那一條,其餘幾份的 `裁決:` 就永遠停在「未裁」。

檔案本來就要開、暫採段本來就要改,這只是順手多改一行;但少了它,那份 spec 三個月後讀起來就是一份沒有答案的問題清單(`delegation-design.md`「裁決結果的權威在這一格」)。「同意這個方向」和「同意這段文字成為契約」之間有翻譯損耗,而契約是唯一真相——回寫完成後,把每一處改動用**原文 → 新文**對照一次呈報,開發者確認措辭(有意見就改了重呈)後才 commit(message 例:`docs(<slug>): WAVE-2 契約裁決回寫`),並把裁決與回寫位置記進 build-log 的「待確認假設彙總」。

批准與回寫確認完成之前,**不得**發出任何 qa 或 impl 的委派。

### 3d. 委派 qa 與 impl(互相不可見)

批准後,對本波:

- **發出任何委派之前,先照 `../_shared/orchestration.md`「骨架快照」建好快照 worktree**,sha 寫進 build-log「排程」表的本波那一列——3e 要拿它驗 qa 的紅綠
- **qa 全部平行發出**(每個 feature 一個 subagent,`model: "sonnet"`)——測試檔各寫各的,互不衝突
- **enhance 目標時,先跑一次完整測試套件當基準線,並把結果寫進每一份 impl 的 prompt**——impl 的禁區含「不得跑完整套件」,基準線只能由你給。整波共用同一份(同一個骨架快照 sha 上的同一套測試,跑幾次結果都一樣)。**輸出寫進檔案留著**(`conventions.md`「跑東西的紀律」第 3 關):3e 波末那次整套要拿它逐條 diff,才分得出「本來就紅」與「這次改壞的」;丟掉就得再跑一次基準線
- **impl 也全部平行發出**(`model: "sonnet"`)——3a 已經逐 feature 指派過**互不重疊**的骨架路徑,impl 的禁區又是「只准替換未實作標記」,所以本波的 impl 寫的是各自骨架檔案的本體,寫入不重疊。**成立的前提只有一個:寫入範圍真的被鎖在那份清單裡**,所以委派 prompt 必須帶下面的寫入白名單;帶不上就退回序列
- **qa 與 impl 之間不設先後**:檔案集不相交(測試檔 vs 實作檔),**寫入**不會互蓋。但**讀取會**——qa「該紅卻綠」判準讀的正是 impl 填的那個狀態,impl 先落地判準就靜默失效。所以紅綠的最終確認不靠誰先跑完,移到 3e 由你在骨架快照上做(見 `../_shared/orchestration.md`「骨架快照」)

prompt 用 `../_shared/orchestration.md`「qa 與 impl 的委派 prompt」的兩段共通模板,impl 那段**必須加上寫入白名單段**(接在角色禁區之後):

```
**寫入白名單**:本次只准寫入下列檔案 —— <該 feature 的骨架路徑清單>。
要新增檔案(私有 helper 模組),或要改動清單外的既有共用實作檔
(往既有模組加 helper、動 export / mod 宣告、改共用型別),
一律**停下該項**、把「要動哪個檔案、為什麼、想加什麼」寫進回報阻塞項,
不要自己動手 —— 本波有其他 impl 正在平行跑,清單外的檔案不屬於你。
```

白名單是平行的**唯一**防線:骨架路徑不重疊只保證「各自的骨架檔案不重疊」,擋不住 impl 為了填本體去動清單外的共用檔——那正是平行會互蓋的地方,而互蓋當下不會有任何錯誤訊息。收到「要動清單外的檔案」的阻塞回報時,**不要放行讓它自己去改**:等本波所有 impl 都回報完(此時已無併發),由你判斷是併進哪個 feature 的下一輪,還是該回頭補骨架。

**白名單對帳(收齊本波所有 impl 回報後、checkpoint commit 之前跑)**:白名單寫在 prompt 裡只是**要求**,不是保證——subagent 有沒有照做,唯一看得出來的地方是工作樹,而互蓋當下不會有任何錯誤訊息,也不會有人主動回報「我剛剛動了不該動的檔案」。所以拿本波的**骨架快照 sha** 當基準,機械對一次帳(不需要判斷力,兩行指令):

```bash
git diff --name-only <骨架快照 sha>        # 追蹤中的檔案:被改了哪些
git ls-files --others --exclude-standard   # 新增的未追蹤檔案
```

**第二行不可省略。** impl 為了填本體自己新增一個 private helper 模組,是白名單最常被繞過的方式(正是 impl prompt 點名的第一種違規),而新檔案從沒進過索引,`git diff` 一個字都不會提——只跑第一行,漏掉的恰好是最該抓到的那一格。

兩行的輸出合起來,每一條路徑都必須落在下面三個集合之一:

1. 本波**任一** feature 的 impl 寫入白名單(配號表的「骨架檔案」欄)
2. 本波 qa 的測試檔
3. **你自己**單線寫的檔案(`spec-gaps.md`、`design.md`、`build-log.md`,以及本波 feature / enhancement 文檔的 frontmatter —— 見 3e (2))

三個集合之外的每一條都是違規,照「要動清單外的檔案」的阻塞路徑處理:先 `git diff <骨架快照 sha> -- <路徑>` 看內容,再判斷是併進哪個 feature 的下一輪,還是該回頭補骨架。**判斷完成之前不要 commit**——一旦進了 checkpoint,`git add -A` 會把它和合法的變更捲進同一顆 commit,退回的粒度就從「這個檔案」變成「整波」。

**對帳結果記進 build-log「排程」表本波那一列的「白名單對帳」欄**,沒有違規也要記 `OK`:沒有記錄的對帳等於沒跑過,3f 的閘門分不出「本波沒違規」與「本波忘了對」。

這道對帳補得起「有沒有人動了不該動的檔案」,補不起「auth/F005-logout 的 impl 動了 auth/F007-device-trust 白名單裡的檔案」——git 不記錄哪個 subagent 寫的,路徑只要落在**某一份**白名單內就會過關。那一格只能靠 3e 的測試與 3f 的 `/arch-audit` 兜,所以「骨架路徑波內不重疊」那條規則還是得守住,對帳是它的稽核,不是它的替代品。

**gap 由你單線寫檔(收到任何一份回報就做,不要積到最後)**:程序照 `../_shared/orchestration.md`「gap 單線寫檔」;對帳對不上(寫進去的條目數 ≠ 各回報的總數)就是漏寫或蓋掉了,回頭補。

本波的 impl 全部回報完後(平行跑,沒有「發下一個」這件事):

- **先跑白名單對帳**(見上),結果記進 build-log;有違規的先處置完再往下走
- 有任何一份回報阻塞或新增 spec-gaps → **本波到此為止,不進下一波**,不要為了湊齊而重發(誤差沿依賴鏈複利是本流程最大的風險)。先把 gap 寫進檔案、排程表本波那一列的狀態改成 `停下:<一句話原因>`,再帶著未完成的項目進 3e
- 全部順利 → 記進 build-log,進 3e

**checkpoint commit 是每波一次,由你做**,subagent 不碰 git。等本波的 qa 與 impl **都**回報完才做——`git add -A` 會把還在寫的測試檔或實作檔一起吞進去。message 帶上本波的文檔全名(例:`feat(auth): WAVE-2 auth/F005-logout…auth/F007-device-trust`),讓 build-log 的進度與 git 歷史對得起來。

checkpoint 的用途不是「這段程式碼已驗收」——驗收在閘門。它是**可回退的已知良好狀態**:上面那條「有阻塞就停下」的規則,要有 checkpoint 才退得回去。impl 平行之後可回退的粒度從 feature 變成波,而波本來就是最小的閘門單位——要退也是整波重來,沒有「只退掉 auth/F006-session-list」這種中間狀態。

### 3e. 跑測試與仲裁(你做,上限 3 輪)

本波的 qa 與 impl 都回報完後,**由你**依序做四件事。**不要相信 subagent 回報的測試結果就跳過**——它們各自只看得到自己那一半。

**(0) 驗 qa 的紅綠基線**:照 `../_shared/orchestration.md`「骨架快照」,在快照狀態上跑本波 qa 的測試檔(不必跑整套),逐條對交付判準那張表與 qa 對照表的預期欄。該紅卻綠的,退回該 feature 的 qa 重寫(`dev-flow:spec-qa`,`model: "sonnet"`,只給該幾條測試名與對應的 spec 條文,**不得附上實作原始碼**),重寫後重驗。**這一步一定要在跑整套之前做**:整套一綠,假綠與真綠就再也分不開,而假綠不產生紅燈,仲裁協議永遠不會為它啟動。驗不成的照 orchestration 標「未驗證」帶到閘門,不得默認通過。

**(1) 跑本波所有 feature 的測試子集**(合起來跑一次,不是一份一份跑;子集指令用批次澄清時記進 `build-log.md` 的那一行)。**這一步不跑整套**——整套要回答的是「有沒有連累別人」,而本波自己都還沒全綠時問那一題,拿回來的是同一批紅燈重印一遍(次數見 `../_shared/spec-roles.md`「測試跑幾次、跑多大」)。

有紅 → 仲裁,每輪只跑上一輪紅的那幾條加該 feature 的子集。

全綠 → **跑一次完整測試套件**,確認本波沒有連累波外的東西。**整條迴圈就這一次**(enhance 目標另有 3d 的基準線那一次),跑完進 (2);這一次有紅照樣走仲裁,修完只重跑紅的那幾條,不再整套重來。

有紅 → 歸因走 `spec-roles.md`「仲裁協議」的四分流,裁決後的處置(誰重派、prompt 給什麼、什麼時候停)照 `../_shared/orchestration.md`「仲裁的裁決與處置」,**禁止直接叫 impl 重寫**。

每一輪的裁決都記進 `build-log.md` 的「仲裁紀錄」:第幾輪、哪條測試、歸因結論、依據的 spec 條文。這張表是事後判斷「spec 哪裡寫不清楚」的唯一資料。

**(2) 回寫本波 feature 文檔的 `status` 與 `code-paths`**:每一份本波的文檔,判準與 `/spec-build` 收尾同一條 —— 骨架已無未實作標記、測試全綠、**且沒有指向該文檔的未結 spec-gaps** → 改 `done` 並更新 `updated`;任一條不成立就**留在 `specced`**,不留白也不發明新值(值域只有 planned / specced / done / dropped,見 `../_shared/doc-lifecycle.md`「狀態與生命週期」)。**同一次把 `code-paths` 也填了**:值來自該份 impl 回報裡的程式碼路徑清單(以檔案為主,不含測試檔),留在 `specced` 的照樣填 —— 路徑是既成事實,跟做完沒做完無關。

**這一步只有你做得到,所以只能由你做。** 委派模式下的 impl 不寫這一格(`spec-impl` 委派模式對照表):文檔不在它的寫入白名單裡,而且「全綠」的前提在 (1) 才成立,它只看得到自己那一份。沒有這一步,`status` 會停在文檔建立時的值 —— 而**沒有任何機制會抱怨**:測試全綠、白名單對帳 OK、程式碼真的寫好了,只有帳沒回寫。等到 3f 跑 `scan-status.mjs` 才看得出來,而閘門最密也只到「每 3 波 / 每 4 個 feature」一次(步驟 1 第 7 點)—— 中間那幾波沒有任何東西會替你記得。

回寫完對一次帳:本波配號表的 feature 數 = 這一輪動過 `status` 的文檔數。留在 `specced` 的每一份要講得出卡在哪(阻塞項或未結 gap),寫進下一步的收線呈報。

**每一份真的推到 `done` 的,同一次動作收束它的過程章節**(規則見 `../_shared/doc-lifecycle.md`「`done` 的收束」):`## 待確認假設` 逐條處置——已裁決的把結論搬進 `## 不可逆決定`(或 ADR)後**刪掉原條目**,還沒裁決的表示這份根本不能 `done`;`## 閘門裁決紀錄` 與 `## 修訂記錄` 整節搬進 `archive/<id>-<slug>-process.md`;`## 實作備註` 只留讀碼看不出來的那幾條。**不留墓碑**——「已於 X 裁決,不再是待確認假設」留在原位是最糟的形式,它同時佔著版面又宣告自己無效。

這件事跟回寫 `status` 綁在同一步,理由跟上一段一樣:**沒有任何機制會抱怨**。工地筆記留著不會讓任何檢查變紅,只會讓下一份委派出去的 spec、下一次 `/study`、三個月後的你,把當初吵架的過程讀成現在的契約——而只讀得到那一份檔的 subagent 沒有辦法質疑它。

**(3) 波次收線呈報(非阻塞,不提問)**:本波不論全綠、提前停下或仲裁用盡,都在這裡輸出一次波次狀態。3c 的閘門呈報講的是「這一波**要裁**什麼」,3f 的五塊講的是「這一**階段**做完了什麼」——波跑完到下一波開跑之間沒有任何輸出,「停在 WAVE-2」與「三波都跑完」在開發者眼裡就是同一片安靜,而 3d 那條「有阻塞就不進下一波」的規則,要有這道呈報才看得見。

格式固定:

```
WAVE-1 ✓  →  WAVE-2 ◀ 現在  →  WAVE-3 待跑 ⛬閘門        auth 子系統階段一,共 3 波
WAVE-2(auth/F005-logout, auth/F006-session-list, auth/F007-device-trust)
  完成:auth/F005-logout 介面 4/4、auth/F006-session-list 介面 3/3 · 測試 22/22 綠
  未完成:auth/F007-device-trust 阻塞(要動白名單外的 `src/Shared.hs`)
  status:auth/F005-logout done · auth/F006-session-list done · auth/F007-device-trust specced(阻塞)
  閘門:spec 閘門 放行(裁 2 條 · 沿用 1 條)· 白名單對帳 OK · 仲裁 1 輪(impl 錯)
  gap:auth/GAP-1 未結(卡住 auth/F007-device-trust 的 store 介面)
```

- 第一行是**本階段的全部波次**(含還沒開跑的),直接投影 `build-log.md` 排程表的「狀態」欄——所以那些列在步驟 1 排完波次時就要先建好;排程表「閘門」欄非 `—` 的那幾波後面加 `⛬閘門`,讓開發者看得到下一次停下來看是在哪一波
- 其餘各格一律從 `build-log.md`(配號表、待確認假設彙總、仲裁紀錄、白名單對帳欄)與 `spec-gaps.md` **投影**,不另外記帳;數字只能來自實際跑過的測試輸出與骨架裡剩餘的未實作標記,**不得估**
- **`status` 欄逐一列出本波每一份文檔的回寫結果**,一份都不能省;**同一行帶上 `code-paths` 填了幾條**。這一欄是 (2) 那一步唯一的憑據——回寫沒做、或做了一半,只有把每一份攤在同一行上才看得出來;寫「都完成了」等於沒寫
- 「未完成」與「gap」沒有條目時寫「無」;該波若是空議程自動放行,「閘門」欄要寫明——空白分不出「沒有」與「沒查」

呈報完,照**排程表「閘門」欄**走:本波標 `—` 且本階段還有下一波 → 回 3a 開下一波;本波標 `期中` 或 `階段`,或本波提前停下 → 進 3f。

### 3f. 閘門(人放行)

**什麼時候進來**:排程表「閘門」欄標 `階段` 或 `期中` 的那一波跑完,或任何一波提前停下。

- **階段閘門**(`階段`):本階段全部波次完成或提前停下。下面八步全做
- **期中閘門**(`期中`):本階段還沒跑完,但自上次閘門起已累計 3 波或 4 個 feature。下面八步照做,**除了**第 4 步只記進排程表本波那一列(本階段結果留到階段閘門)、第 6 步的第一個選項改成「繼續本階段的下一波」、第 8 步跳過(還沒到收尾)

兩種都不可跳過,也不可合併到下一次 —— 期中閘門存在的理由就是「不要等到最後才一次看」,延後它等於沒有它。

進來之後:

0. **不重跑測試**:本階段每一波都在波末跑過一次完整套件,而波末到現在你沒有動過任何程式碼——沿用最後一波那一次的輸出,回報裡寫明「沿用 WAVE-n 波末那次整套」(`../_shared/conventions.md`「跑東西的紀律」第 2 關;次數帳見 `../_shared/spec-roles.md`)。**閘門是看帳,不是再驗一次**
1. 跑 `node "<S>/arch-audit/scripts/scan-status.mjs" .design`。**拿輸出跟 build-log 的配號表對一次帳**:本階段交付過的 feature,腳本這邊還顯示未完成的,一律當成 3e (2) 的回寫漏了或該文檔真的沒做完——逐一查清楚再往下,不要當成雜訊。腳本同時會點名 `spec-gaps.md` 裡格式不合的條目(`- 狀態:` 不是列表項、狀態值不是 `open` / `resolved`),那些會讓 gap 被讀成永遠未結,順手修掉
2. 專案有程式碼知識圖時,先照 `../_shared/codegraph.md` 把圖更新到最新再進下一步——本階段剛寫進去的程式碼不在舊圖裡,不更新的話閘門的架構檢測看到的是上一階段的世界
3. 跑 `/arch-audit subsys <slug>`——檢查資料流管線一致性、SRP、邊界外洩、模組介面漂移。**這是委派品質的把關點**,不可跳過
4. 更新 `build-log.md` 的本階段結果
5. 向開發者回報(**期中閘門**:下面所有「本階段」讀成「自上次閘門起的那幾波」)。**先出逐波狀態表**:範圍內每一波各一列(波次 / features / 完成 / 未完成 / 閘門與白名單對帳結果 / 未結 gap),把 3e 的波次收線壓成一行,含空議程自動放行的波次、有違規或沒對到帳的波次——階段做完才回頭看,開發者要的是整階段的波次帳,不是最後那一波。再走固定五塊:
   - **完成了什麼**:features、介面實作數(n/m)、測試結果(law 幾條、example 幾條、通過/失敗)、**qa 紅綠基線**(驗過幾條、退回重寫幾條、未驗證幾條——未驗證的要點名是哪幾個 feature)
   - **未結的 spec-gaps**:每一條的內容、卡住哪個項目、需要 spec 回答什麼——**這是閘門的重點,不能只講「都完成了」**
   - **契約裁決與自裁**:閘門裁過的**不可逆決定**、**新增依賴邊**與**契約假設**各幾條、裁了什麼、回寫到哪;自裁清單本階段新增幾條、其中編排者**降級**幾條、**升級**幾條。**閘門密度選「快速」時,本階段所有「快速檔逕行採用」的契約假設在這裡逐條攤開**(哪一條、採了哪個方案、波及哪幾個 feature、實作已經照著寫了),請開發者逐條確認——這是快速檔把裁決延後到的那個位置,不攤開就等於那些契約從來沒有被人看過;確認不同意的,照第 6 點當成「先修這些問題」處理。降級比例高 → spec subagent 把實作細節往上丟,門檻要收緊;升級比例高 → 它的層級自答太寬鬆,`觸及符號` 欄要求要講得更死。邀開發者從自裁清單**抽 2-3 條**看裁得對不對——這是雜訊的事後審計路,裁錯率高再收緊,比預設全部上桌便宜
   - **仲裁紀錄摘要**:幾輪、歸因分佈(impl 錯 / qa 誤讀 / spec bug),spec bug 的每一條都要點名
   - **arch-audit 發現** 與 **建議的上層變更**:依嚴重度排序
   - **定錨區塊**(`../_shared/anchor.md`):位置樹以本階段的 features 為「目前」、逐條列介面與型別的狀態;未結的 spec-gaps 與與契約牴觸的假設一律進偏離清單;下一步 = 下一點的三個選項
6. 用 AskUserQuestion 讓開發者選:**進下一階段** / **先修這些問題**(修 spec 後重跑該波的 qa+impl,或走 `/bugfix`、`/spec-design`,或回 `/subsys-design` 改契約後重跑本階段) / **就此停下**
7. 開發者要修契約 → 由**你**更新 `design.md`(不是 subagent),更新後受影響的 feature 要重跑,不能靠既有產出將就
8. 詢問是否為本階段收尾(squash 成一個 commit 或打 tag 皆可;checkpoint 已在過程中留下,這裡只處理歷史整理)。**不主動 push**;整合發 PR 走 `/branch-pr`

## 4. `build-log.md`

路徑 `.design/subsystems/<slug>/build-log.md`。版面照本 skill 目錄下的 `templates/build-log.md`——建檔或更新時打開它照抄,七個章節:排程、委派決策記錄、配號表(含骨架路徑與模型欄)、待確認假設彙總、自裁清單、仲裁紀錄、階段結果。

全部階段完成後 `status` 改 `done`。

## 5. 收尾

- 摘要:跑了幾個階段、產出幾份 spec、幾條介面、測試總結、仲裁輪數與歸因分佈、`## 契約` 是否在過程中被修訂(修訂一律經 `/spec-redesign`)
- **未結的 spec-gaps 與未裁決的待確認假設**:如果開發者選擇提前停下,明確列出還懸著的每一條
- **自裁清單**:總條數、編排者降級與升級各幾條,提醒開發者定期抽查(抽 2-3 條;裁錯率高就收緊層級門檻)
- **git 狀態**:已 checkpoint 到哪一個 feature、有沒有未 commit 的殘留
- 剩下的階段與繼續方式(再跑一次 `/subsys-build <slug>` 會走接續模式)
- **本次涵蓋的範圍**:有「模組群」表時,重申「涵蓋 active 的 K 群,planned 的 J 群(X、Y)這一輪不做」。所有 active 群跑完 ≠ 子系統交付;**摘要裡不准出現讓開發者以為子系統做完的說法**
- 最後輸出**定錨區塊**(`../_shared/anchor.md`):位置樹展開本子系統全部 features 的最終狀態,`planned` 模組群各一行標「未開工」;完成度第一行照樣是產品級(開發階段 + 名冊建檔數);未結的 spec-gaps 進偏離清單;下一步從樹上推(還有 planned 群 → `/subsys-design <slug>` 補契約並建出該群的 feature 檔;全部階段完成且無 planned 群 → `/arch-audit system`、`/branch-pr`;提前停下 → 再跑 `/subsys-build <slug>` 接續)

## 邊界

- **不跑跨子系統**:一次只展開一個子系統。多個子系統要一個一個來(先跑被依賴的那個)
- **不改 Level 1**:過程中發現主架構要改,回報給開發者走 `/system-design` 更新模式,不自己動
- **不做 enhancement / bugfix 的委派**:`/spec-design` 的 **enhance 模式**需要先讀程式碼再與人討論 scope、`/bugfix` 需要人確認重現條件,兩者都不適合無訪談委派。過程中發現的問題,在閘門建議開發者走 `/spec-design`、`/bugfix`;enhance 的 scope 談完、spec 寫好之後,**後半段(qa ∥ impl → 測試 → 仲裁)走 `/spec-build <文檔全名>`**——那條迴圈與 feature 完全相同
- **單份 spec 不必動用本 skill**:只要跑一份已寫好的 spec(F00x 或 E00x),用 `/spec-build <文檔全名>`(例 `/spec-build auth/F005-logout`)就夠了;本 skill 多出來的是排波次、配號、階段閘門與 `design.md` 回填
- **契約不完整時不啟動**:前置第 4 條的門檻是硬性的(`契約就緒 n/m` 不滿格就停)
- **需要改契約時停下來**:委派過程中發現某份 `## 契約` 本身寫錯了(不是留白,是錯),不要自己改也不要讓 subagent 改——記進 gap、停住那一支,收尾建議開發者走 `/spec-redesign`。契約改動要人拍板,因為它可能是 Level 2 的事(`契約就緒 n/m` 不滿格就停)
