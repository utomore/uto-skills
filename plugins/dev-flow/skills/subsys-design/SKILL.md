## 目標

基於主架構,為**單一子系統**產出 `.design/subsystems/<subsystem-slug>/design.md`(並建立 `features/`、`enhancements/`、`bugfixes/` 空資料夾結構):承接 Level 1 定下的邊界與職責,把子系統設計到「**一個讀不到本次對話的執行者也能直接開始寫 feature 設計文檔**」的程度。**在範圍與設計明確之前,禁止產出任何文件。**

這個判準決定了本層的產出深度:除了契約與資料流,還要為每個 feature **建出一份 `status: planned` 的文檔,裡面一節 `## 契約`**(見流程 2b)。契約寫得夠完整,Level 3 才能被委派出去平行執行(`/subsys-build`);寫得含糊,下游只能靠腦補補完。

本文件是三層階梯的 **Level 2**:只定義「模組邊界契約」與「資料流管線」。**絕對禁止**定義內部私有函數、helper 名稱、私有變數或內部暫存資料結構——模組間的抽象 Interface(Go Interface / TypeScript Type / Rust Trait)是本層的下限,再往下屬於 Level 3 的實作自主權。

## 前置(不可跳過)

1. 讀取 `.design/system.md`。**不存在時**:停止,告知開發者必須先執行 `/system-design` 建立主架構——沒有 Level 1 就沒有子系統可言(只有舊版 `docs/arch/` 體系時,提醒先用 `/system-design` 遷移)
2. 讀取與本子系統相關的 `.design/adr/`(依主題挑選,不必全讀)
3. 讀主架構 frontmatter 的 `subsystems` **名冊**與「子系統劃分」章節,確認要設計的子系統是否已有 `design.md`;把它那一小節的**職責逐句抄下來**——那是本次產出要逐條對帳的東西(`contract-readiness.md` A10)

## 模式判斷

- 目標子系統無 `subsystems/<slug>/design.md` → **初始模式**:完整訪談後從零產出
- 已存在 → **更新模式**:先讀取現有內容,針對要調整的部分訪談,更新文件並視情況新增 ADR。更新模式做的是**加東西**:新的 feature、新的模組群、把 `planned` 群轉 `active`
- **要改的是既有契約時,這裡不是入口** —— 走 `/spec-redesign`。它會先判這次改動是 Level 3 就地改還是要回 Level 2,並留下可查證的修訂痕跡。從這裡直接改契約會繞過那道判準
- **由 spec-gaps 觸發的更新**:那是 `/spec-redesign` 的事,它會判層級後決定要不要回到這裡

## 流程

### 1. 訪談階段(核心,不可跳過)

先向開發者確認**要設計哪一個子系統**(主架構「子系統劃分」有列的,用 AskUserQuestion 讓開發者選;沒列的,先確認是否要回頭更新主架構)。之後分多輪詢問直到設計完全明確,**不確定就再問,禁止自行腦補**。必須涵蓋:

1. **邊界確認**:主架構寫的職責、邊界、對外契約還成立嗎?本子系統做什麼、明確不做什麼?與主架構描述衝突時,先和開發者確認以哪邊為準(需要改主架構就先改)
2. **對外契約(Public Interface & DTOs)**:其他子系統或外部呼叫者怎麼使用它?輸入輸出的 DTO 長什麼樣?如何對齊 Level 1 定義的通訊契約?
3. **內部模組劃分**:子系統內有哪些核心模組(Controller / Service / Repository / Pipeline Engine…)?各自的單一職責?
3b. **模組群(領域)**:這個子系統裡裝的是**一條資料流管線上的幾個模組**,還是**多個平行領域**(彼此沒有天然先後、共用同一個部署 / 編譯單位,例如同一個內部函式庫裡的 Interaction / Economy / Progression)?
   - 是後者:把領域清單問齊——**包含這一版不打算做的**——每個領域一句話職責,並確認哪些現在就要寫契約(`active`)、哪些先掛著(`planned`)
   - **這一問不能省**。省掉的後果是:本份 `design.md` 只寫得出已落地的那一個領域,而該子系統的進度分母就只有那一個領域的 feature ——其餘領域完全不存在,子系統會在只做了五分之一的時候顯示 100%
   - 是前者(單一領域):明講一句,`design.md` 就不寫「模組群」表
4. **資料流管線(Data Flow Pipeline)**:資料從「輸入 → 驗證 → 業務處理 → 儲存/外部呼叫 → 輸出」怎麼流動?
5. **模組間介面**:模組互相調用的抽象 Interface 怎麼定義?(只定簽名與 DTO,不寫內部邏輯)
6. **技術選型**:沿用主架構技術棧?有無子系統特有的框架、儲存?——每個新選擇都要問偏好並給建議與理由(給建議時遵守 `boundary-rules.md`「每個『建議』的義務」:當下成本 + 三個月後的代價 + 是否觸碰 invariant)
7. **開發階段**:對應主架構哪個(些)階段?內部有無自己的里程碑?

每輪訪談後摘要目前已確認的內容,列出仍不明確的點繼續問。全部明確後,向開發者做最終確認再產出。

### 2. 規劃 feature 並整批建檔(主動提出,不可跳過)

設計明確後、產出文件前,**由你主動規劃並列出**「完成這個子系統需要哪些 features」——不是問開發者要什麼,而是基於訪談結果先提出完整草案再請開發者修改確認:

1. 依模組劃分與開發階段,拆出 feature 清單:幾個 features、分幾個階段、各是哪些;合起來要能覆蓋**每一個 active 模組群**(對外契約、內部模組、資料流管線全部有人負責),每個 feature 的粒度以「一份 feature 設計文檔可以承載」為準。`planned` 的模組群這一輪不列 feature,但要在小結講明還剩幾群沒開工
2. 每個 feature 給:一句話說明、所屬模組群(多群時必填)、負責模組、所屬階段、與其他 feature 的先後依賴
3. 呈現給開發者確認:太大就拆、太細就併、缺的補上;同意後定案寫進文件

這份清單是**規劃層級**的路線圖,不是規格——細節留給 `/spec-design` 逐一展開。

4. **清單定案的當下,整批鑄號建檔**(一個 feature 一道指令,一次做完):

   ```
   node "<S>/arch-audit/scripts/scan-ids.mjs" .design --claim <子系統>/F --slug <kebab-slug>
   ```

   建出來的每一份都是 `status: planned`,frontmatter 有 `stage` / `modules`(有模組群時再加 `group`),內文只有一節 `## 契約` 的六欄空骨架——步驟 2b 就是把那六欄填滿。

   **為什麼在這裡配號、而不是等寫 spec 時再配**:一次配一整批落在同一個 commit,比分散在幾週內、幾條分支上一次配一個更不會撞號;而且依賴關係從第一天就寫得出真 id(`depends-on: [auth/F001]`),不必先發明一層「列號」再翻譯。理由見 `../_shared/doc-lifecycle.md`「命名與編號規則」。

### 2b. 每一份 feature 檔的 `## 契約`(不可跳過)

建檔之後,把**每一份**檔的 `## 契約` 六欄填滿。判準只有一句話:

> **一個沒有你在旁邊、也讀不到這段對話的執行者,拿著這一節加上本文件的契約章節,能不能直接開始寫 feature 設計文檔?**

一句話說明載不住一個 feature,所以這一節要補上六件事(**階段**已由 frontmatter 的 `stage` 帶入,照抄一份給讀的人)——注意這**全部都還是 Level 2 的資訊**(邊界與契約),不是實作細節:

1. **負責模組**:落在「內部模組劃分」的哪些模組
2. **實作的 Level 2 介面**:逐條引用本文件「對外契約」/「模組間公開介面」的**具體條目名稱**(不是「相關介面」這種含糊寫法);只用不新增時寫「無新增」
3. **資料流管線段落**:走「資料流管線」的哪一段(從哪到哪)
4. **驗收標準**:怎樣算做完(可觀察的行為,不是「功能正常」)。這一欄是 Level 3 **Laws** 的來源——寫成「對所有輸入都成立的性質」形式最好,寫不出性質至少要寫成可以逐條驗證的觀察,「功能正常」這種寫法到了 Level 3 就翻不成任何測試。

   **提到的每一個量都要附觀察點**:指得出「對外契約」/「模組間公開介面」的哪一條介面觀察得到它,寫成 `<行為> — 觀察點:<介面條目>`。指不出來 = 介面缺觀察點,回去補契約——留到 Level 3 才發現,唯一的出路就是開測試後門,而後門在 `testing-policy.md` 一律禁止(判準見 `../_shared/contract-readiness.md` A5)
5. **明確不做**:這個 feature 的邊界外緣——最容易被執行者自行擴張的地方,寫清楚才守得住粒度

寫的時候仍受**資訊抽象邊界**約束:`## 契約` 裡不准出現私有函數名、helper 名稱、內部暫存結構。若發現某一份非得寫實作細節才講得清楚,那是「Level 2 契約本身沒定義完整」的訊號——回去補契約章節,不要在這一節裡越界。

寫完後跟開發者確認一輪定案。**`## 契約` 是 `/subsys-build` 能否委派展開的門檻**:六欄有空的或寫得空泛,委派就只能靠腦補。跑這道確認就緒度:

```
node "<S>/arch-audit/scripts/scan-status.mjs" .design --subsys <slug>
```

「契約就緒 n/m」滿格才委派得動(分母只算 `planned` 的檔)。

**這一節寫完就凍結**:`/spec-design` 只准往它下面加節,要改得走 `/spec-redesign`。所以「明確不做」那一欄要現在就寫對——它是這個 feature 負向邊界的唯一紀錄,之後沒有人有權限靜默改掉它。

### 3. 產出 `.design/subsystems/<slug>/design.md`

檔名固定 `design.md`,資料夾名 = 子系統 slug(英文 kebab-case),內文繁體中文,固定章節:

```markdown
---
id: <subsystem-slug>
type: subsystem
title: <subsystem-slug>
description: <一句話,40 字內:這個子系統負責什麼>
status: active
created: <today>
updated: <today>
parent: system
related-adr: []
code-paths: []          # 選填,見下
---

# <子系統名稱> 子系統架構

## 定位與範圍
(在主架構中的位置、承接的職責、明確不做什麼;引用 system.md「子系統劃分」對應小節)

## 對外契約(Public Interface & DTOs)
(其他子系統/外部呼叫者使用的介面:函式/API 簽名、輸入輸出 DTO Schema;
 必須對齊 Level 1 的通訊契約。**每個 DTO 用欄位表寫,「單位/值域」欄不可省略**——
 判準見 contract-readiness.md A4:qa 拿著這一列,寫不寫得出一個有具體期望值的斷言?)

### <DTO 或介面名稱>
| 欄位 / 參數 | 型別 | 單位 / 值域 | 語意 |
|---|---|---|---|
| `expiresAt` | int64 | 毫秒,UTC epoch,必為正 | 憑證逾期時間 |

## 模組群(Module Groups)
(**只有多領域子系統要寫**;單一領域的子系統整節省略。
 這張表是本子系統的**真分母**:狀態欄只有 active / planned 兩個值,
 `planned` 代表契約章節還沒寫、feature 檔也還沒建,那一群不算進進度)

| 模組群 | 狀態 | 職責一句話 | 契約章節 | 模組前綴 / 目錄 |
|---|---|---|---|---|
| <Group> | active | <這一群負責什麼> | 對外契約 §X、§Y | <Foo.Group.*> |
| <Group> | planned | <這一群負責什麼> | 未寫 | <Foo.Group.*> |

(小結:共 N 群,active M 群、planned N-M 群。
 **planned 的那幾群不在進度分母裡**——它們的 feature 檔一份都還不存在)

## 內部模組劃分(Internal Modules)
(各核心模組與其單一職責;只寫模組邊界,不寫內部實作。
 有「模組群」表時,每個模組要標明屬於哪一群)

## 資料流管線(Data Flow Pipeline)
(輸入 → 驗證 → 業務處理 → 儲存/外部呼叫 → 輸出 的完整流動路徑)

## 模組間公開介面(Module Interfaces)
(模組互相調用的抽象 Interface 定義:簽名與 DTO,不寫具體內部邏輯;
 參數與回傳的欄位語意同樣要寫到「單位/值域」的顆粒度)

## 使用的技術
(沿用主架構的部分一句帶過,只詳述子系統特有的選型;不羅列基礎函式庫)

## 架構圖
(ASCII 繪製:子系統內部模組與資料流管線,標出對外契約的出入口)

## 開發階段
(對應主架構開發階段;有內部里程碑則列出)

## 功能總覽
(**生成的**索引,不要手寫:跑 `scan-status.mjs .design --write-index`。
 兩個標記之間的內容每次都會被覆蓋;每一格的權威在各自的 `features/F00x-*.md`。
 建檔當下先貼空的標記對,腳本才有地方寫)
```

`code-paths`(選填,規格見 `../_shared/doc-lifecycle.md`):本子系統的程式碼會落在哪些路徑前綴,如 `code-paths: [src/auth]`。它把檔案級的工具產出(程式碼知識圖等)捲回子系統級;訪談時順手問一句「這個子系統的程式碼放哪」就填得起來,專案沒用這類工具就留 `[]`。**這是路徑宣告,不是實作細節**,不違反抽象邊界。

**產出前自我檢查**:逐條跑 `../_shared/contract-readiness.md` 的 **A 段(A1–A10)**,不可跳過、不可挑著跑。

那十條裡有九條是**純文檔的機械比對**——不需要判斷力、不需要讀原始碼、不需要問開發者(A10 要開 system.md 對帳職責,一樣是機械比對)。跑不動代表文檔缺了東西,那就是發現本身。有任何一條不過就回去補 `design.md`,補完重跑,**不准「這個留給 Level 3 補」**:在這裡改的是一份文檔,漏到閘門才抓到要改 spec → qa 重寫測試 → impl 重寫實作。

十條的名稱與判準以該片為準(這裡不重複,避免兩份走樣);**`/subsys-build` 的委派門檻會拿同一份清單再跑一次**,所以這裡放水只是把同樣的工作推遲一步,而且推遲到你已經不在場的時候。

`A10`(職責覆蓋)是**多領域子系統的救命條**:它問的是「`system.md` 給這個子系統的職責,本份 `design.md` 是不是每一條都有著落」。答案是「有幾條還沒寫」時,正確處置是**把它們寫成 `planned` 模組群**,不是當作不存在——當作不存在的那一刻,它們就從所有進度分母裡消失了。

### 4. 跨子系統契約對帳(有相鄰子系統已建檔時,必做)

**條件**:本子系統有依賴或被依賴的子系統,而且那些子系統已經有 `design.md`。一個都沒有就整段跳過,等相鄰者建檔時由那一次 `/subsys-design` 補跑。

`system.md` 只定完「誰跟誰講話」(拓撲),**「講什麼」的雙邊對齊沒有任何一步在做**——契約分散在各份 `design.md`,而且每一份都是在「消費者不在場」的情況下單方面寫的。這一步就是補這件事。

1. 先拿反向索引當素材(指令與界線見 `../_shared/design-query.md`):

   ```
   node "<S>/arch-audit/scripts/scan-status.mjs" .design --subsys <slug>
   ```

   「反向依賴」段是誰在消費本子系統的候選清單。**腳本只產生索引不下判斷**,逐條對照兩邊的 `design.md` 自己判。

2. 逐條跑 `../_shared/contract-readiness.md` 的 **B 段(B1–B4)**:每條對外契約指得出消費者、每條消費得到滿足、方向與拓撲一致且無環、知識歸屬不重疊。

3. **多方共用、不屬於任何一方的契約**(共用 DTO、跨子系統事件 schema、共同遵守的錯誤語意)建成 `.design/contracts/G-C00x-<slug>.md`(格式、編號與引用寫法見 `../_shared/doc-lifecycle.md`「全域契約文檔」),消費端只引用不重新定義。

   **不准塞進某一個子系統的 `design.md` 再讓別人引用**——那份 `design.md` 從此擁有一個不屬於它的事實,違反知識歸屬(B4)。反過來,只有**一個**使用者的契約不該建成全域,它屬於那個子系統。

4. B 段發現要改到**對方**的 `design.md` 時,不要自己動手改別人的文檔:列出來跟開發者確認,經同意後再改,並同步對方的 `updated`。

### 5. 回填與同步(必做)

1. 確認本子系統 slug 已在 `system.md` frontmatter 的 `subsystems` **名冊**裡。名冊是 `/system-design` 在子系統劃分定案時就寫齊的(含未建檔者),所以正常情況下**這裡不必動它**;真的沒有,代表這個子系統當初沒進規劃——補進去並同步 `updated`,同時檢查「子系統劃分」與「開發階段」有沒有一起漏掉它
2. `system.md`「子系統劃分」對應小節把「design.md:未建」改成實際路徑
3. 訪談若修正了子系統邊界或對外契約,回頭更新主架構的對應描述與架構圖(經開發者同意)
4. 步驟 4 若新建或修改了 `G-C00x`,確認它的 `subsystems` 欄列全了使用者,並在本 `design.md` 的對外契約章節以 `G-C001-<slug>#<條目>` 引用(不要複製條目內容)
5. 跑一次索引生成,讓 `design.md` 的「功能總覽」對得上實際檔案:

   ```
   node "<S>/arch-audit/scripts/scan-status.mjs" .design --write-index
   ```

   (由 `/spec-redesign` 帶進來的更新,gap 回填與下游影響清單由那支負責,這裡不重複)

### 6. 產出 ADR(視情況)

子系統層級的**重大技術選擇**(特有框架、儲存方案、關鍵協定)各產出一份 `.design/adr/ADR-00x-<slug>.md`(格式同 `/system-design`,編號接續現有最大值),並把 id 填入本 `design.md` 的 `related-adr`。沿用主架構既有決策的不必重開 ADR。

### 7. 收尾

- 向開發者摘要:產出的檔案、子系統設計重點、**模組群結論(共幾群、active 幾群、planned 幾群,planned 的分別是什麼)**、feature 規劃結論(建了幾份 planned 檔、幾個階段、契約就緒 n/m)、A 段與 B 段檢查修正過什麼、主架構同步了什麼、新增了哪些 ADR 與共用契約(都寫全名:`ADR-003-jwt`、`G-C001-session`)
- 有 `planned` 模組群時,摘要**必須明講**「本次交付涵蓋 K/N 群,其餘 J 群這一輪不做」。只講已完成的那幾群 = 讓開發者以為子系統快好了
- 最後輸出**定錨區塊**(`../_shared/anchor.md`):位置樹畫到每一份 feature 檔一行(此時全是 `planned`),`planned` 模組群各一行標「未開工」。

**下一步怎麼給:先看還有沒有相鄰子系統沒設計。** 順序原則與完整理由見 `../_shared/contract-readiness.md`「設計順序」,摘要如下——

| 現況 | 建議的下一步 |
|---|---|
| **同階段內還有互相有通訊邊的子系統沒設計** | 先 `/subsys-design` 把那一組做完,再回來動工。對外契約是**不可逆決定**,消費者不在場就凍結它,代價會由對方承擔 |
| **那一組都設計完了**(或本子系統沒有相鄰者) | 挑**一個**先打通到底——選「對外契約被最多人消費」或「最不確定」的那個。第一根樁的價值是暴露契約在實作上站不站得住,而這個反饋你會想在其他子系統動工**之前**拿到 |

選定要動工的子系統後,展開方式二選一,讓開發者選:

- **逐一手動**:`/spec-design` 一次把一份 `planned` 檔寫成 `specced`,每個 feature 都能訪談深談;spec 與骨架寫完後接 `/spec-qa <文檔全名>` 與 `/spec-impl <文檔全名>`(例:`/spec-impl auth/F001-login`)
- **委派展開**:`/subsys-build <slug>` 一次跑完整個子系統——批次澄清一次問完、依「依賴」欄排波次委派 subagent、每個階段結束停下來給你驗收

**不要建議「設計一個就做一個」**:第二個子系統設計時幾乎必然要回頭改第一個的對外契約,而第一個那時已經有程式碼和測試了。
