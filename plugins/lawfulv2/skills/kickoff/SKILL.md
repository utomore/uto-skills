# lawfulv2:kickoff — 開案

> **核心**：This skill sets the rules of a project and nothing more: say how the whole project will be built, ask until the user has decided every foundation question, write each decision down, then leave the building to the user.（這個 skill 只替專案定規範：先講整個專案會怎麼建，問到使用者把每一個基礎問題都決定了，把每個決定寫下來，之後怎麼做交給使用者。）步驟與這一句衝突時，這一句贏：停下，回報。

## 輸入 / 產出

| 輸入 | 產出 |
|---|---|
| 使用者對這個專案的想法；既有的檔案（有的話）；型錄 `${CLAUDE_PLUGIN_ROOT}/catalog/README.md` | `CLAUDE.md`（給 LLM 的專案記憶）、`README.md`（專案的門面）、`docs/adr/` 的索引與設計、流程各四份 ADR、`docs/glossary.md`（名詞表）、`docs/guide/`（給人看的說明）、`docs/backlog.md`（還沒定的點子）；架構選了型錄的一格，另有那一格的目錄、依賴契約、檢查腳本、pre-commit、CI、CODEOWNERS，`make check` 與 `make test` 綠 |

ADR 分兩類，各住一個資料夾，格式是精簡的 MADR（見 `docs/adr/README.md`）：

| 設計 `docs/adr/design/`：技術的抉擇 | 流程 `docs/adr/process/`：開發流程、架構規範 |
|---|---|
| D-001 語言與執行環境 | P-001 北極星與不做清單 |
| D-002 資料放哪裡 | P-002 工作流程 |
| D-003 軟體架構 | P-003 架構規範 |
| D-004 工具（專案管理、檢查、CI 與 CD） | P-004 檢查與合併的關卡 |

照步驟 4 到 8 的順序談：目標、技術基礎、工作流程、軟體架構、檢查與 CI。前面的決定限制後面的選項。

**什麼才寫成一份設計 ADR**：有考慮過別的選項，或者反悔要付代價。沒有選擇空間的工具選擇（例如 formatter 用哪個）沒人會反對、三個月後也沒影響，不另開一份，併進 D-004 的工具表一列。專案用不到的那一份（例如沒有要存的資料就沒有 D-002）刪掉，索引那一列一起刪。

## 前置

兩件都成立才開始，任何一件不成立就回報是哪一件並停下，由使用者接好再回來：

- **原始碼庫**：目標目錄是 git repo，`git remote -v` 列得出遠端。
- **專案管理工具**：問使用者用哪一個（GitHub issue、Jira、Trello 或別的），用這個 session 連得到它的方式做一次只讀的查詢，查得到才算連上。

## 分流

- 已經有 `docs/adr/process/P-001-north-star.md` → 更新模式：只談使用者點名的那一份。改完之後，談的順序排在它後面的每一份逐份問一句「這個決定還成立嗎」，不成立的接著談。上線之前直接改寫那一份；上線之後寫新的一份，舊的 `status` 改成 `superseded by <新的編號>`。新的技術抉擇開一份新的 D、新的流程規則開一份新的 P，編號接著往上加。
- 要設 GitHub repo 的標籤 → `lawfulv2:labels`。
- 使用者要的是開始寫功能 → 不在這裡。規範定好之後，怎麼做由他與 LLM 照 `CLAUDE.md` 與 ADR 自己談。

## 怎麼問

這個 skill 的工作就是問。每一步底下列的題目是起點，不是清單：專案用不到的不問，專案特有的要自己追出來。

- **一次只問一題**，等到答案再問下一題。
- **能列選項的題目就列**：二到四個，每個附「適合什麼情況」與「代價」。有傾向就講、說為什麼；決定是使用者的。
- **每個答案往下追**：答案帶出的下一層問題當場問完。選了語言，就問版本、套件管理、型別檢查；說了「之後要部署」，就問部署到哪、誰放行。
- **模糊的答案不收**：「都可以」「之後再說」「看情況」要追到變成一個決定；真的定不了，就明確記成待決定（`docs/adr/README.md` 的「待決定」，寫明卡在什麼）。
- **點子不當成決定**：使用者順口提到、現在不做的想法，照 `docs/backlog.md` 的四行格式記下，當場念給他確認。
- **沒登記的名詞當場問**：「它是什麼、不是什麼」，一句話記進名詞表。
- **不替使用者回答**：不用「一般來說都會…」帶過；他沒講的不寫進任何一份文件。
- **一步談完就複述**：把這一步的決定逐條念一遍，他確認了才談下一步。

## 步驟

1. **確認前置**（見上）。
2. **看現況。** 目標目錄是空的，還是已經有程式碼、設定與文件。已經有的東西是使用者做過的決定：一件一件念出來，問他「這個照舊嗎」，照舊的直接記進對應的 ADR，不重問。
3. **先講全貌。** 動手問之前，把整個專案會怎麼建講給使用者聽：最後會有哪幾份檔、各自給誰看；ADR 為什麼分設計與流程兩類、談的順序與為什麼是這個順序；接下來會被問哪幾類問題；這個 skill 不做什麼（不寫功能、不替他選、不管進度）。講完問一句「這樣的建法有沒有哪裡跟你想的不一樣」，照他的回答調整再開始。
4. **目標：P-001 北極星與不做清單。** 起點：替誰解決什麼問題、為什麼現在做。然後問出兩樣東西：
   - **北極星**：一句話，拿來判斷一件工作的種類（六個種類的判準見模板 `CLAUDE.md`「工作的種類」）。問完當場驗：請使用者舉三到五件他想做的工作，用這句話判斷各自的種類，念給他聽。判斷不出差別，或排序沒有因此改變，就追問、改寫到判斷得出來。只描述願景、判斷不出任何一件工作種類的句子不收。驗過的工作與種類記進 P-001。
   - **不做清單**：跟北極星相關性極低、已經判定不做的具體項目。使用者說沒有，就記「目前沒有」，這一節照樣建。
5. **技術基礎：D-001 語言與執行環境、D-002 資料放哪裡。** 起點：幾個人、有沒有期限或要移交；語言與版本；在什麼設備或環境上執行與部署；套件管理；主要的框架、套件與版本；資料放哪裡、多少、誰維運。主要的框架與套件有考慮過別的、或反悔要付代價的，各開一份新的 D；其餘併進 D-004 的工具表。
6. **工作流程：P-002，專案管理工具寫進 D-004。** 工具在前置已經確認。起點：一個工作項目是什麼、要寫哪些內容、多大；里程碑是什麼、怎樣算完成；狀態有哪幾種、誰改；標籤或分類；時程怎麼排；分支怎麼命名；工作項目怎麼和分支與 PR 連起來；誰可以開與關；誰審、每張 PR 最多幾輪審查；誰合併、順序；報告除了「此次任務的達成目標」與「沒做的事」還要哪些區塊；進度誰看、在哪裡看。進度與狀態住在工具裡，不在 repo 的文件裡。使用者要在 repo 裡用文件管，照他的決定寫，並把代價（要先 commit 一份文件才能動工）寫進「三個月後的影響」。另外三題一定要問：
   - **種類的待遇**：六個種類逐一問做不做、優先序、什麼時候做。使用者對某一種沒有想法，照預設「只做目的，其他寫進報告」填，並記成待決定。
   - **里程碑怎麼切**：列選項給他選。傾向里程碑用北極星的階段（做得完、會關），種類用標籤或分類；不傾向里程碑直接用種類，代價是種類永遠做不完、里程碑永遠關不掉。選了階段，不是「目的」的工作項目放在一個常駐的里程碑（例如「待排」）。工具是 GitHub 時，種類的標籤由 `lawfulv2:labels` 建。
   - **第二把尺**：這個專案的工作做之前還要再過哪一關。通常是 P-003 的架構規範，也可能是設計規範或合規要求；記下名字與指向哪裡。
7. **軟體架構：D-003 選哪一種、P-003 規範。** 先問問題再談架構：有哪幾種入口、業務規則多不多、幾個人同時開發、之後誰接手。然後讀型錄總表，把符合 D-001 的每一格的「適用條件」與「代價」講給他聽；他選一格，或講出他要的別種架構。選了哪一種寫進 D-003；怎麼切、依賴往哪個方向、law 住哪寫進 P-003。
   - **選了型錄的一格**：讀那一格的 `README.md`，把分層表與代價再念一次，逐條確認他接受。D-003「選擇」裡預填的選項，逐一問他有沒有考慮過，沒考慮過的刪掉。
   - **型錄沒有的架構**：照他講的把怎麼切、依賴往哪個方向寫進 P-003，並明講「型錄沒有這一格，這裡只記決策，不附檢查」。**不准現場發明一格**：不替他寫依賴契約與檢查腳本。
   - **law 住哪，一定要問。** law 是這個專案必須成立的性質。問它跟著程式碼的哪個單位（一個 package、一個 module、一個領域資料夾），寫在哪個檔，怎麼和測試對起來。選了型錄的一格，把那一格的做法講給他聽，由他確認。
8. **檢查與 CI：P-004 關卡，工具寫進 D-004。** 把 P-003 定下的規則一條一條拿出來問「這一條由什麼守」：linter、型別檢查、檢查腳本、AI review，還是只能靠人 review（誰）。再問 pre-commit 跑哪些、等多久可以接受；AI review 用不用、誰跑、擋不擋；誰批准會影響所有人的路徑。CI 用什麼跑、什麼時候跑、跑哪幾步、和本地是不是同一道；哪幾步綠了才能合進主線、分支保護誰設；現在要不要 CD、要不要完全自動、部署到哪些環境、誰放行。現在不做 CD 就記「現在只有 CI」與打算什麼時候再定。選了型錄的一格，把那一格附帶的檢查一道一道念，每一道由他決定留或拿掉。
9. **落地。** 先 `--dry-run` 把會建哪些、跳過哪些念給使用者，他確認再正式跑：

   ```
   node "${CLAUDE_PLUGIN_ROOT}/bin/scaffold.mjs" --target <目錄> --project <專案名> --tagline "<一句話>" [--catalog <格> --package <套件名> --owner <帳號>]
   ```

   不給 `--catalog` 只鋪文件層。四個值都用前面談定的，沒談到的回去問：
   - **專案名**（`--project`）：小寫字母、數字、連字號；選了型錄的一格，它也是 pyproject 的 name 與 cli 指令名。
   - **一句話**（`--tagline`）：這個系統替誰做什麼，README 的第一句。只寫使用者說的。
   - **套件名**（`--package`，選了型錄的一格才要）：`src/<套件名>/`，小寫字母、數字、底線；通常是專案名把連字號換成底線。
   - **owner**（`--owner`，選了型錄的一格才要）：CODEOWNERS 的帳號，會影響所有人的路徑改動都要他 review；團隊帳號也可以。

   鋪完之後：
   - **填每一份檔裡 `<…>` 的佔位符**，只寫談定的內容。每一份 ADR 都精簡：「當前情境」兩三句，`decision-makers` 寫拍板的人。設計的「選擇」只列他真的考慮過的選項；只考慮過一個的，寫它與反悔的代價，不編別的選項。
   - **`CLAUDE.md` 的「三把尺」「種類的待遇」「不做清單」「工作方式」**：照 P-001 與 P-002 談定的填，和 ADR 一字不差；「工作的種類」的判準表照模板留著，讓這份 `CLAUDE.md` 單獨也讀得懂。
   - **`CLAUDE.md` 的「協作規則」**：從 ADR 整理出每次寫程式都要守的規則，一條一行，行尾註明出自哪一份。
   - **`README.md`**：這是什麼樣的專案，用使用者自己的話。
   - **名詞表與 backlog**：把談的過程中記下的名詞與點子寫進去。
   - **`docs/guide/`**：他現在有要寫給人看的說明才建那一份，否則只留索引。
   - **他決定拿掉的檢查**：`Makefile`、`.pre-commit-config.yaml` 與 P-004 的表三處一起改，不留一處。
   - **「已存在、沒動」的每一個檔**逐一處理，`bin/scaffold.mjs` 不覆蓋任何既有的檔，要併的由使用者決定再手動改：`CLAUDE.md` 已存在 → 把模板的「## 三把尺」「## 工作的種類」「## 種類的待遇」「## 不做清單」「## 工作方式」「## 協作規則」六節補在檔尾，它已經有的同名節由使用者決定怎麼併，其餘一個字不動；`pyproject.toml` 已存在 → 把模板的 `[tool.ruff]`、`[tool.pyright]`、`[tool.pytest.ini_options]`、`[tool.importlinter]` 各節併進去，`[project]` 與依賴由他決定；其餘的檔 → 列出模板裡有而它沒有的段落，由他決定併不併。
10. **驗**（選了型錄的一格才有）：`make sync`，然後 `make check` 與 `make test` 都要綠。紅的是鋪的問題，修到綠；不准為了綠去改檢查腳本或契約。

## 收尾

回報：每一份 ADR 各一句決定了什麼，設計與流程分開列，刪掉了哪幾份、為什麼；北極星，以及驗證它時判斷過的那幾件工作和各自的種類；種類的待遇裡記成待決定的是哪幾種；不做清單有幾項；第二把尺是什麼；還有哪幾題記成待決定、各卡在什麼；名詞表登記了幾個名詞、backlog 記了幾個點子；選了型錄的哪一格與他接受的代價，或「型錄沒有這一格，只記了決策」；鋪檔用的專案名、一句話、套件名與 owner；建了幾個檔、跳過了哪幾個與各自怎麼處理；`make check` 與 `make test` 的結果（有的話）。建議照 P-002 定的分支命名開一條分支發 PR 合進主線。最後明講：規範定好了，接下來做什麼、怎麼做，由使用者與 LLM 照 `CLAUDE.md` 與 ADR 談，工作項目開在 D-004 定的工具裡。

## 邊界

不替使用者做任何一個決定、不替他寫他沒講的內容；不寫任何業務程式碼、不建任何領域、不在名詞表登記他沒講過的名詞；不在 repo 裡建立管進度的文件，不替他在專案管理工具裡開、改、關任何東西；不發明型錄裡沒有的架構，不替型錄沒有的架構寫檢查腳本或依賴契約；不為了讓檢查變綠改檢查腳本或契約；不覆蓋任何既有的檔；前置沒成立不開始。
