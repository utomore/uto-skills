## 工作的種類

每件工作（要做的功能、審查發現、順手看到的問題）都標一個種類。分類看這件工作保護的是什麼，不看它屬於哪個子系統。

| 種類 | 判準 |
|---|---|
| 目的 | 少了它，北極星做不到 |
| 延伸 | 北極星已經做得到，這是多一種方式或更方便 |
| 工程保證 | 軟體本身的可靠性與正確性；跟北極星無關，但出事會壞資料或壞狀態 |
| 效能 | 北極星做得到，但太慢、太大或太耗資源 |
| 開發工具 | 服務開發的人，不是服務用產品的人 |
| 維護 | 既有的債：警告、重構、文件對帳 |

## 協作規則

- 取新名字（型別、函數、模組、資料夾）之前，先讀 `docs/glossary.md`；命名只用登記過的名詞，表上沒有的，先登記再命名。
- 測試不是越多越好，也不設數量上限：功能的輪廓由 law 定（住哪見 P-003），測試是證明輪廓成立的證據。
  - 每條測試都要有歸屬：`<package>/LAW-n`、`<package>/EX-n`，或修 bug 的回歸測試（名字帶工作項目的編號）。歸屬不了的，抽成 law、改成例子，或刪掉。
  - 一條 law 原則上一條性質測試，產生器涵蓋 law 寫的定義域；拆成多條要說得出理由。
  - 例子少而有目的：每個例子說得出它示範輪廓的哪一處（典型、邊界、曾經壞過的地方），重複示範同一處的不留。
  - 新的或改寫的測試要有紅轉綠的證據：把實作改壞，它會紅才算數。
  - 回報與 PR 看品質不看條數：寫新增、改寫、作廢了哪些 law，紅轉綠的證據，有沒有沒歸屬的測試；不把總條數當進度。
- <從 ADR 整理出來、每次寫程式都要守的規則，一條一行，行尾註明出自哪一份（例：P-003）。>
