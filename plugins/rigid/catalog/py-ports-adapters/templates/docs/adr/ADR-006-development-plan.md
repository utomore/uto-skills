# ADR-006：開發計畫與完成的定義

- 狀態：採用
- 日期：<YYYY-MM-DD>

## 背景

開發需要一份依依賴排序的計畫：做一個功能的人只讀和手上工作有關的部分，每個單元做到哪裡看得出來，而且看得出來的根據是程式碼，不是有人手動填的欄位。

## 決策

### 計畫的形狀

- **開發計畫放在 `docs/plan/`。** `README.md` 放寫法、完成的定義、驗收情境、里程碑的出口條件；每個里程碑一個檔案 `M<n>-<英文短名>.md`，裡面是可開發單元與驗收。
- **里程碑依實際的依賴排序**，和對客戶交代的順序無關。
- **可開發單元**：一個垂直切片，一個人一到五個工作天，合併後展示得出來；依賴只指向同一個或更早的里程碑。id 是 `REQ-<三位數>`，跨檔不重複、不重用。

### 完成的定義

- **一個單元完成，是它的每一條驗收都有證據。** 狀態由證據推算，不手動填：每條都有是「完成」，有一部分是「進行中」，都沒有是「未開始」。
- **證據寫在驗收那一行的行尾**，格式是「（證據：a、b）」，由文件指向程式，讀需求的人一眼看得到每一條由什麼證明。證據有五種：
  - `law:<領域或 platform>/LAW-<n>`：領域的規則。
  - `test:<路徑>::<名稱>`：platform、api、cli 的測試。
  - `ci:<步驟 id>`：CI 裡每次都會跑的步驟。
  - `check:<腳本>`：`make check` 跑的檢查腳本。
  - `展示:<代號>`：只能由人在測試環境看的。看過之後在里程碑檔的「## 展示紀錄」記一列，「展示」欄寫 `<REQ id>/<代號>`，依據寫得出查得到的東西（建置編號、網址、截圖位置）；沒有紀錄，這條就還沒有證據。
- **一條驗收寫不出證據，就是還沒做，或是寫得檢查不了**；後者要改寫驗收。

### 檢查

- `check_laws` 檢查單元表：id 不重複、domains 欄列的領域都存在、law 提到的 REQ 存在且列了那個領域。
- `check_evidence` 檢查證據真的存在：law 在 `## Laws` 且單元的 domains 欄列了那個領域；測試的檔案與名稱存在；步驟 id 在 CI 設定裡；腳本在 `make check` 裡；展示紀錄對得到一條驗收，代號在單元裡不重複。測試有沒有過不另外查，進了主線就代表 CI 綠了。
- `make progress` 依階段與里程碑列出幾個單元完成；`make progress M=M3` 列出每個單元有幾條驗收有證據。

## 後果

- 做一個單元只讀 README 與一個里程碑檔。
- 改一個里程碑不會和改另一個里程碑衝突。
- platform 與基礎設施的單元沒有領域的 law，一樣看得出進度。
- 測試改名、CI 步驟改名時 `check_evidence` 失敗，逼人回頭更新驗收。
- 驗收要寫得具體到有東西能證明，寫不出證據的會一直是「進行中」。
- 展示紀錄由人寫，是唯一靠人誠實的一環，所以要求寫出查得到的依據。

## 否決的做法

- **單元表加手動的狀態欄**：和程式碼會分岔，看不出憑什麼算完成。
- **在測試上標 `@pytest.mark.req("REQ-004")`，由程式指向文件**：看不出測試證明的是哪一條驗收；CI 步驟與展示也標不上去。
