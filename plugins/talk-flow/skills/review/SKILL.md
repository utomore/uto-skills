# /review — 演講整體審查

先讀取 `../_shared/conventions.md`、`../_shared/layouts.md` 與 `../_shared/styles.md`,遵守所有文檔慣例、版型詞彙與風格基底詞彙。

## 唯讀原則(不可違反)

本命令**不修改任何原始碼、文檔與 metadata**、不「順手修一下」。只有兩個合法寫入:

1. **審查報告**:結論寫入 `review/review-<YYYY-MM-DD>-<序號>.md`(資料夾不存在就建立;序號 = 當日已有報告數 +1,從 1 起算),並在對話中給精簡摘要與報告路徑
2. **重新建置產物**:`talk/dist/` 與 `talk/src/slides.md` 是可再生成的**產物**,審查前執行 `node build.mjs` 重新建置不算違反唯讀(審過期產物才是錯的)

使用者要動手修時,導向對應命令:單頁/圖形 → `/page-adjust`、段落設計 → `/section-design`、頁面與備註 → `/section-impl`、主軸/時間分配/theme/文字規範 → `/topic-design`。

## 範圍

- 無參數 → **全場審查**
- 參數是段落 id 或編號(`section-02`、`02`)→ **局部審查**:只審該段與其 `depends-on`、以及它與前後段的接縫;指標照算但在報告標明「局部,總分僅供該段參考」

## 前置

1. 執行機械檢查腳本(唯讀):

```
node <本 skill 目錄>/scripts/scan-coherence.mjs [專案根目錄,預設 .]
```

腳本交叉比對段落覆蓋、頁數三處同步(deck 實際張數 / deck frontmatter / docs section)、圖形引用完整性、先備知識順序、時間帳與產物新鮮度,並輸出**頁面地圖**(版型、內文形式、圖、備註字數、文字摘要)、**圖形 SVG 分析表**(viewBox、字級、色數、節點、連接線轉折)、**theme tokens 與寫死色值清單**。

2. 有「frontmatter 格式不合規」時**先停下**:清單欄位讀不到值,後面的比對全部不可信。請使用者(或經同意)改回行內陣列 `[a, b]` 再重跑。
3. 讀取 `docs/topic.md`(核心訊息、聽眾輪廓、`style-base` 風格基底、投影片風格與**文字規範**是所有判斷的基準)、全部非 rejected 的 `docs/section-*.md`(含「文字技法選用」)、全部 `talk/src/section-*.md`(含備註)。rejected 段落不讀。
4. **build 後逐頁目視,一頁都不能跳過**。腳本的表格只是證據與清單,不是替代品 — Layout、配色統一、用語一致、AI 感、圖形實際可讀性只能看:
   - 產物過期或缺席時先在 `talk/src/` 執行 `node build.mjs`(依 `topic.md` 的 `outputs`)
   - 可行時**用瀏覽器開 `talk/dist/slides.html` 逐頁目視**(claude-in-chrome),這對 Layout 與 AI 感最準;同時讀 `talk/src/` 原始碼確認版型類別、備註內容與圖形 SVG 的色值座標
   - 不能用瀏覽器時,逐檔讀 deck 原始碼 + 圖形 SVG 判斷(版型類別與圖形座標都在原始碼裡,要自己在腦中排版)
   - 局部審查時開該段所有頁,加上前後相鄰各一頁(判斷接縫);頁數多時分批開,每批做完就記下該批結果

## 判斷準則

### 偏題怎麼算

逐段標記四類,**偏題不是罪,量太多才是**:

- **貼題**:直接推進核心訊息
- **支援**:不直接推進但為後段鋪路(先備知識、動機、反例)
- **呼吸點**:刻意的幽默、故事、閒聊 — 服務節奏,**不計入偏題**
- **偏題**:對核心訊息無貢獻,也不服務節奏

偏題比例 = 偏題段落的 `est-minutes` 合計 ÷ 總時長。呼吸點超過 15% 時另計為節奏問題,不算偏題。

### 銜接怎麼評

每個接縫(段落接縫 = 段數 − 1;頁面接縫 = 頁數 − 1)評三級:

- **自然**:上一段/頁的結尾為下一個開場提供理由(問題被提出 → 下一段回答;概念被建立 → 下一頁使用)
- **可接受**:順序合理但沒有明說理由,聽眾要自己補
- **突兀**:主題硬切、需要尚未鋪陳的概念、或版型/視覺語彙突變

段落接縫同時看備註的「銜接:」「交棒:」提醒是否對得上實際的前後頁內容。只列**突兀**與**可接受**的接縫並寫明理由;自然的只給數量。

### 峰值怎麼找

以「每分鐘新概念數」估段落難度(新概念 = 聽眾輪廓的「未知」清單裡的詞、或本段首次出現且需要解釋的術語)。峰值 = 明顯高於相鄰段落者。判斷三件事:

1. 峰值位置 — 落在演講 30–70% 處最好;全擠在最後 20%(疲勞區)最糟
2. 峰值是否連續 — 連續兩段高峰等於讓聽眾一路掉線
3. 峰後有沒有喘息 — 複習頁、圖解、呼吸點

### 逐頁看什麼(開頁時的八個面向)

八個面向的「收斂 vs 失控」都**以 `topic.md` 的風格基底為準**:`styles.md` 各基底附有「review 提示」— 同一現象在不同基底下判法不同(center 大字頁佔比高在 keynote-impact 是特性、在 tech-deep 是離群;版型多變在 keynote-impact 不扣、在 tech-deep 從嚴),「投影片風格」記錄的偏離視為合規,不重複扣分。

**Layout 與版型**

- 版型是否出自 `layouts.md` 詞彙表;同 section 同類內容是否沿用同一版型,跨頁重點位置是否固定
- 切格是否有理由:內容是一個整體卻被硬切成多格(整頁單一區塊本來就是合法版型),或每頁都反射性三等份 — 都算版型誤用
- grid 沒塌陷(格數 = 內容數)、格內不擁擠、文字不溢出格子;層級 3 級以內,重點分得出來
- 一頁一重點:能不能一句話說出這頁要幹什麼;說不出來就是該拆
- 圖是主角時有沒有給夠大的格

**視覺引導(動線)**

- 開頁第一眼落在哪?是不是這頁的重點?第一眼被次要元素(裝飾、過大的次要圖、強調濫用)搶走就是動線失敗
- 閱讀順序能否一次走完:左→右、上→下與內容邏輯(先→後、因→果)一致,不需要跳來跳去回頭找
- 有圖的頁:連接線是否**順著動線引導視覺** — 線的方向把眼睛帶向重點,而不是拉回頭或指向頁面外;圖文之間的對應關係一眼能接上
- 判斷方法:對每頁說出「眼睛從 A 進 → 依序看 B、C → 停在 D」;說不出來或與講述順序相反,就是要修

**配色統一**

- 色值只住在 `theme.css` tokens;deck 內寫死色值(腳本已列)逐條確認是特例還是失控
- 強調色只在強調時出現(一頁最多一處);語意跨頁固定(紅=問題不能中途換義)
- 對比:正文對背景要看得清;符合 `topic.md` 的 `slide-style` — 偏離要指出哪一頁偏到哪去

**文字規範遵循**(基準 = `topic.md` 的「文字規範」與該段設計文件的「文字技法選用」)

- **可區分性**:標題與內文、條列各點之間讀起來分得開 — 行距與字級落差足夠,沒有字擠成一團難以掃讀的區塊;grid 格內文字沒有因塞太多而變成密文
- **出自規範**:每頁用到的字級、強調方式(粗體/底線/強調色)、列表符號都在文字規範的選單裡且用在規範說的情境;規範外的用法逐條列出(哪頁、什麼寫法、規範裡沒有)
- **同情境一致**:同類內容跨頁同字級、同強調、同符號(同是要點就不該一頁圓點一頁編號、同是關鍵術語就不該一頁粗體一頁底線);出現差異時檢查有沒有明確理由(刻意對比等),沒有理由的差異就是失控
- 強調是否過量:一頁裡粗體/底線/強調色加起來蓋掉太多正文,等於沒有強調

**圖形(有圖的頁才評)**

- **連接線轉折 ≤2 折**:3 折以上就扣分,要靠重排節點解決;腳本已列候選,開檔確認哪些是真的連接線
- 交叉線盡量為 0;流向一致(同圖單一主方向);標籤貼近所指(<20px);節點 ≤7
- **實際渲染可讀性**:圖形字級是名目值,嵌入格縮放後還讀得到才算數 — 這只能在 dist 頁面上看
- 目視存疑時用 `/svg-layout` 的 lint 取得量化證據(標籤溢出幾 px、端點間隙幾 px、幾折);報告要指得出數字,這裡是數字的來源
- 圖形類型與設計文件規劃一致;圖上元件名稱與頁面文字、備註同名
- **截圖加註圖**:截圖是否 base64 內嵌(外連路徑在 `<img>` 下不載入,整張空白就是這個);標記與頁面圖例編號**一一對應**且順序 = 動線順序;標記 ≤5、色值出自 tokens;縮放後截圖裡被指的 UI 與標記編號仍看得清(連接線折數規則對此類圖不適用,改看標記對應)

**備註品質**

- 每頁有備註;內容是**提醒**(要點、措辭、數字、時間)而非逐字稿或情境描述;段落首尾有「銜接:」「交棒:」
- 備註與頁面內容對得上(備註講 A 頁面寫 B 就是不一致)

**用語與概念一致**

- 同一概念全場同名(投影片、備註、圖形標籤都算);中英夾雜規則一致:首次全稱 + 縮寫,之後統一
- 專有名詞大小寫正確且一致;標題語法一致(全名詞短語或全結論句);數字與單位格式一致

**AI 感(具體訊號,不是感覺)**

- 樣板骨架:每頁都「標題 + 三張等寬卡片」,內容換了結構沒換;`card` 類別濫用
- 強迫對稱:什麼都湊成三點、每點字數幾乎一樣長;無意義裝飾與 emoji 項目符號
- 空泛語言:賦能、助力、一站式、全方位、無縫整合;無資訊標題(「概述」「總結」)
- 假數據:圖表軸沒單位、數字是 100/200/300、趨勢線沒有來源
- 沒有講者痕跡:沒有真實專案名、實際數字、踩過的坑、取捨理由

反面證據(有人味):具體數字與專案名、明說的取捨、不對稱但有理由的版面、承認的失敗。判斷 AI 感時**先找反面證據**,找不到才扣分。

## 十三項指標(每項 0–5,總分 65)

| # | 指標 | 5 分 | 3 分 | 1 分 |
|---|---|---|---|---|
| 1 | **主軸貼合度** | 偏題 ≤10%,每段都說得出對核心訊息的貢獻 | 偏題 ≤25%,或有 1 段貢獻說不清 | 偏題 >35%,或核心訊息在投影片與備註中從未出現 |
| 2 | **結構完整度** | 開場鉤子、核心訊息明說、收束與行動呼籲三者都在 | 缺其中一項 | 缺兩項以上,或結尾停在最後一張技術頁 |
| 3 | **銜接自然度** | 無突兀接縫,可接受 ≤1 | 突兀 1–2 處 | 突兀 ≥3 處,或有段落接縫完全沒有理由 |
| 4 | **先備知識鋪陳** | 概念都在使用前被解釋,`depends-on` 與 order 一致 | 有 1 個概念用在解釋之前 | 順序倒置,或依賴 rejected 段落 |
| 5 | **備註完備度** | 每頁有提醒式備註,首尾銜接/交棒齊全,備註與頁面一致 | 1–2 頁缺備註或備註逐字稿化 | 大面積無備註,或備註與頁面講的是兩回事 |
| 6 | **節奏與時間帳** | est 合計佔總時長 90–95%;每頁 20–180 秒 | est 佔比略出界,或 1–2 段翻頁過快/停留過久 | est 超出總時長,或多段節奏出界 |
| 7 | **認知負荷曲線** | 單一峰值落在中段且峰後有喘息 | 峰值偏後段,或峰後無喘息 | 多個連續峰值,或峰值全在最後 20% |
| 8 | **版面與配色一致度** | 版型出自詞彙表且跨頁收斂;色值只住 tokens 且語意固定;無溢出塌陷 | 2–3 頁版面或用色離群 | 每頁自成一套、寫死色值失控,或有溢出/對比不足 |
| 9 | **用語與概念一致度** | 同概念全場同名(含圖形標籤與備註),縮寫規則一致 | 有 1–2 個概念換過名字 | 關鍵概念三種以上叫法,聽眾會以為是不同東西 |
| 10 | **去 AI 感/原創度** | 版面隨內容變化,有真實數字、專案名與取捨 | 有樣板痕跡但內容具體 | 樣板骨架 + 空泛語言 + 假數據,看不出誰講的 |
| 11 | **圖解可讀性** | 所有連接線 ≤2 折、無交叉、流向單一、標籤貼線、節點 ≤7、縮放後讀得到 | 有 1–2 條 3 折線,或少量交叉 | 有 ≥4 折線、線條交叉成網、看不出流向,或縮放後文字不可讀 |
| 12 | **視覺引導** | 每頁第一眼落在重點,動線一次走完且與內容邏輯一致,連接線順著動線 | 2–3 頁動線要回頭找,或第一眼被次要元素搶走 | 多數頁說不出動線,資訊量大但抓不到重點 |
| 13 | **文字規範遵循度** | 字級/強調/列表符號全出自文字規範且同情境一致;標題內文行距分明 | 2–3 處規範外用法或無理由的不一致 | 文字技法各頁自創、同類內容寫法不一,或多頁文字擠成一團難以掃讀 |

第 11 項只在有圖形時計分;整場沒有圖就標「不適用」,總分改除以 60。`topic.md` 沒有「文字規範」章節時,第 13 項改以 theme.css 既有字級與全簡報實際用法的一致性評分,並在報告建議補跑 `/topic-design` 定規範。

**符合度** = 總分 ÷ 65(無圖時 ÷ 60)。判定帶:

- **≥90%** 可以上台
- **75–89%** 小修即可上台(列出修哪幾處)
- **60–74%** 有結構問題,先修再排練
- **<60%** 回頭重整段落設計

**阻斷項**(命中就先修,分數再高也不放行):腳本有任何 ✗、先備知識順序倒置、頁面引用的圖檔不存在、任何外部資源(離線就掛)、核心訊息在投影片與備註中從未出現、文字溢出格子或畫面、build 失敗。連接線轉折只計入第 11 項扣分,不列阻斷(腳本用 △ 標示)。

**流程阻斷**:有任何一頁沒開過就不准給第 5/8/9/10/11/12/13 項分數 — 改寫「未評(第 XX 頁未檢視)」,不要用腳本表格推測;審過期產物同罪,先 build 再看。

## 輸出格式

報告寫入 `review/review-<YYYY-MM-DD>-<序號>.md`(當日已有報告時序號 +1,不覆蓋舊報告),開頭加 metadata:

```yaml
---
id: review-<YYYY-MM-DD>-<序號>
type: review
title: <talk-slug>-review
description: <一句話:本次審查的範圍與結論,40 字內>
created: <YYYY-MM-DD>
scope: full            # full | section-XX(局部審查)
score: <N>/65          # 無圖時 /60
verdict: <判定帶,如:小修即可上台>
---
```

報告內文結構如下;寫完後在**對話中只給摘要**(符合度、判定帶、阻斷項、前三優先修正)與報告路徑:

```markdown
## 檢查範圍
(讀了哪些檔案、幾段幾頁幾張圖;**是否重 build、逐頁開了哪幾頁、用瀏覽器還是讀原始碼**;局部審查要標明)

## 機械檢查
(腳本結果摘要:✗ 逐條列、△ 擇要;無 ✗ 就一句話帶過)

## 逐段評述
| Section | 分鐘 | 分類 | 對核心訊息的貢獻 / 問題 |
|---|---|---|---|
(分類 = 貼題 / 支援 / 呼吸點 / 偏題;偏題與呼吸點寫明理由)
偏題比例:X 分 / Y 分 = Z%

## 逐頁檢視(每一頁都要有一列,✓ 無問題 / △ 待確認 / ✗ 要修)
```

## 紀律

- **證據優先**:每個扣分都要指得出檔案、段落、頁碼,視覺問題還要指得出元素或色值(「第 04 頁 #00ff88 不在 tokens 且不是強調」勝過「配色不統一」);講不出證據的扣分不要寫
- **沒看過不評**:逐頁檢視表缺哪一頁就寫「未檢視」,不要用腳本表格或原始碼推測那頁渲染起來長什麼樣
- **AI 感要留餘地**:先找反面證據(真實數字、專案名、取捨),找不到才扣分;風格偏好是使用者的,`topic.md` 允許的風格與選定的風格基底特性(見 styles.md 各基底 review 提示)不算 AI 感
- **不腦補主軸**:核心訊息以 `docs/topic.md` 為準;覺得主軸本身有問題,寫進建議讓使用者決定,不要自己換一個主軸來評分
- **不重寫內容**:報告寫「哪裡不對、為什麼、建議往哪個方向」,不要在報告裡代寫頁面、備註或 SVG
- 使用者反駁某項評分時,重新檢視證據:證據不足就下修結論,證據充足就把證據攤開,不要為了順從而改分
