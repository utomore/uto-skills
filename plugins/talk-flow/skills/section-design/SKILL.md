# /section-design — 演講段落設計

先讀取 `../_shared/conventions.md`,遵守其中所有文檔慣例。

## 子命令 status

參數是 `status` 時不進入設計流程,直接執行:

```
node <本 skill 目錄>/scripts/scan-status.mjs [docs目錄]
```

腳本掃描 `docs/topic.md` 與 `docs/section-*.md` 的 metadata,輸出各段落的主軸、狀態(open / in-progress / done / rejected)、時長、頁數與圖形,並比對 `topic.md` 的 `sections` 清單找出缺漏。把表格轉述給使用者,不合規項目(缺 metadata、清單不一致、frontmatter 格式)逐條說明。

出現「frontmatter 格式不合規」時,先把該欄位改回行內陣列(`sections: [section-01, section-02]`)再重跑,不要憑印象解讀清單不一致 —— 清單欄位寫成 YAML 區塊列表時腳本讀不到內容,後面的比對結果不可信。

## 前置

1. 讀取 `docs/topic.md`(燈塔)。**不存在時**:告知使用者建議先執行 `/topic-design`,除非使用者明確要求直接寫段落
2. 確認目標段落:使用者指定編號則用之;未指定則列出目前狀態,建議 `order` 最小的 open 段落
3. 讀取目標段落文檔(佔位或既有內容),以及其 `depends-on` 指到的段落文檔;不相關的段落不讀
4. 使用者要新增一個 topic.md 沒有的段落時:先確認它與主軸的關係與時間來源(哪一段讓出時間),取最大編號 +1 建檔,並同步 `topic.md` 的 `sections` 與時間帳

## 流程

### 1. 深度討論(不可跳過)

與使用者反覆討論直到段落完全明確,**不確定就問,禁止腦補**:

- **存在理由**:為什麼需要這個段落?拿掉會怎樣?它替主軸(topic.md 的核心訊息)貢獻什麼?
- **討論方向**:這個片段要往哪個方向談?(問題導向、案例導向、原理拆解、對比取捨、演進脈絡…)哪些點加入、哪些調整、哪些刪除或置換?每個點對這批聽眾是新知還是複習?
- **內文內容與形式**:每個要點要放什麼內容、往什麼方向寫?適合**條列**(並列要點)、**表格**(維度對比)還是**段落文字**(定義、結論)?
- **文字技法選用**:從 `topic.md` 的「文字規範」中**圈出本段會用到的**字級情境、強調方式與列表符號 — 本段有沒有需要強調的結論句(用哪種強調)?條列是並列(圓點)還是步驟(編號)?**只能從規範選,不得新發明**;確實需要規範外的用法時,回 `/topic-design` 把它加進文字規範,不在段落內私設
- **圖形輔助**:哪些要點用講的講不清楚、需要圖?一張圖回答一個問題;不需要圖硬配圖是 AI 感的來源。**使用者提供了截圖或參考圖時,先問是否直接用截圖加註**(以原圖為底疊編號標記,最忠實也最省工),不合適再重畫。需要時從下表選型(也可組合或提出表外類型):

| 圖形類型 | 適用 |
|---|---|
| 架構圖 | 系統元件與依賴關係 |
| 流程圖 | 步驟、判斷分支、資料流 |
| 結構圖 | 組成關係、樹狀階層 |
| 幾何圖 | 抽象概念的空間隱喻(集合、交疊、距離) |
| 包裹圖 | 內外包覆關係(容器、封裝、作用域) |
| 分層圖 | 上下堆疊的層次(協定棧、抽象層) |
| 金字塔圖 | 有數量或重要性梯度的層級 |
| 時間軸圖 | 演進、里程碑、版本歷程 |
| 象限圖 | 兩個維度的定位與取捨 |
| 循環圖 | 迴圈、回饋、生命週期 |
| 對比圖 | before/after、方案 A/B 並排 |
| 漏斗圖 | 逐階段收斂或流失 |
| 網絡圖 | 多對多關係、拓撲 |
| 資料圖表 | 有真實數據時的長條/折線/圓餅 |
| 截圖加註圖 | 實際產品畫面、操作導覽 — 使用者提供截圖或參考圖時,直接以該圖為底疊加編號標記 + 圖下對應圖例,不重畫 |

- **先備知識**:聽這段需要什麼前提?由哪個段落鋪陳(`depends-on`)還是這段自己補?講者自己需要先補什麼?
- **頁面切分**:這段需要 0 頁(純口述)還是幾頁?每頁的一句話重點是什麼?(Layout 怎麼排是 `/section-impl` 的事,這裡只定「每頁講什麼、放什麼、有沒有圖」)
- **時間**:est-minutes 是否要調整?調整會擠壓誰?

討論中使用者若決定**不要這個段落** → `status: rejected`,在文檔記錄拒絕理由,同步 `topic.md`(清單保留、時間帳重算,多出的時間問使用者分給誰),流程結束。

### 2. 產出 `docs/section-<編號:01>-<slug>.md`

frontmatter 依 conventions(`parent-topic: topic`、`order`、`est-minutes`、`slides: 0`(實作後回填)、`diagrams`(規劃的圖形 id,如 `[diagram-02-1]`;無圖留 `[]`)、`depends-on`),內文固定章節:

```markdown
# Section 0x:<段落名稱>

## 段落定位
(存在理由;與 topic.md 主軸的掛勾 — 引用核心訊息說明這段貢獻什麼;本段的討論方向一句話)

## 內容要點
(逐點列出:要講什麼、往什麼方向講;標註新知/複習;討論中被刪除或置換的點記錄於此並附理由)

## 先備知識
- 聽眾:(需要什麼前提;由哪個段落鋪陳或本段自行補充)
- 講者:(需要事前準備或查證什麼)

## 文字技法選用
(從 topic.md「文字規範」圈出本段使用的子集;impl 只能用這裡列的)
- 字級情境:<如 h2 頁標 + 正文條列;用到 h3 格內小標要說明哪頁為什麼>
- 強調方式:<本段用哪幾種、各用在哪些內容上;沒有要強調的就寫「無」>
- 列表符號:<圓點/編號/其他;選了不只一種時說明語意差異>

## 頁面規劃
(0 頁則寫「純口述」與理由;有頁面則每頁一列 — Layout 與圖形繪製留給 /section-impl)
| 段內頁 | 一句話重點 | 內文內容與形式 | 圖形 | 圖形類型與構想 |
|---|---|---|---|---|
| 1 | <這頁要說服聽眾什麼> | <條列:要點方向 / 表格:比什麼維度 / 段落:寫什麼> | diagram-0x-1 或 - | <類型;這張圖回答什麼問題> |

## 備註要點
(講稿已全面簡化為頁內備註;這裡只記本段的關鍵提醒:開頭怎麼接上一段、結尾怎麼交棒、必須講對的措辭或數字、時間警戒點)

## Demo
(無則寫「無」;有則寫目的、操作流程概要、環境需求 — 預設 uv + python + notebook)
```

### 3. 一致性檢查(必做)

1. `depends-on` 指到的段落必須存在,且 `order` 都在本段之前;先備知識段落若是 rejected,回頭與使用者解決(改由本段自補或救回該段)
2. 重算時間帳:所有非 rejected 段落 `est-minutes` 總和 ≈ `duration-minutes`;超支就列出來讓使用者裁決
3. 節奏粗檢:頁數 × 每頁 20–180 秒是否裝得下 `est-minutes`;明顯裝不下就回頭調頁數或時間
4. 比對 `topic.md` 的「大綱與段落規劃」表:名稱、目的、分鐘數、頁數預估有出入時,經使用者同意後更新 `topic.md`(同步 `updated`)

### 4. 收尾

摘要:段落檔案路徑、狀態、頁面與圖形規劃、時間帳結論、topic.md 是否有更新;建議下一個要設計的段落,或(全段落設計完成時)建議開始 `/section-impl`。
