# /section-impl — 演講段落實作

先讀取 `../_shared/conventions.md`、`../_shared/layouts.md`、`../_shared/styles.md`、`../_shared/layers.md`、`../_shared/diagrams.md` 與 `../_shared/wording.md`,遵守所有文檔慣例(metadata、命名、Marp 建置)、版型詞彙、風格基底詞彙、分層詞彙、圖形詞彙與**文案語感規範**。

**文案語感是硬性禁區,寫下任何一個字之前先讀 `wording.md`**:投影片上直接講事情 —— 禁對比翻轉句(「A,不等於 B」「是 A,不是 B」「不是 A,而是 B」「不只是 A,更是 B」…同一句裡否定再翻轉)、禁人稱代名詞(我/我們/你/你們/大家/各位)、禁空泛詞。這條約束標題、副標、內文、表格、圖形標籤與備註,**沒有實作自主權可言**;要做對比就交給版面(兩欄、表格、✓/✗、前後兩頁)。

**標題另有硬性規則(`wording.md` 禁區四)**:每一頁的標題**一句話講完**,寫的是這頁的**重點主軸**(結論或這頁要回答的問題)。**非必要不用逗號** —— 要用逗號把兩件事串起來才寫得完,代表這頁塞了兩個重點,拆頁或砍掉一半。要「描述」的事情(介紹什麼、說明什麼、比較什麼,以及前提、範圍、方法、步驟)放內文與備註,不進標題。

## 實作自主權(本階段的核心原則)

只要符合 `topic.md` 定下的**語意規範**(文字規範的選單、投影片分層的套數與語意、風格基底)與設計文件的**內容規劃**,你擁有**完全的呈現自主權**:

- 每頁選哪個版型、視覺動線怎麼安排、圖形的座標與節點怎麼擺、圖放哪一格多大、哪一頁用哪個背景類別 —— **都由你決定**,不需要也**不得**為了這些選擇回頭修改 `topic.md` 或設計文件
- `theme.css` 的 tokens 是視覺數值的唯一真相:依真實頁面調整字級、間距、`--bg-opacity` 屬於本階段的職權,**調完不必回寫 topic.md**(那裡只記語意)
- 只有**語意或內容本身要變**才回上層:需要規範外的強調寫法或新的背景套數 → `/topic-design`;要拆頁、併頁、換圖形類型、改內容要點 → 先取得同意並回寫設計文件

反過來:規範內的東西不要自己另立一套。字級、強調、列表符號只能從 `topic.md`「文字規範」選;背景只能用「投影片分層」定義過的套數與語意。

## 前置

1. 讀取 `docs/topic.md`(燈塔;不存在時建議先執行 `/topic-design`),特別是 `style-base` 與「投影片風格」(**風格基底決定版面、圖形與節奏的預設方向** — 如 tech-deep 標題固定左上、版型收斂;keynote-impact 大字置中頁為主力)、「**投影片分層**」(有幾套背景、各用在哪、哪些頁型一律關背景)、「**文字規範**」(執行期唯一合法的字級/強調/列表符號選單)與 `talk/src/theme.css` 的 tokens
2. 確認目標段落:使用者指定編號則用之;未指定則建議 `order` 最小、status 為 open 且已完成設計的段落。**目標段落必須已經過 `/section-design`**(內文有「內容要點」與「頁面規劃」章節且非空);只有佔位說明時,告知使用者建議先執行 `/section-design`,除非使用者明確要求直接實作
3. 讀取目標段落設計文件與其 `depends-on` 段落(掌握銜接),特別看「規範外需求」是否已經回 `/topic-design` 處理完;確認 `talk/src/` 鷹架存在(deck-header.md、theme.css、build.mjs;缺了先回 `/topic-design` 補)
4. 掃描 `talk/src/section-*.md` 與 `talk/assets/` 現況,確認本段的 deck 檔與圖形序號沒有撞名

## 流程

### 1. 逐頁排版方案(開工前先想清楚)

對「頁面規劃」的每一頁,依 `layouts.md` 的判斷順序決定**呈現方案**。方案由你決定(實作自主權),開工前**摘要一次**讓使用者知道這段會長什麼樣即可 —— 不必逐頁等待批准;只有**偏離設計文件**(拆頁/併頁/換圖形類型)才需要先取得同意:

- **格局**:從版型詞彙表選 — **整頁單一區塊也是合法選項**(內容是一個整體就不要硬切格),其餘有左右對分、上下對分、上中下、三等份、四象限、上三下三、左三右三、上三下二…;選擇傾向依風格基底(styles.md 各基底的「版面」節,如 workshop-guide 慣用上截圖下步驟);相鄰頁盡量沿用同一版型語彙
- **視覺引導(每頁必答)**:這頁的動線是什麼 — 眼睛從哪進、依什麼順序看、在哪停?動線要與內容邏輯一致(左→右 = 先→後、上→下 = 因→果),強調處就是動線的終點;說不出動線就是版型不對或資訊太多,回頭改格局或拆頁
- **標題(每頁必答)**:先用一句話說出這頁的重點主軸 —— 說得出來,那句話就是標題;要用逗號串兩件事才說得完,先回頭拆頁。標題只留結論或問題本身,描述、前提與方法留給內文
- **內文**:條列、表格或段落文字,放在哪一格;有對比關係的內容用版面承載(兩欄、表格、✓/✗ 兩列),不靠句內翻轉
- **文字技法**:字級、強調方式、列表符號**只從 `topic.md`「文字規範」選**(規範是唯一選單,設計文件不再列子集),不自創;同類內容跨頁用同一種寫法(同是要點就同字級同符號),要做出差異必須有明確理由(如刻意對比)並在備註記錄。設計文件的「規範外需求」還沒回 topic 處理完的,先處理完再實作
- **圖形**:有圖的頁,圖放哪一格、佔多大(限高/限寬),圖是主角還是輔助;連接線方向順著本頁動線
- **分層(每頁必答)**:這頁的背景用哪一個 —— 沿用預設、`bg-none`(圖表/截圖/密集表格頁)、`bg-soft`(文字密)、`bg-strong`(封面/divider/結論)、`bg-2` / `bg-3`(topic.md 定義過語意的第二、三套)。**類別的選用是你的職權**,但只能落在 `topic.md`「投影片分層」定義過的套數與語意內,不自創新的一套;設計文件寫了視覺備註(如「密集表格別讓背景干擾」)就照它的語意對應到類別。真正一次性的一頁才用 `<style scoped>` 覆寫並在備註記理由。背景不得蓋過第一眼落點

與設計文件的「頁面規劃」有出入(實作時發現要拆頁/併頁/換圖形類型)時,先說明理由取得同意並回寫該表。開工時把段落 `status` 改為 `in-progress`。

### 2. 繪製圖形 SVG(有圖的頁才做)

依「頁面規劃」的圖形類型與它要回答的問題,逐張產出 `talk/assets/diagram-<section編號>-<序號>-<slug>.svg`。**畫法由你決定**,遵守 `diagrams.md`:

- 開頭 XML 註解 metadata(`type: diagram`、`diagram-type`、`section`、`status: draft`;註解內不得有連續兩個減號)
- **圖形標籤同受文案語感約束**:標元件與角色的名字(`API Gateway`、`使用者`),不寫「我方系統」、不在標籤裡塞翻轉句
- 圖形紀律(轉折 ≤2、交叉 0、單一流向、標籤貼近、節點 ≤7)、尺寸回推(渲染字級 ≥18px)、配色只用 theme.css tokens 色碼 —— 準則見 `diagrams.md`;風格傾向依 `topic.md` 的 `style-base`(該表也在 `diagrams.md`)
- **畫完用 `/svg-layout` 量測**(normalize → inspect → lint),把 error 修掉再往下 —— 標籤溢出、端點沒貼齊、線穿過節點靠目視看不出來
- **截圖加註圖**(使用者提供截圖/參考圖時):規範見 `diagrams.md` 的「截圖加註圖」節(base64 內嵌、標記 ≤5、編號順序 = 動線順序、說明文字放頁面內文作圖例)
- 一張圖回答一個問題 — 畫完自問這張圖的問題是什麼,答不出來回到設計文件

### 3. 撰寫 Marp 頁面(talk/src/section-XX-\<slug\>.md)

建立與設計文件**同編號同 slug** 的 deck 檔,frontmatter 依 conventions(`type: deck`、`section`、`slides`),內文依排版方案逐頁撰寫:

- 頁與頁之間以 `---` 分隔;整頁類別用 `<!-- _class: title|divider|center -->`,背景類別接在同一個 `_class` 後面(如 `<!-- _class: divider bg-2 bg-strong -->`),內容區用 layouts.md 的 grid 容器 div(**div 與 Markdown 內容之間留空行**)
- 文字內容依設計文件「內容要點」;一頁一重點,不搬運整段文件
- **每一句都是直述句**:內文寫事實、數字、專案名;不得寫出對比翻轉句,不得出現人稱代名詞(設計文件的措辭若違反,實作時改寫成直述句,並回報給使用者)
- **標題就是排版方案定案的那一句**:一句話、非必要不用逗號、只寫這頁的重點主軸;設計文件「頁面規劃」的一句話重點若是描述句(「介紹 X 的流程」)或串了兩件事,實作時改寫成結論句並回報,不要照抄成標題。全簡報標題語法統一(全名詞短語或全結論句,依 `topic.md`「文字規範」)
- 字級、強調、列表符號依排版方案定案的文字技法(出自 topic.md「文字規範」);行距等排版值住在 theme.css,不逐頁覆寫
- 圖形以 `![h:400](../assets/diagram-XX-N-<slug>.svg)` 嵌入規劃的格
- **每頁結尾一個 `<!-- ... -->` 備註**:只寫提醒(要點順序、關鍵措辭、數字、時間警戒),1–5 行,禁止逐字稿、情境描述與口播人稱(「我要跟大家說…」);本段第一頁備註以 `銜接:` 開頭,最後一頁含 `交棒:`(內容依設計文件「備註要點」)
- 段落開頭是否加 `divider` 隔頁,依 topic.md 的演講風格與使用者偏好

### 4. 建置與驗收(必做)

1. 在 `talk/src/` 執行 `node build.mjs`(加上 `topic.md` `outputs` 列的其他格式,如 `node build.mjs html pdf`);build 失敗先修再往下
2. 打開 `talk/dist/slides.html`(可行時用瀏覽器,否則請使用者開)檢查本段每一頁:文字不溢出格子、grid 沒塌陷(格數 = 子 div 數)、圖形清晰且文字讀得到、風格與前後段一致;**逐頁跑 `wording.md` 的自檢清單**(有沒有「不…而是/是/更」的翻轉句、有沒有人稱代名詞、**標題是不是一句話說出這頁的重點主軸**(有逗號串兩件事或在描述這頁要講什麼就當場改寫,兩個重點就提出拆頁)、有沒有空泛詞 —— 標題、內文、圖形標籤、備註全算,命中就當場改掉);**每頁重走一次動線**(第一眼落點是不是重點、閱讀順序有沒有被版面或連接線帶偏)、**文字技法對照文字規範**(字級/強調/列表符號都出自選單、同情境同寫法、標題與內文行距讀起來分得開)、**分層檢查**(背景有沒有搶走第一眼、正文疊在背景最深處還讀得清、該關背景的頁有沒有關、換背景的頁對得上 topic.md 定義的語意、深色頁的角標對比夠不夠)
3. 逐項核對設計文件:「內容要點」每一點都有落頁或落備註;「頁面規劃」每一列都有對應頁面與圖形(拆併頁差異回寫該表,附理由)
4. **分層強度定案(本演講第一個有頁面的段落才做)**:`/topic-design` 在 theme.css 填的 `--bg-opacity` 是起始值,到這裡才有真實頁面可判斷 —— 挑本段**最文字密的一頁**(正文疊在背景最深處讀得清嗎)與**最空的一頁**(畫面不空嗎),不滿意就直接調 theme.css 的 `--bg-opacity` 或換素材,重 build 看到滿意為止。**這是數值調整,不回寫 `topic.md`**;只有需要新增背景套數或改某一套的用途才回 `/topic-design`
5. 回寫 metadata:deck 檔 `slides` = 實際張數、`status: done`;各 diagram `status: done`;docs section 的 `slides`、`diagrams` 回填實際值、`status: done`;`topic.md` 段落規劃表的頁數欄同步(經使用者同意)
6. 節奏粗檢:本段 `est-minutes` × 60 ÷ 頁數落在 20–180 秒/頁之外時告知使用者,建議調頁數或時間

### 5. Demo(僅目標段落有 Demo 規劃時)

- 依設計文件「Demo」章節建立 `demo/`:預設 `uv init` 的 python 專案 + notebook(依使用者要求可置換)
- demo 操作順序寫進該頁備註(提醒式:步驟與預期結果,不寫口播詞);`demo/README.md` 記錄環境建置與執行方式

### 6. 收尾

摘要:本段產出的檔案(deck 檔、圖形 SVG、dist 輸出)、每頁用的版型與背景類別、與設計文件的偏差及理由、**動到的 theme.css tokens(若有)**、節奏檢查結果、**文案語感自檢的結果(改寫掉哪些句子、改寫掉哪些標題;設計文件裡違反規範的措辭有沒有一併回寫)**;建議下一個要實作的段落,或全部完成時建議用 `/page-adjust` 微調、`/section-design status` 總覽,並在上台前跑 `/review` 做整體審查。
