# dev-flow 2.2.1:核心功能模型(feature 重要度絕對、設計檔即真理)

日期:2026-09-04
狀態:2026-09-05 已實作,分四個階段性 commit(doc-lifecycle + spec-redesign → subsys-design / spec-design / 模板 / 其餘 skill 用語 → 腳本與 fixtures → migrate-v3 帳本制遷移)。實際規則以 `_shared/doc-lifecycle.md` 與各 SKILL.md 為準,本稿是設計時的推理與決定紀錄
前提:2.0.0 已把「一個 feature 一份檔、契約住在檔上」做完;本稿只改**分類的意義**與**改動的去處**,不動資料夾樹與腳本的骨架

---

## 0. 一句話

**feature 是「少了它子系統就不能運作」的東西,enhancement 是「少了它照樣運作」的東西;兩者都是新功能。任何對既有功能的改動,一律改那份檔本身,不准另開檔。**

現在的流程把 E 定義成「既有程式碼的優化」,結果每一次改既有功能都會長出一份新檔,而 F 檔從此停在它被寫下的那一天。三個月後沒有人知道 F001 現在到底長什麼樣——要讀完 F001 加上所有指向它的 E,自己在腦中合併。這正是「設計檔即真理」被腐化的路徑。

---

## 1. 現況裡的三個縫(引現行文檔原話)

| 縫 | 現在寫的 | 後果 |
|---|---|---|
| E 的定義 | `spec-design`:「enhance(既有程式碼的優化)」;判準「**有沒有必須被保護的現有行為**——有就是 enhance」 | 任何改動都符合這個判準,於是任何改動都開 E。F 檔永遠是初版 |
| 修訂時的出口 | `spec-redesign` 2A.1:「真要擴張就另開 `E00x`」;2B.4:「已經 `done` 的 feature 檔契約改了時……是否要開 `E00x` 補做由開發者決定」 | 唯一能改 F 的 skill,自己把人往「開 E」推 |
| `done` 的收束 | `doc-lifecycle`:「`## 修訂記錄`……整節搬進 `archive/`」 | F 檔沒有自己的變更史;讀者無法分辨「這是初版」還是「改過三次」 |
| E/B 的生命週期 | 「`E00x` / `B00x` 沒有 `planned` 這一格……建檔當下就是 `specced`」 | E 沒有 `## 契約`,非核心功能沒有 Level 2 邊界,也沒有「明確不做」 |

四個縫指向同一個根因:**E 被當成「動作」(改東西)而不是「東西」(一個功能)。** 分類一旦是動作,檔案就跟著動作長,而不是跟著功能長。

## 2. 新的分類:六種任務文檔,判準各一句話

| type | 意思 | 判準(可查的一句話) | 位置 | 生命週期 |
|---|---|---|---|---|
| **F** | 子系統的核心功能 | 拿掉它,這個子系統就**無法履行 `system.md` 給它的職責** | `subsystems/<slug>/features/F00x` | planned → specced → done |
| **E** | 子系統的擴充功能 | 拿掉它,子系統**照樣履行職責**,只是少了某個好處 | `subsystems/<slug>/enhancements/E00x` | planned → specced → done(**新增 planned**) |
| **B** | 子系統的缺陷 | 某條 law 或 example 在現況下不成立 | `subsystems/<slug>/bugfixes/B00x` | open → closed(不變) |
| **G-F** | 跨子系統核心功能 | 要 ≥2 個子系統各做一段才成立,而且**任一段缺,某個開發階段就達不成** | `.design/features/G-F00x` | planned → specced → done |
| **G-E** | 跨子系統擴充功能 | 要 ≥2 個子系統配合,但拿掉它階段照樣達成 | `.design/enhancements/G-E00x` | planned → specced → done |
| **G-B** | 跨子系統核心功能的障礙 | 某份 G-F 的 law 在現況下不成立 | `.design/bugfixes/G-B00x` | open → closed |

G-C(共用契約)、ADR、SPK 不是任務文檔,維持原樣。

### 2.1 核心判準要寫進檔,不能只在腦中

`## 契約` 多一行,F 與 E 各一種寫法,**腳本查有沒有填**(缺了進「提示」,和契約六欄同級):

```markdown
- **核心判準**:少了它,auth 就無法「讓使用者以憑證換取工作階段」(system.md 子系統劃分 §auth 職責第 1 句)   ← F
- **非核心判準**:少了它,auth 照樣完成登入;它加的是「記住裝置,30 天內免二次驗證」            ← E
```

這一行必須**指到 `system.md` 職責的哪一句**(F)或講清楚**少了它還剩什麼**(E)。指不到職責的 F,就是分類錯了。這是 `contract-readiness.md` A10 的反向:A10 查「職責有沒有落點」,這一行查「落點有沒有職責」。

### 2.2 分類的時機與改錯怎麼辦

- **分類在 `/subsys-design` 規劃當下做**,和鑄號建檔同一個動作。訪談時逐個功能問一句「拿掉它,這個子系統還能不能做 system.md 說的那件事」,答得出「不能」的才是 F。
- **分類錯了(F 其實是 E,或反過來)是唯一允許「刪檔重建」的情況**:type 改、資料夾搬、重新 `--claim` 配號,舊號永久空缺(`scan-ids.mjs` 已略過 archive,空號不會被重用),在 `design.md` 的決策段留一行「F003 重分類為 E002,理由:___」。不允許為了省事把 E 留在 features/ 底下。

### 2.3 重要度絕對 = 分母重新定義

「重要度絕對」落到數字上就是:**子系統能不能運作,只看 F**。

| 指標 | 分子 / 分母 | 誰看 |
|---|---|---|
| **可運作**(新) | F done / F 總數,且無 planned 模組群 | 開發階段的達成條件;PM 的「這個子系統好了沒」 |
| 擴充度(新) | E done / E 總數 | 排程參考,**不進可運作,不擋階段** |
| 開發階段達成 | 涵蓋子系統全部「可運作」,且該階段的 G-F 全 done | 產品級分母,規則不變 |

現在的「進度 1/3 (33%)」欄改成兩欄:`核心 1/3` 與 `擴充 0/2`。`/arch-audit status` §1 的「要達成還差 n 件」只數 F 與 G-F;E 與 G-E 在 §2 平行道照列,但備註「不擋階段」。

## 3. 設計檔即真理:修訂取代新增

### 3.1 唯一的分流問題

要動既有功能時,只問一句:

> **這個改動能不能被描述成「拿掉它,原功能還在、行為不變」?**

| 答案 | 意思 | 去處 |
|---|---|---|
| 能 | 這是一個**新的、可獨立拿掉的能力** | 新檔。核心判準答「不能運作」→ F;答「照樣運作」→ E |
| 不能 | 它**改變了既有功能**的行為、介面、邊界或效能承諾 | **修訂原檔**,走 `/spec-redesign`,不開新檔 |

效能優化、重構、換演算法、改簽名、收回「明確不做」、放寬定義域——全部是「不能」,全部修訂原檔。現在 `spec-design` enhance 模式那套「先讀程式碼、基準線、量化目標、回歸 law」**不是廢掉,是搬家**:它變成修訂輪次的紀律(見 3.3),住在原檔。

### 3.2 三處要反過來寫的規則

| 現在 | 改成 |
|---|---|
| `spec-design`:enhance 判準「有沒有必須被保護的現有行為」 | enhance 判準改成 2 的「非核心判準」;**「有必須被保護的現有行為」= 這是修訂,去 `/spec-redesign`** |
| `spec-redesign` 2A.1:「真要擴張就另開 `E00x`」 | 「擴張 scope 一樣在這份檔裡做:契約追加修訂行、Laws 加條、`rev` +1。只有『能獨立拿掉的新能力』才另開檔,而那不叫擴張,叫新功能,回 `/subsys-design` 分類」 |
| `spec-redesign` 2B.4:「是否要開 `E00x` 補做由開發者決定」 | 「`done` 的檔契約改了,**那份檔退回 `specced`、`rev` +1**,重新委派被動到的 law 與介面。沒有『補做』這個第二份檔」 |
| `doc-lifecycle`「`done` 的收束」:`## 修訂記錄` 搬 archive | `## 修訂記錄` **常駐**,一輪一條摘要;討論過程才搬 archive |

### 3.3 修訂輪次 REV-n

frontmatter 新欄 `rev: 0`(初版 0),每次修訂 +1。原檔常駐一節 `## 修訂記錄`,一輪一條、**只寫結論不寫過程**:

```markdown
## 修訂記錄
- REV-1(2026-09-10,依 auth/GAP-3):過期判定改用伺服器時鐘,不再讀客戶端時間
  - 動到:LAW-2 改寫、LAW-5 新增(時鐘偏移上限)、介面 `refresh(req)` 多一個 `now` 參數
  - 保護:REG-1(既有 session 在修訂前後都還能 refresh)
  - 重委派:qa(LAW-2、LAW-5、REG-1)、impl(`refresh`)
  - 連動:billing/F004-invoice-session 的 `## 契約` 同步(Level 2,design.md「模組間公開介面」§3)
- REV-2(2026-09-18,依開發者:效能):refresh 的 p95 從 400ms 壓到 80ms
  - 動到:LAW-6 新增(p95 ≤ 100ms,基準線 2026-09-18 量測 400ms)
  - 保護:REG-2(輸出一字不變)
  - 重委派:qa(LAW-6、REG-2)、impl(內部,簽名不動)
```

四條規則:

1. **狀態機**:`done` 被修訂 → 退回 `specced`,`rev` +1;`planned` / `specced` 被修訂 → 狀態不變,`rev` +1。做完再推 `done`。
2. **law 編號單調遞增,刪掉的號永久空缺**:REV 刪掉 LAW-3,之後新增的是 LAW-7 不是 LAW-3。`lint-laws-traceability.mjs` 的「幽靈引用」靠這條才抓得到「測試還在守一條已經不存在的 law」;號被重用就抓不到。
3. **REG- 住在原檔**:修訂時「必須不變的既有行為」寫成 `REG-n`,和舊 enhance 的回歸 law 同一個東西,只是不再需要另一份檔來裝。
4. **腳本對帳**(進不一致):`rev` 與 `## 修訂記錄` 的 REV 條數對不上;`done` 但最後一條 REV 的日期晚於 `updated`;REV「動到」點名的 law 在檔裡不存在。

過程(為什麼吵成這樣、否決了什麼)才進 `archive/<F00x-slug>-rev<n>-process.md`,規則沿用「`done` 的收束」。

### 3.4 「修訂中」不是狀態:排隊的修訂用 GAP 記

`specced` 的定義不變:**文檔是完成的,等待實作**。修訂不會產生一個「文檔正在被改」的持久狀態,理由是修訂本來就是一次 `/spec-redesign` 做完的事——定層級、改條文、留 REV、講明重委派誰,同一個 session 內結束。改到一半的檔只存在於 git 的工作區,不是流程裡的一格。

所以 `done` 退回 `specced` 的意思是:**文檔已經是新版本(`rev` +1),實作落後於它**。沒被 REV 點名的 law 測試照樣綠,只重做被點名的那幾條。

「知道要修、還沒修」這個狀態**已經有家**:開一條 GAP。`spec-gaps.md` 的條目不限 qa / impl 提出,開發者自己發現設計有問題也寫一條(`## GAP-4(auth/F001-login / 開發者)`),那份檔就會被標 `⚠卡`、派工狀態變「卡住」、`/subsys-build` 會擋。修完 GAP 結案、REV 的「依」欄指到它。這樣一來:

| 時刻 | 文檔長什麼樣 | 派工報告怎麼看 |
|---|---|---|
| 發現要改,還沒改 | `status` 不變,`spec-gaps.md` 多一條 open | 卡住(等修 spec) |
| `/spec-redesign` 改完 | `rev` +1、`## 修訂記錄` 多一條、`done` 退回 `specced`;GAP resolved | 可開工(`/spec-build`,只重做 REV 點名的) |
| 實作重做完 | `done` | — |

不加 `revising` 狀態的代價是 status 欄看不出「這是修訂後的 specced」,要看 `rev`;報告裡印成 `auth/F001-login(rev 2)` 就夠了。

### 3.5 升版不是一個決定,是紀錄的副作用

沒有「要不要對外升版」這件事要決定。`/spec-redesign` 每改完一次就追加一條 REV 並把 `rev` +1,**兩者是同一個動作**,人不另外判斷。`rev` 只是 `## 修訂記錄` 條數的快取——腳本查兩者對不上就報不一致,所以它不會成為第二個真理。

「下游出問題編譯就會知道」對一半:簽名改了,編譯器與骨架會抓;**law 的語意改了,什麼都不會抓**——型別沒變、意思變了,下游的契約文字還寫著舊語意、測試照樣綠。所以要有一條對帳,但責任先放在**改的人**身上,對帳只是接住漏網的:

1. **推**:`/spec-redesign` 2B.3 本來就要求改的人跑 `scan-status --doc` 拿反向依賴、逐份同步下游契約,並把同步過的下游寫進 REV 的「連動」欄
2. **對帳**(提示,不進 exit code):X 依賴 Y,Y 最後一條 REV 的日期晚於 X 的 `updated`,**而且那條 REV 的「連動」欄沒點名 X** → 「Y 修訂到 rev n 時沒有點名 X,X 也沒對過帳」。改的人有列到 X 就不報——這樣提示消失的方式是「上游盡到責任」,不是「下游 bump `updated` 表示看過了」。純比日期的版本會逼出那個儀式,而儀式一定會變成沒看就 bump
3. 兩邊都沒做到的語意影響 → 由整合測試或之後的 B 文檔抓,接受

## 4. G-F:跨子系統核心功能

### 4.1 為什麼需要它

現在跨子系統只有 G-E(優化)與 G-B(修復),沒有「跨子系統的**新核心功能**」這一格。結帳、下單、同步這種要 auth + billing + notify 各做一段才成立的功能,現在只能拆成三份各自的 F,而「三段接起來能不能用」沒有任何文檔負責——端到端的 law 沒有家。

### 4.2 形狀

`.design/features/G-F001-<slug>.md`:

```yaml
---
id: G-F001
type: feature
title: checkout
description: 使用者能把購物車結成一張已付款的訂單
status: planned
stage: S2                    # 必填:它是某個階段的達成條件
rev: 0
subsystems: [cart, billing, notify]
created: 2026-09-04
updated: 2026-09-04
depends-on: []
related-adr: []
code-paths: []
---
## 契約
- **核心判準**:少了它,S2(商務上線)無法達成——沒有任何一條路徑能從購物車走到已付款
- **分工**:
  | 子系統 | 負責的段 | 承接的 feature |
  |---|---|---|
  | cart | 鎖定購物車、產生訂單草稿 | cart/F004-order-draft |
  | billing | 收款、開立發票 | billing/F002-charge |
  | notify | 付款結果通知 | notify/F001-payment-mail |
- **端到端介面**:引用 G-C 條目(`G-C002-order#OrderId`)與各子系統對外契約
- **驗收標準**:端到端(從 cart 的入口到 notify 的出口)
- **明確不做**:退款(那是 G-F002)
## 介面 / ## Laws / ## Examples
Laws 的觀察點**必須跨過至少一條子系統邊界**——只在單一子系統內就觀察得到的 law 不屬於 G-F,搬去那個子系統的 F
```

各子系統那一段就是**各自的普通 F**,frontmatter 加 `part-of: G-F001` 回鏈。**分工表是權威,`part-of` 是索引**,腳本雙向對帳(表列了的 F 沒有 `part-of`、或 `part-of` 指到的 G-F 分工表沒列它,都是不一致)。

### 4.3 生命週期與腳本判準

| status | 判準 |
|---|---|
| planned | 有 `## 契約` 與分工表,分工表每一列都指到一份存在的 F |
| specced | 有端到端 Laws;分工 F **不必**都 specced(它們各自走自己的漏斗) |
| done | 分工 F **全部** done,且端到端測試綠;分工 F 有未 done 而 G-F 標 done = 不一致 |

G-F 的派工狀態(2.2.1 的 §2–§4 那套)多一種「卡住」原因:**等分工 F**——腳本把未 done 的分工 F 列成「卡它的」,解法是去做那份 F。

G-E 同一個形狀、非核心判準、不擋階段。G-B 的 `related-feature` 指 G-F,修復流程沿用 `/bugfix`。

### 4.4 G-C 還需不需要:能不能被 G-F / G-E 取代

G-C 與 G-F 答的是兩個不同的問題:G-C 答「**這個共用事實歸誰**」(知識歸屬,沒有做完的一天),G-F 答「**這個跨系統功能做完了沒**」(任務,有生命週期)。能不能合併,看共用事實的三種情況:

| 情況 | 例 | 住 G-F 行不行 |
|---|---|---|
| A. 只被一份 G-F(含它的分工 F)用 | `OrderId` 只出現在 G-F001-checkout | **行,而且應該**。型別就是那個功能的介面,寫進 G-F 的 `## 介面`,分工 F 引用 `G-F001-checkout#OrderId`。另建 G-C 是憑空多一層 |
| B. 被兩份以上 G-F / G-E 用 | `OrderId` 同時出現在 checkout、refund、invoice | **不行**。住在 checkout 裡,refund 改 `OrderId` 就得修訂 checkout(REV +1、`done` 退回 `specced`),而 checkout 的程式碼可能一行都沒動——派工報告 §3 會多出一條假的「卡住」。歸屬落在「碰巧先定義它的那個功能」,那是歷史偶然,不是知識歸屬 |
| C. 被兩個以上子系統用,但沒有任何 G-F 擁有那段互動 | 全域錯誤碼表、事件信封、id 格式 | **不行**。這些是慣例不是功能,硬造一份 G-F 會得到一個永遠答不出「做完了沒」的假 feature。放 `system.md` 也不行——那是 Level 1,`/arch-audit system` 第 4 項會把欄位表判成越界 |

B 與 C 就是 G-C 的存在理由,而且正好是「設計檔即真理」最需要的東西:**任何時刻每個事實只有一個家**。廢掉 G-C 不會讓這個需求消失,只會讓它回到 2.0.0 之前的樣子——塞進某一份 G-F 或某一個子系統的 `design.md`,再讓別人引用。

結論:**保留 G-C,但縮窄,並加一條升格 / 降格規則**:

1. **單一 G-F 用的型別住 G-F**,不建 G-C(情況 A)。`subsystems` 欄的「至少兩個」規則改成「**至少兩份 G-F / G-E,或兩個以上子系統且沒有 G-F 擁有那段互動**」
2. **第二個消費者出現時升格**:型別從 G-F 搬進 G-C,原 G-F 記一條 REV「`OrderId` 升格為 `G-C002-order#OrderId`,本檔改為引用」——同一時刻只有一個家,搬家留痕
3. **只剩一個消費者時降格**:反向搬回那份 G-F,G-C 條目標 `superseded`
4. 腳本兩條提示(不進 exit code):G-C 的條目只被一份 G-F 或一個子系統引用 → 「該搬回」;某份 G-F `## 介面` 定義的型別被別份 G-F 引用 → 「該升格」。這是 `contract-readiness.md` B2「投影 vs 複製」的機械那一半

對 2.2.1 現有 fixture 的示範專案來說:`G-C001-session`(auth 發、billing 驗)在新模型下多半是情況 A——「跨系統 session 驗證」本身就是一份 G-F,`SessionToken` 該住那份 G-F;等第二份 G-F 也要用它,再升格。

### 4.5 誰跑

`/subsys-build` 是子系統級的委派,**不跑 G-F**。G-F 的端到端 spec 與測試由人跑 `/spec-design G-F001-checkout` 與 `/spec-build G-F001-checkout`;它的 qa 只能讀 G-F 本身與它引用的 G-C 條目,**不能讀分工 F 的 spec**(qa 的「別人的 spec 不准看」規則不變)。

## 6. 既有專案的遷移

每一份既有 E / G-E 都要人判一次,**腳本只列清單、不自動摺**:

| 這份 E 是 | 處置 |
|---|---|
| 改既有 F 的行為 / 介面 / 效能(有 REG- 或「修改」列) | **摺回那份 F**:契約追加修訂行、Laws 併入(REG- 保留)、`rev` +1、`## 修訂記錄` 補一條 REV;E 檔搬 `archive/`,號永久空缺 |
| 新的、可獨立拿掉的能力 | 留在 enhancements/,補 `## 契約`(含非核心判準);已 done 的 status 不動 |
| 兩者混 | 拆:能獨立拿掉的留 E,其餘摺回 F |

`migrate-v3.mjs` dry-run 印三欄:E 全名、它的「數據與介面變動」表有幾列「修改 / 移除」(有 = 傾向摺回)、`related-feature` 指誰。人逐份決定後 `--apply` 只做機械的搬檔與 frontmatter,Laws 合併由人寫。遷移前後 **done 的 F 份數必須相等**(沿用 migrate-v2 的對帳原則);摺回讓 F 退回 specced 的,列進「遷移後要補的」。

沒有既有 G-F 可遷:它是新格。

### 6.1 既有專案遷移的實際步驟(`migrate-v3.mjs`)

判準是「2.0.0 之後的樹」:有 `features/F00x` 檔、契約住在檔上。更早的專案先跑 `migrate-v2.mjs`。

| 步驟 | 機械(腳本 `--apply` 做) | 人判(腳本只列清單) |
|---|---|---|
| 1. F / G-E 加欄 | 每份 F 補 `rev: 0`;`## 契約` 補一行 `- **核心判準**:待補`(缺就進提示,和契約六欄同級) | 逐份把「待補」填成指到 `system.md` 職責的一句;填不出來的就是分類錯了,走 2.2 重分類 |
| 2. 既有 E / G-E 分流 | 印三欄:全名、「數據與介面變動」表有幾列「修改 / 移除」、`related-feature` 指誰 | 每份三選一:摺回 F(它改了既有功能)/ 留 E(可獨立拿掉的新能力)/ 拆 |
| 3. 摺回 | 依人的決定:E 檔搬 `archive/`(號永久空缺)、目標 F `rev` +1、`## 修訂記錄` 補 REV(依欄寫「遷移自 auth/E002-…」)、`status` 若 E 未 done 則 F 退回 `specced` | Laws 合併(REG- 併入原檔、衝突的條文取捨) |
| 4. 留 E | `status` 不動;`## 契約` 骨架補上(六欄 + 非核心判準,值留空) | 填契約;填不出「非核心判準」的,回步驟 2 重判 |
| 5. G-E → G-F | 印每份 G-E 的 `subsystems` 與它是否出現在某個開發階段的達成條件 | 人判是核心就改 type、搬 `.design/features/`、重新配號 G-F;分工表由人寫 |
| 6. 對帳 | `done` 的 F 份數遷移前後相等;每份摺回的 E 在 archive 找得到;`rev` 與 REV 條數一致 | — |

先不帶 `--apply` 看三張清單(要填的核心判準、要分流的 E、要重判的 G-E),決定了再落地。做完跑 2.2.1 的 `scan-status.mjs`:新欄位它已經認得,舊欄位一個都沒拿掉,遷移中途也跑得動。

### 6.2 逐步判斷:帳本檔,不做臨時 skill

遷移是大工程,但不必一次做完——**一份 E 一個決定,決定可以跨好幾個 session 慢慢下**。要能逐步,狀態就不能只活在對話裡(下一個 session 就忘了),所以把它放進一份帳本:

`.design/migration-v3.md`(遷移期間存在,做完刪,`type: migration`,不編號、不進分母):

```markdown
| 文檔 | 提示 | 決定 | 目標 | 狀態 | 日期 |
|---|---|---|---|---|---|
| auth/E001-token-cache | 修改 2 列、related auth/F002 | 摺回 | auth/F002-token-refresh | Laws 已合併,待 --apply | 2026-09-05 |
| auth/E002-remember-device | 新增 3 列、無 related | 留 E | — | 契約待填 | 2026-09-05 |
| pay/E001-money | 修改 1 列、新增 2 列 | 拆 | pay/F001-charge + pay/E001 | 未決 | |
| G-E001-cache | subsystems 2、不在任何階段 | 未決 | | | |
```

三方分工:

| 誰 | 做什麼 |
|---|---|
| `migrate-v3.mjs`(不帶旗標) | 掃 E / G-E,帳本沒有的補一列(提示欄由腳本填:介面表幾列修改 / 新增、`related-feature`、Laws 數、code-paths 與目標 F 重疊幾個);印**下一份未決的**,附它的契約與介面表原文 |
| 人 + LLM(對話) | 看那一份,用 3.1 的分流問題討論,把「決定 / 目標」寫進帳本。**一次一份**,決定不了就留未決往下一份 |
| `migrate-v3.mjs --apply` | 只處理帳本裡「決定已下、狀態未完成」的列,做機械的那半(搬檔、frontmatter、REV 條目、archive),回寫狀態欄;Laws 合併留給人,狀態寫「Laws 待合併」 |

不做臨時 skill 的理由:skill 的價值在「載入紀律 + 觸發詞」,遷移只有一個入口(這支腳本)和一條分流問題(3.1),寫進 `arch-audit` SKILL.md 現在放 `migrate-v2.mjs` 的那一段就夠,做完刪那一段。多一個 skill 就多一份要在遷移結束後拆掉的東西。

「直接說」當然也行——對話本身就是決定的地方;帳本只是讓決定**落地、可續、可查**。判斷不在腳本裡:它永遠不會替你在「摺回 / 留 / 拆」之間選。

對帳沿用 6.1 第 6 步,加一條:帳本每一列狀態都是「完成」才准刪帳本,刪帳本那一刻 `done` 的 F 份數與遷移前相等。

## 7. 為什麼不用 `F001v2` 這種在 id 裡帶版本的寫法

「版本持續前進」是對的需求,但把版本放進 id 會付三筆代價,每一筆都直接撞上「設計檔即真理」:

1. **每一次修訂都要改所有引用**。`depends-on: [auth/F001]`、`part-of`、GAP 標題、spike 的 `feeds`、測試檔裡的 `spec: auth/F001` 與 `auth/F001#LAW-3`——修訂一次,這些全部要跟著改成 `F001v2`,漏一處就指到舊版。`lint-laws-traceability.mjs` 會在修訂後把每一個測試都報成幽靈引用,直到有人逐檔改完。這正是文檔腐化的另一條路:引用指到的東西不再是現況
2. **檔名一改,一份功能就變成兩個 id**。`scan-ids.mjs` 要決定 `F001v2` 是新號還是舊號的別名,git 的 `--follow` 也斷;而「一個 feature 一份檔,從搖籃到墳墓」是 2.0.0 最重要的一條
3. **版本掛在 id 上等於允許舊版繼續被引用**。`billing/F004` 寫 `depends-on: [auth/F001v1]` 在語法上合法,於是同一時刻有兩個「真理」。單一真理的意思是:引用永遠指現況,誰落後由腳本點名

`rev` 欄給的正是同一件事,而且沒有這三筆代價:單調遞增、住在檔裡、id 不動、腳本對帳。

「引用的人不知道上游改過」這個真正的擔憂,用**一條對帳**解決,不用改 id:X 的 `depends-on` / `part-of` 指到 Y,Y 的最後一條 REV 晚於 X 的 `updated`、而且那條 REV 的「連動」欄沒點名 X → 提示(規則與理由見 3.5)。報告裡把 rev 印出來(`auth/F001-login(rev 2)`),讀者一眼看得到版本,引用寫法一個字不變。

唯一帶版本的檔名是 `archive/F001-login-rev2-process.md`——退場區的過程紀錄,沒有人引用它,所以無所謂。
