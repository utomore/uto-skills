# 里程碑一律用全名;調整(RF-n)退場

2026-09-20 使用者拍板,兩個 plugin(dev-flow、lawful)一起做,同一個 PR(分支 `feat/milestones-only`)。這份是紀錄,不是規章。

## 1. 引用里程碑一律用全名
引用一條里程碑一律寫全名 `M-n-<slug>`:CLI 印出來的每一句、REV 的依欄、決策紀錄、commit 訊息、PR 內文、回報、下一步的指令。`M-n` 只是配號用的編號。CLI 的輸入給編號時靜默認得,印出來一律是全名。

## 2. 調整(RF-n)退場
使用者問「RF 是什麼」——這個詞本身是負擔。上一輪加了「里程碑可以綁既有的文檔(靠修訂達成)」之後,調整與這種里程碑是同一件事:在某條需求底下,修訂既有的文檔,走到一個使用者看得到的階段(「結帳一秒內完成」)。合成一個概念:

- 需求檔只有一張表:里程碑表。`RF-n`、調整表、`requirement refinement` 指令、status / 看板 / brief 裡的調整欄位與段落、規章與 skill 裡的「調整」,全部不存在。把既有的東西改快、改小、改好,就是這條需求底下再加一條里程碑,綁既有的文檔。
- **靠修訂達成的里程碑怎麼算達成**(取代調整原本「REV 引用 RF-n」那一套,同時補上上一輪留下的洞:綁上一份 verified 的文檔,里程碑當場被算成達成):
  - 一份文檔被好幾條里程碑綁定時,**最先綁它的那一條**(照需求的優先與編號、里程碑表的列序)是做出它的里程碑:達成 = 這份文檔達成。
  - **後來才綁它的里程碑**是靠修訂它達成的:達成 = 這份文檔達成,**而且**它的修訂記錄裡有一條 REV 的依欄引用了這條里程碑(比對的是編號 `M-n`;規章要求寫全名)。
  - 所以 `require-design` 談需求的當場就可以把既有的文檔填進綁定欄(`--bind`),不必等修訂開工才填;在那條 REV 出現之前,status 顯示這條里程碑「待修訂」,下一步是 `scope-revise <文檔全名>`(既有的 law 不動、新的承諾用新增的 law 表達)或 `scope-laws <文檔全名>`(要調整既有的 law),REV 的依欄寫這條里程碑的全名。
  - 里程碑依序:沒有「里程碑全部達成之後才能開調整」這條規矩了,先後就是里程碑表的列序。
- **需求仍要達成**:修訂之後需求的驗收測試要綠,這件事由既有的「里程碑全部達成而驗收沒過」警訊承接。

## 3. CLI
- `requirement refinement` 不存在;`requirement milestone <R-n> <slug> <一句話> --bind <既有的文檔全名>` 就是原本加調整的做法。
- 讀取層:需求檔的調整表靜默照讀——每一列讀成一條里程碑(編號就是 `RF-n`、沒有英文名、綁定 = 「動到」欄),排在里程碑表之後;REV 依欄的 `RF-n` 照同一套規則算引用。規章不提。status 多一條警訊指到 `migrate requirements`;寫檔的指令在這種樹上停下來叫人先 migrate。
- `migrate requirements`:調整表的每一列換成里程碑表的一列——配新的 `M-n`(全資料夾最大號往上),沒有英文名(列進「人要判的」:補英文名),綁定 = 「動到」欄;每份文檔修訂記錄裡依欄的 `RF-n` 改寫成新的 `M-n`;調整表刪掉。帳本逐列印對照(`RF-1 → M-7`)。與其他兩道(lawful 是三道)migrate 以任何先後接連跑,落地的樹仍然相同。
- status:摘要行、需求表沒有調整;每條需求「下一個里程碑」那一行對靠修訂達成的里程碑印「待修訂」與下一步;`--json` / 看板資料沒有 `refinements`,里程碑多一個欄位講它是不是靠修訂達成的、REV 引用了沒。看板頁面(兩個 plugin 逐位元組相同)若讀 `refinements` 就跟著改,並跑 `tests/board`。
- brief:`requirement` 區塊、`scope-revise` 的說明裡的調整字樣拿掉。

## 4. 規章、skills、模板、夾具
- 「調整」「RF-n」「refinement」「優化」作為這個概念從規章、skills、模板、README、plugin 說明、CI 範本裡消失(「調整實作」「調整既有的 law」這種一般動詞不算)。`scope-revise` 的來源從「調整 RF-n」改成「一條靠修訂這份文檔達成的里程碑」;`require-design` 的「調整」那一步併進「切里程碑」(綁既有文檔的里程碑);「里程碑可以綁既有的文檔」那一條照 §2 改寫(當場就綁、REV 引用才算達成)。
- 模板 `requirement.md` 只剩里程碑表。
- 夾具:有調整表的(dev-flow `goals`、`shaky`;lawful `save-game`、`broken`、`preflow`、`verified-ref` 等)換成靠修訂達成的里程碑;留一個「REV 已引用 → 達成」與一個「還沒引用 → 待修訂」的例子;migrate 的輸入夾具(`goals`、`flat`、`preflow`)保留調整表當輸入,並驗靜默照讀。

## 5. 改規章與 skills 時自己決定的事(契約沒寫)
- **修訂做在哪條分支**:靠修訂達成的里程碑,修訂做在它的 `build/M-n-<slug>`(沿用上一輪對「里程碑綁既有文檔」的規定);來源不是里程碑的修訂(GAP、bug、開發者的話)照舊開 `build/<文檔全名>`。原本調整走的是 `build/<文檔全名>`,這一點跟著里程碑走了。
- **一條里程碑綁好幾份既有文檔**:每一份各一次修訂、各一條依欄引用它的 REV(沿用調整原本「動到的每份各一條 REV」)。規章的「完成度」寫成:還沒有那條 REV 是「待修訂」,有 REV 而文檔未達成是「進行中」。
- **混合的里程碑**(既要一段新的貫通、又要修訂既有文檔):roles.md「分支與所有權」寫成既有文檔的條文由修訂的 skill 在 `build/M-n-<slug>` 上改,另外要的那一段新貫通由 `spike-impl` 在同一條分支上只做新的那一段。綁定欄已經有既有文檔時 status 不會再說「還沒有切片」,這種里程碑要不要先跑 `spike-impl` 只能靠 `require-design` 的回報講。
- **重排列序**:「最先綁」由列序決定,所以加了一條規矩:重排里程碑時,綁同一份文檔的幾條之間,做出它的那一條排最前面(features.md / pipelines.md 與 `require-design` 的「重排與修改」)。沒有加 lint。
- **`require-design` 的 `--bind`**:撐這個階段的文檔已經存在、已經做到、而且還沒被任何里程碑綁定,才當成「做出它的里程碑」直接綁;已經被別條里程碑綁過的,綁上去就是靠修訂達成的里程碑。
- **migrate 的輸入怎麼講**:CLAUDE.md 規定舊 → 新只准出現在遷移工具與 `kickoff` 前置那一句,所以「調整表」三個字只出現在兩份 `kickoff`;tooling.md 的 `migrate requirements` 列、status 警訊清單與根 README 用不點名的條件句:「需求檔裡除了里程碑表還有別張表的樹」。同一列的「人要判的」補了「沒有英文名的里程碑」。
- **拿掉而沒有替代的**:status 警訊「調整之後需求未達成」(由「里程碑全部達成而驗收沒過」承接)、「調整動到這條需求的里程碑沒綁過的文檔」(里程碑可以綁任何既有文檔,跨需求也行,需求的依賴由綁定推)。收尾定錨「主軸檢查」的偏離清單裡,那一項換成「靠修訂達成的里程碑的 REV 依欄沒有寫它的全名」。
- **audit 第 6 題**:從「調整有沒有偷渡新 feature」改成「靠修訂達成的里程碑有沒有偷渡新能力」:那一句看不看得到、量不量得到;REV 的保護欄含不含需求的驗收引用的 law;加進來的若是可以獨立拿掉的新能力,它該是做出新文檔的里程碑。
- **例子**:規章的需求檔範例多一列 `M-4-fast-checkout`(結帳一秒內完成,綁 `F-001-checkout`)/ `M-4-small-save`(存出來的檔案不超過 1 MB,綁 `P-001-save-write`);dev-flow `scope-revise` 量基準線那一步的例句跟著換成「結帳一秒內完成;基準線量到 2.4 秒」。
- **需求的依賴**:dev-flow 的 features.md 與 tooling.md 補上 lawful 已經有的那半句——綁了別條需求的里程碑先綁過的文檔,也算依賴那一條(兩邊的 status 都這樣算)。
- **用字**:宣告式自查的樣式會命中「後來才」,規章裡寫成「最先綁它的那一條 / 其餘綁它的每一條」。
- **frontmatter**:`require-design` 的 description 拿掉「調整、refinement、RF-n」,補一句「把既有的東西改快改好也是一條里程碑」;`scope-revise` 的觸發詞留「效能調整」,`RF-n` 換成「靠修訂達成的里程碑」。
